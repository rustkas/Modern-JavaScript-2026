
# Часть VI. Современная архитектура

## Глава 23. Baseline и современная Web Platform: совместимость как инженерное решение

В 2026 году разработчику уже недостаточно знать, существует ли определённый Web API или синтаксическая возможность JavaScript. Для production-разработки необходимо понимать, **насколько равномерно эта возможность реализована в браузерах и когда её можно безопасно использовать без специальных обходных решений**.

Именно эту задачу решает **Web Platform Baseline**.

Baseline не является новой версией JavaScript, стандартом браузера или набором обязательных API. Это система классификации совместимости, которая показывает, насколько широко определённая возможность поддерживается основными браузерами. Изначально инициатива была предложена Chrome, а сейчас её определением занимается WebDX Community Group. В основной набор входят Chrome для desktop и Android, Edge для desktop, Firefox для desktop и Android, а также Safari для macOS и iOS.

Для JavaScript-разработчика Baseline важен потому, что позволяет заменить вопрос:

> «Работает ли эта технология в браузерах?»

на более точный:

> «Какой уровень браузерной поддержки имеет эта технология и соответствует ли он требованиям моего проекта?»

Это важное изменение инженерного мышления. Современная разработка больше не требует автоматически избегать каждой новой возможности или, наоборот, безусловно использовать всё самое новое. Необходимо определить целевой уровень поддержки, проверить статус конкретной возможности и выбрать подходящую стратегию совместимости.

## 23.1. Что означает Baseline

В 2026 году Baseline использует два основных уровня зрелости.

### Baseline Newly available

Функция становится **Baseline Newly available**, когда она становится интероперабельной во всём основном наборе браузеров.

Это означает, что функция уже появилась во всех основных браузерных движках, но ещё не обязательно является оптимальным выбором для проекта с очень консервативной матрицей поддержки.

Например, функция может стать Newly available в 2026 году, потому что последний из основных браузеров только что реализовал её.

**Newly available означает:**

- технология стала межбраузерной;
- основные браузеры имеют её реализацию;
- разработчик может начинать использовать её в проектах, если целевая аудитория допускает такую политику;
- для старых браузеров или специальных корпоративных окружений всё ещё может потребоваться запасной вариант.

Таким образом, Newly available — это прежде всего **граница интероперабельности**.

### Baseline Widely available

Статус **Baseline Widely available** присваивается через 30 месяцев после достижения интероперабельности.

Эта граница предназначена для проектов, которым необходима более консервативная политика поддержки. По данным, использованным при формировании модели Baseline, примерно за этот период большинство пользователей успевает перейти на версии браузеров, поддерживающие соответствующую возможность.

Следовательно:

**Newly available = технология уже интероперабельна.**

**Widely available = технология давно интероперабельна и подходит для значительно более широкого круга production-сценариев.**

Эти статусы нельзя считать абсолютными гарантиями. Конкретный проект может иметь собственные требования, например поддержку старых корпоративных браузеров, встроенных WebView или устройств с контролируемой версией браузера.

## 23.2. Baseline — не список «всего, что можно использовать»

Baseline не устанавливает универсальное правило:

> «Если функция Baseline, её всегда можно применять».

Статус Baseline отвечает только на вопрос о совместимости с определённым набором браузеров и их версиями.

Архитектурное решение требует ещё нескольких параметров:

1. **Целевая аудитория.** Необходимо знать, какие браузеры и устройства реально используют пользователи. Для публичного сайта это одни данные, для корпоративного приложения — другие.

2. **Минимальная версия браузера.** Корпоративное приложение может поддерживать значительно более старые браузеры, чем публичный сайт. Например, если организация использует стандартизированные корпоративные сборки с фиксированными версиями.

3. **Цена fallback.** Если современная функция недоступна, необходимо определить, можно ли заменить её другим API или предоставить упрощённый интерфейс. Разные функции имеют разную стоимость альтернативной реализации.

4. **Критичность функции.** Отсутствие декоративной анимации допустимо компенсировать упрощённым интерфейсом. Отсутствие механизма авторизации — уже архитектурная проблема, требующая обязательного решения.

5. **Среда выполнения.** Браузер, WebView, embedded browser и серверный JavaScript-runtime могут иметь разные наборы возможностей. Например, WebView в мобильных приложениях может использовать более старую версию движка.

Поэтому Baseline является **входными данными для архитектурного решения**, а не самим архитектурным решением.

## 23.3. Современный JavaScript без избыточной транспиляции

Baseline особенно важен для определения того, сколько совместимого кода действительно необходимо отправлять пользователю.

Современный JavaScript уже содержит большое количество возможностей, которые поддерживаются браузерами на широком уровне:

- ES-модули (`import`/`export`) — статус Baseline Widely available.
- Динамический `import()` — статус Baseline Widely available.
- `Promise` и `async`/`await` — статус Baseline Widely available.
- `Set` и `Map` — статус Baseline Widely available.
- Современные методы массивов (`toSorted()`, `toReversed()`) — статус Baseline Widely available.
- `URL` и `URLSearchParams` — статус Baseline Widely available.
- Многие современные Web API — Fetch, Web Workers, Web Storage, Canvas — статус Baseline Widely available.
- Import Maps — статус Baseline Widely available.

Это позволяет во многих проектах уменьшать объём исторического слоя совместимости (транспиляции и полифилов).

Однако из этого **не следует**, что в 2026 году транспиляция и полифилы больше не нужны.

Если приложение имеет целевой браузер, который не поддерживает определённую возможность, остаются три основных решения:

- отказаться от этой возможности;
- предоставить альтернативную реализацию (fallback);
- использовать транспиляцию или полифил.

Выбор определяется целевой матрицей браузеров, а не календарным годом.

Поэтому правильный принцип 2026 года выглядит так:

> **Не транспилируйте JavaScript автоматически ради старых браузеров, которые ваш проект фактически не обязан поддерживать. Но и не отказывайтесь от транспиляции там, где целевая аудитория действительно требует её.**

## 23.4. Baseline и Progressive Enhancement

Baseline хорошо сочетается с архитектурным принципом **Progressive Enhancement**.

Progressive Enhancement означает, что приложение сначала предоставляет базовый рабочий сценарий, а затем использует более современные возможности там, где они доступны. MDN определяет этот подход именно как предоставление основного содержания и функциональности максимально широкой аудитории с последующим улучшением опыта в современных браузерах.

Для JavaScript-приложения это означает следующую последовательность:

### Шаг 1. Базовый сценарий

Основная задача должна иметь рабочее решение без зависимости от необязательной современной возможности.

Например, форма должна иметь нормальный HTML-механизм отправки, работающий даже если JavaScript не выполнился.

### Шаг 2. Проверка возможности

JavaScript определяет, доступна ли современная функция:

```javascript
if ('someFeature' in globalThis) {
  // современная реализация
} else {
  // запасной вариант
}
```

### Шаг 3. Улучшение

Если API доступен, приложение получает дополнительную функциональность или более качественный пользовательский интерфейс.

Такой подход особенно полезен для Web API, которые ещё не достигли Widely available или имеют ограниченную поддержку (например, Scoped Custom Element Registries или File System Access API).

При этом Progressive Enhancement не означает, что абсолютно каждое приложение должно работать без JavaScript. Для сложного приложения JavaScript может быть обязательной частью основной архитектуры. Принцип означает другое: **критические пользовательские возможности не следует без необходимости связывать с необязательными возможностями платформы.**

## 23.5. Feature Detection вместо определения браузера

В 2026 году проверка конкретной возможности предпочтительнее определения конкретного браузера.

**Плохой архитектурный подход (browser sniffing):**

```javascript
if (browser === 'SomeBrowser') {
  // ...
}
```

**Надёжный подход (feature detection):**

```javascript
if ('URLPattern' in globalThis) {
  // использовать URLPattern
} else {
  // использовать альтернативную реализацию
}
```

Feature Detection проверяет реальное состояние среды выполнения, а не предполагает его на основании названия браузера или номера версии. User-Agent и связанные с ним признаки не дают надёжной гарантии фактических возможностей среды, поскольку могут быть подделаны, изменены или не отражать точную версию движка.

**Важно:** Особенно важно различать **наличие API** и **готовность среды выполнить конкретную операцию**.

Например, для `SharedArrayBuffer` недостаточно проверить существование конструктора:

```javascript
if (typeof SharedArrayBuffer !== 'undefined') {
  // этого недостаточно
}
```

Необходимо также учитывать состояние cross-origin isolation:

```javascript
if (
  typeof SharedArrayBuffer !== 'undefined' &&
  globalThis.crossOriginIsolated
) {
  // SharedArrayBuffer можно использовать
}
```

Таким образом, feature detection должен проверять **реальное предусловие конкретной функции**, а не только наличие её имени.

## 23.6. Baseline и выбор архитектурного target

Важное практическое следствие Baseline заключается в том, что проекту необходимо заранее определить **целевой уровень совместимости**.

Для нового приложения можно, например, установить:

> Используем Baseline Widely available.

Для приложения с более современной аудиторией допустимо выбрать:

> Используем Baseline Newly available.

Для проекта с конкретным набором поддерживаемых браузеров можно определить собственную матрицу:

```
Chrome >= N
Edge >= N
Firefox >= N
Safari >= N
iOS Safari >= N
Android Chrome >= N
```

После этого уже проверяется, какие возможности JavaScript и Web Platform доступны в этой матрице.

**Baseline в Browserslist:** Baseline поддерживается инструментами экосистемы Browserslist. Для проекта можно выбрать, например:

- `baseline widely available` — только технологии, доступные во всех основных браузерах не менее 30 месяцев.
- `baseline newly available` — технологии, только что ставшие интероперабельными.
- Конкретный год Baseline, например `baseline 2026` — технологии, вошедшие в Baseline в указанном году.

Таким образом, политика совместимости может стать частью конфигурации проекта, а не оставаться устной договорённостью команды.

## 23.7. Baseline и современные Web API

Baseline особенно полезен там, где JavaScript взаимодействует с большим количеством API Web Platform.

В 2026 году разработчик может встретить одновременно технологии совершенно разной зрелости:

| Категория | Архитектурное решение |
| --------- | ---------------------- |
| Baseline Widely available | Можно рассматривать как стандартную основу проекта. |
| Baseline Newly available | Можно использовать после проверки целевой аудитории. |
| Limited availability | Нужны fallback, progressive enhancement или строгая целевая матрица. |
| Экспериментальная технология | Не следует делать её обязательной частью архитектуры без специального обоснования. |
| API конкретного браузера | Необходимо учитывать привязку к конкретной реализации (например, Chrome-only API). |
| Предложение стандарта | Нельзя считать его частью платформы до достижения соответствующей стадии стандартизации. |

Именно поэтому нельзя говорить о «современной Web Platform» как об однородном наборе технологий.

Например, в 2026 году:
- ES Modules, Fetch API, Web Workers имеют статус Widely available.
- Declarative Shadow DOM, View Transitions, Navigation API имеют статус Newly available (вошли в 2024-2025 годах).
- Scoped Custom Element Registries имеют статус Limited availability (поддерживаются в Chrome и Safari, но не в Firefox).
- File System Access API имеет статус Limited availability (только в Chromium-браузерах).
- Signals — предложение Stage 1, не является частью платформы.

В течение самого 2026 года Baseline продолжает обновляться: новые функции переходят в Newly available, а более старые — в Widely available.

## 23.8. Baseline и серверный JavaScript

Современная архитектура JavaScript всё чаще использует одни и те же Web Platform API на клиенте и сервере.

Это направление поддерживается инициативой **WinterTC**, чей организационный статус стоит указать точно. Изначально работа велась в открытой рабочей группе W3C — **WinterCG** (Web-interoperable Runtimes Community Group). В январе 2025 года участники WinterCG приняли решение перенести усилия по стандартизации в новый технический комитет Ecma International — **Ecma TC55** («Web-interoperable server runtimes»), неформально сохранивший имя **WinterTC**. После полного завершения этого перехода работа WinterCG была закрыта. Это изменение — переход от открытого сообщества к полноценному техническому комитету Ecma, обладающему полномочиями публиковать официальные стандарты, — принципиально: именно в этом новом статусе в декабре 2025 года был принят первый стандарт **Minimum Common Web API** (документ ECMA-429, 1-е издание) — набор API, которые Web-interoperable runtimes должны реализовывать для совместимости с веб-платформой.

Это создаёт основу для переноса между браузером и сервером таких концепций, как:

- `fetch` — выполнение HTTP-запросов.
- Web Streams — потоковая обработка данных.
- `URL` — парсинг и конструирование URL.
- Web Crypto — криптографические операции.
- `AbortController` / `AbortSignal` — отмена операций.

Но это не означает, что браузер и сервер обладают одинаковой средой.

Например, браузер имеет DOM, `window`, пользовательские события, Clipboard API и множество других интерфейсов, которых серверный runtime не обязан иметь. И наоборот, сервер имеет доступ к файловой системе, процессам и другим системным ресурсам, которых в браузере нет.

Поэтому правильная архитектурная формула выглядит так:

> **Общие Web API позволяют переиспользовать модели и код между средами, но не превращают браузер и сервер в один и тот же runtime.**

## 23.9. Baseline не заменяет тестирование

Baseline существенно уменьшает неопределённость, но не устраняет необходимость тестировать приложение.

Даже если API имеет статус Widely available, необходимо проверять:

- корректность работы приложения с этим API;
- производительность в реальных условиях;
- доступность для пользователей с ограничениями;
- особенности мобильных устройств (разные версии iOS Safari);
- WebView и встроенные браузеры (могут использовать более старые версии движков);
- взаимодействие нескольких API одновременно;
- ошибки конкретной реализации (баги в конкретном браузере);
- поведение при ограниченных ресурсах (слабое устройство, медленная сеть).

Кроме того, Baseline описывает поддержку **возможности платформы**, а не корректность конкретной библиотеки или приложения.

Поэтому production-процесс должен выглядеть примерно так:

```
Baseline
   ↓
целевой набор браузеров
   ↓
Feature Detection
   ↓
fallback / Progressive Enhancement
   ↓
автоматические тесты (unit, integration)
   ↓
тесты в реальных браузерах (BrowserStack, Sauce Labs)
   ↓
мониторинг production (ошибки, производительность)
```

Baseline отвечает на вопрос: «Насколько широко доступна эта возможность?»

Feature Detection отвечает: «Доступна ли она сейчас в этой среде?»

Тестирование отвечает: «Работает ли наше приложение с ней правильно?»

Это три разных вопроса, и ни один из них не заменяет остальные.

## 23.10. Baseline как часть инженерной политики проекта

Наиболее полезное изменение, которое Baseline приносит в современную разработку, связано не с конкретным API, а с процессом принятия решений.

Раньше совместимость часто определялась неформально:

> «Мы вроде бы поддерживаем современные браузеры».

В 2026 году эту формулировку можно заменить конкретной политикой:

```
Browser target:
Baseline Widely available

Enhancement target:
Baseline Newly available

Required APIs:
только Widely available

Optional APIs:
Newly available + feature detection

Experimental APIs:
не используются в основной архитектуре
```

Такой документ превращает совместимость из субъективного мнения разработчика в проверяемое техническое требование.

Для крупных проектов это особенно важно: изменение Browser Target становится архитектурным изменением, которое можно обсуждать, тестировать и фиксировать в конфигурации сборки.

## Заключение: Baseline как язык инженерных решений

В 2026 году Baseline не отменил различия между браузерами и не сделал Web Platform монолитной системой. Его значение в другом: **он сделал степень интероперабельности Web Platform понятной и формализованной.**

Современный JavaScript-разработчик должен мыслить не списком «поддерживаемых API», а несколькими уровнями зрелости:

1. **ECMAScript и Web Platform имеют разные стандарты и процессы развития.** ECMAScript определяет язык, Web Platform — браузерные API.
2. **Baseline показывает степень межбраузерной доступности конкретной Web Platform-возможности.**
3. **Newly available обозначает интероперабельность, а Widely available — более консервативный уровень зрелости после 30 месяцев.**
4. **Feature Detection проверяет фактическую доступность возможности в текущем runtime.**
5. **Progressive Enhancement позволяет использовать новые возможности без превращения их в обязательное условие для каждого пользователя.**
6. **Fallback остаётся необходимым там, где целевая аудитория или архитектура проекта этого требует.**
7. **Тестирование необходимо даже для Baseline Widely available API.**
8. **Baseline не заменяет знание спецификаций, документации и особенностей конкретного runtime.**

Поэтому профессиональный принцип Modern JavaScript 2026 можно сформулировать очень просто:

> **Не спрашивайте, является ли технология современной. Определите, насколько она интероперабельна, кому она нужна, что произойдёт при её отсутствии и соответствует ли её уровень зрелости целям конкретного проекта.**

Именно такой подход превращает Baseline из таблицы совместимости в полноценный инструмент архитектурного планирования.
