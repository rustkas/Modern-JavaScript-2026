# Часть VI. Современная архитектура

## Глава 20. Управление состоянием без state-management библиотек: нативные примитивы и архитектура данных

Современное JavaScript-приложение не обязано начинаться с Redux, MobX, Zustand или другого специализированного state-management решения. Для многих приложений достаточно правильно организовать обычные объекты JavaScript и использовать несколько стандартных возможностей Web Platform.

При этом важно разделять три разные задачи:

1. **хранение состояния** — где находятся данные приложения;
2. **уведомление об изменениях** — как другие части приложения узнают, что состояние изменилось;
3. **синхронизация состояния с интерфейсом и навигацией** — когда и каким образом обновляется DOM, URL и история браузера.

Web Platform предоставляет хорошие инструменты для второй и третьей задач, но не предлагает единого встроенного хранилища состояния приложения. `EventTarget`, `URL`, `URLSearchParams` и `Navigation API` решают разные архитектурные задачи и не являются заменой друг другу.

Особенно важно не путать существующие стандарты с будущими предложениями. В 2026 году TC39 Signals остаются предложением Stage 1. Их задача — стандартизировать общий фундамент гранулярной реактивности, прежде всего для взаимодействия разных фреймворков и библиотек. Signals пока не являются частью стандартного JavaScript и не предоставляют разработчику браузера универсальный встроенный state-management API.

## 20.1. Состояние приложения: обычный JavaScript без специального хранилища

Самый простой вариант управления состоянием не требует никакого специального API:

```javascript
const state = {
  user: null,
  filter: 'all',
  page: 1
};

state.filter = 'active';
state.page = 2;
```

Такой объект сам по себе ничего не знает о пользовательском интерфейсе. Изменение `state.filter` не вызывает автоматически перерисовку DOM и не уведомляет другие части приложения.

Это принципиальное свойство JavaScript:

> **обычный объект хранит данные, но не является реактивным объектом.**

Поэтому приложение должно самостоятельно определить механизм изменения состояния и уведомления потребителей.

Для небольшого приложения достаточно обычных функций:

```javascript
const state = {
  count: 0
};

function setCount(value) {
  state.count = value;
  render();
}

function render() {
  document.querySelector('#counter').textContent = state.count;
}

setCount(1);
```

Такая архитектура уже содержит важный принцип современного state management: **изменение состояния проходит через контролируемую точку**, а не выполняется произвольной записью из любого места приложения.

По мере роста приложения возникают дополнительные требования:

- несколько независимых потребителей одного состояния;
- производные значения;
- подписка и отписка;
- синхронизация разных компонентов;
- обмен данными между вкладками;
- сохранение состояния в URL;
- асинхронные операции;
- контроль жизненного цикла подписок.

Для этих задач можно использовать стандартные механизмы Web Platform.

## 20.2. `EventTarget`: стандартный механизм уведомления об изменениях

`EventTarget` предоставляет простой контракт для публикации событий и управления подписчиками. Это базовый интерфейс, от которого наследуются `Element`, `Document`, `Window` и многие другие объекты платформы.

Небольшое хранилище состояния можно построить без сторонней библиотеки:

```javascript
class Store extends EventTarget {
  #state = {
    count: 0
  };

  get state() {
    return this.#state;
  }

  setCount(value) {
    this.#state.count = value;

    this.dispatchEvent(
      new CustomEvent('statechange', {
        detail: this.#state
      })
    );
  }
}

const store = new Store();

store.addEventListener('statechange', event => {
  console.log('New state:', event.detail);
});

store.setCount(1);
```

Здесь `EventTarget` не хранит состояние и не делает объект реактивным. Он решает только одну задачу: **доставляет уведомление подписчикам**.

Это позволяет отделить модель данных от потребителей:

```
             ┌──────────────┐
             │    Store     │
             │   state      │
             └──────┬───────┘
                    │
              statechange
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
    Component A  Component B  Logger
```

Такой подход особенно полезен для модульных приложений, Web Components и микрофронтендов, где разные части системы должны обмениваться событиями, не зная внутреннего устройства друг друга.

### Custom Events не являются глобальной шиной данных

`CustomEvent` хорошо подходит для событий внутри одного JavaScript-контекста:

```javascript
element.dispatchEvent(
  new CustomEvent('cartchange', {
    detail: { items: 3 }
  })
);
```

Но `CustomEvent` не является универсальным механизмом коммуникации между вкладками, Web Workers и разными процессами браузера.

Для таких задач существуют другие API:

- `BroadcastChannel` — обмен сообщениями между контекстами одного origin;
- `postMessage()` — обмен сообщениями между окнами, iframe и workers;
- `SharedArrayBuffer` и `Atomics` — разделяемая память между совместимыми агентами;
- Service Worker — посредник между клиентами и сетевым слоем.

Следовательно, архитектура должна выбирать механизм коммуникации в зависимости от границы, через которую проходят данные.

## 20.3. Гранулярная реактивность: почему Signals важны, но ещё не являются стандартом

Гранулярная реактивность решает другую задачу. Вместо того чтобы после каждого изменения состояния заново запускать крупную функцию `render()`, система отслеживает зависимости отдельных вычислений и обновляет только те потребители, которым действительно нужны изменившиеся данные.

Например, состояние может иметь такую структуру:

```
count
 ├── isEven
 │    └── badge
 └── doubled
      └── counter
```

Если изменился `count`, реактивная система знает, какие производные значения зависят от него.

Именно такую модель пытается стандартизировать TC39 Signals.

Предложение TC39 Signals находится на **Stage 1**. Оно описывает `Signal.State` для изменяемого состояния и `Signal.Computed` для производных значений, а также механизмы автоматического отслеживания зависимостей. Однако предложенный API пока не является частью ECMAScript и может измениться.

Важная особенность предложения состоит в том, что оно ориентировано прежде всего на **общий фундамент для фреймворков**, а не на обязательную замену всех существующих state-management библиотек. Авторы прямо рассматривают Signals как основу, поверх которой фреймворки смогут строить собственные механизмы реактивности и планирования.

Поэтому в книге о Modern JavaScript 2026 Signals следует рассматривать как **важное направление развития языка**, но не как API, на котором можно строить сегодняшнее кросс-браузерное приложение без дополнительной реализации.

Практическая граница выглядит так:

| Технология                     | Статус в 2026                                  | Назначение                     |
| ------------------------------ | ---------------------------------------------- | ------------------------------ |
| обычные объекты                | стандарт                                       | хранение данных                |
| `EventTarget`                  | стандарт                                       | события и подписки             |
| `CustomEvent`                  | стандарт                                       | пользовательские события       |
| `URLSearchParams`              | стандарт                                       | состояние в URL                |
| `Navigation API`               | Baseline Newly available                       | управление навигацией          |
| Signals                        | TC39 Stage 1                                   | будущий фундамент реактивности |
| Signals конкретного фреймворка | production-ready в соответствующих экосистемах | гранулярная реактивность       |

Таким образом, термин **«нативная реактивность» в 2026 году использовать без оговорки нельзя**. Нативными являются отдельные строительные блоки, но единой стандартной реактивной модели JavaScript пока нет.

## 20.4. URL и `URLSearchParams`: состояние, которое можно передать ссылкой

Не всё состояние приложения должно находиться только в памяти JavaScript.

Для состояния, которое должно:

- переживать перезагрузку;
- попадать в историю браузера;
- копироваться пользователем;
- открываться на другом устройстве;
- индексироваться или передаваться другим пользователям,

естественным хранилищем становится URL.

Например:

```
/products?category=books&sort=price&page=3
```

В JavaScript это состояние удобно представлять через `URLSearchParams`:

```javascript
const params = new URLSearchParams(location.search);

const category = params.get('category');
const sort = params.get('sort');
const page = Number(params.get('page') ?? 1);
```

Изменение состояния можно синхронизировать с URL:

```javascript
const params = new URLSearchParams(location.search);

params.set('category', 'books');
params.set('page', '3');

history.pushState(
  null,
  '',
  `?${params}`
);
```

После этого URL становится частью публичного контракта приложения.

### Что следует хранить в URL

В URL хорошо подходят:

- фильтры;
- сортировка;
- номер страницы;
- выбранная вкладка;
- идентификатор открытого объекта;
- режим отображения;
- поисковый запрос.

В URL не следует помещать:

- пароли;
- токены доступа;
- персональные данные, которые не должны попадать в историю и логи;
- большие объёмы состояния;
- внутренние структуры объектов приложения.

URL — не универсальная база данных. Это **адресуемое и совместно используемое состояние навигации**.

## 20.5. `Navigation API`: современная синхронизация состояния и навигации

В 2026 году `Navigation API` стал Baseline Newly available. Он предназначен для управления навигацией приложений и решает ряд проблем старого `History API`. API предоставляет единый объект `navigation`, события навигации и методы для переходов, перемещения по истории и обновления состояния history entry.

Простейший пример перехвата навигации:

```javascript
navigation.addEventListener('navigate', event => {
  if (!event.canIntercept) {
    return;
  }

  event.intercept({
    async handler() {
      const url = new URL(event.destination.url);

      await renderRoute(url);
    }
  });
});
```

Программная навигация выглядит так:

```javascript
await navigation.navigate('/products').finished;
```

Состояние, связанное с конкретной записью истории, можно передать через `state`:

```javascript
navigation.navigate('/products', {
  state: {
    filter: 'books'
  }
});
```

Получить состояние текущей записи можно через `navigation.currentEntry`.

Это позволяет разделить два типа состояния:

```
URL
 └── состояние, которое должно быть адресуемым
     и доступным через ссылку

History Entry State
 └── состояние конкретного перехода,
     которое не обязательно кодировать в URL

In-Memory State
 └── внутреннее состояние текущего приложения
```

Такое разделение значительно лучше, чем попытка хранить всё в одном глобальном объекте.

### Navigation API не отменяет необходимость маршрутизации

`Navigation API` предоставляет платформенный механизм навигации, но не определяет структуру приложения.

Он не решает автоматически:

- какой компонент соответствует `/users`;
- как загружать данные страницы;
- как организовать layout;
- как управлять правами доступа;
- как выполнять server-side rendering;
- как кэшировать данные маршрута.

Эти задачи остаются ответственностью архитектуры приложения или используемого фреймворка.

## 20.6. Синхронизация состояния между вкладками и агентами

Состояние приложения может существовать одновременно в нескольких контекстах:

```
Tab A ──┐
        │
Tab B ──┼── same origin
        │
Worker ─┘
```

Для обмена событиями между вкладками и другими контекстами одного origin подходит `BroadcastChannel`:

```javascript
const channel = new BroadcastChannel('app');

channel.postMessage({
  type: 'theme-changed',
  theme: 'dark'
});

channel.addEventListener('message', event => {
  if (event.data.type === 'theme-changed') {
    applyTheme(event.data.theme);
  }
});
```

Это отличается от `EventTarget`:

- `EventTarget` связывает объекты внутри одного контекста;
- `BroadcastChannel` передаёт сообщения между несколькими контекстами одного origin.

Для сложных приложений это позволяет строить state synchronization без специальной глобальной библиотеки.

Однако передавать через такие каналы следует **события и минимальные данные**, а не большие графы состояния. Это уменьшает связанность и стоимость межконтекстного обмена.

## 20.7. Архитектура состояния: разделяйте источники истины

Главная архитектурная проблема state management заключается не в выборе библиотеки, а в определении того, **где находится источник истины для каждого типа данных**.

Практическая модель может выглядеть так:

```
                    APPLICATION STATE
                           │
       ┌───────────────────┼───────────────────┐
       ▼                   ▼                   ▼
   URL state          Server state         Local state
       │                   │                   │
 filters/page        fetched resources      UI state
       │                   │                   │
       └──────────────┬────┴───────────────────┘
                      ▼
                 View / DOM
```

### URL state

Используется для состояния, которое должно иметь собственный адрес:

```
/search?q=javascript&page=2
```

### Server state

Представляет данные, полученные с сервера:

```javascript
const response = await fetch('/api/products');
const products = await response.json();
```

Такое состояние нельзя смешивать с локальным UI-state. Данные сервера имеют собственный жизненный цикл: загрузку, обновление, ошибки, кэширование и устаревание.

### Local UI state

Содержит временное состояние интерфейса:

```javascript
{
  menuOpen: false,
  selectedTab: 'details',
  dialogOpen: true
}
```

Такое состояние обычно не имеет смысла в URL и не должно превращаться в глобальный серверный store.

### Derived state

Производные значения не следует дублировать без необходимости:

```javascript
const total = items.reduce(
  (sum, item) => sum + item.price,
  0
);
```

Если `total` полностью определяется `items`, то хранение одновременно `items` и `total` создаёт два источника истины. При изменении `items` их можно случайно рассинхронизировать.

Хорошее правило:

> **Храните минимальное состояние, а производные значения вычисляйте из него.**

## 20.8. Когда нативных механизмов достаточно

Нативный подход хорошо подходит для приложений, в которых:

- состояние относительно небольшое;
- число потребителей ограничено;
- бизнес-логика не образует сложный граф зависимостей;
- нет необходимости в сложном middleware;
- не требуется развитая система DevTools для состояния;
- приложение состоит из Web Components или независимых модулей;
- состояние естественным образом разделяется между URL, серверными данными и локальным UI-state.

Простейшая архитектура может состоять всего из:

```
State object
     │
     ▼
EventTarget
     │
     ├── UI
     ├── URL synchronization
     └── other modules
```

В таком случае использование большой state-management библиотеки может добавить больше абстракций, чем решить проблем.

## 20.9. Когда библиотека управления состоянием действительно оправдана

Нативные API не являются принципиальной заменой специализированным библиотекам.

Библиотека становится оправданной, когда приложение требует системных возможностей, которых стандартные API напрямую не предоставляют:

- сложного графа производных состояний;
- автоматической гранулярной реактивности;
- транзакций и batching;
- middleware;
- undo/redo;
- time-travel debugging;
- развитой интеграции с DevTools;
- сложной нормализации данных;
- кэширования серверного состояния;
- централизованного контроля большого количества независимых модулей.

В таком случае правильный вопрос звучит не как:

> «Можно ли обойтись без библиотеки?»

а как:

> **«Какие архитектурные возможности библиотека предоставляет сверх Web Platform и действительно ли они нужны приложению?»**

Это важное изменение инженерного мышления. Нативный JavaScript следует использовать там, где его возможностей достаточно, а библиотеку — там, где она решает конкретную архитектурную проблему.

## 20.10. Что действительно означает «Modern JavaScript 2026»

Современный state management не сводится к появлению одного нового API.

Архитектура 2026 года строится на разделении ответственности:

- **обычные объекты JavaScript** хранят состояние;
- **`EventTarget` и `CustomEvent`** передают уведомления внутри контекста;
- **`BroadcastChannel` и `postMessage()`** обеспечивают межконтекстную коммуникацию;
- **`URL` и `URLSearchParams`** хранят адресуемое состояние;
- **`Navigation API`** связывает состояние приложения с современным жизненным циклом навигации;
- **Signals** показывают направление будущей стандартизации гранулярной реактивности, но ещё не являются стандартной частью JavaScript;
- **фреймворки и библиотеки** добавляют реактивность, планирование, кэширование и инструменты разработки там, где нативных примитивов недостаточно.

Главный принцип можно сформулировать так:

> **Не начинайте архитектуру состояния с выбора библиотеки. Сначала определите источники истины, границы состояния и способы его изменения. Затем используйте минимальный набор платформенных и библиотечных механизмов, необходимый для реализации этой модели.**

Именно такой подход соответствует Modern JavaScript 2026: не отказ от библиотек, а осознанное использование платформы вместо абстракций, которые приложение не использует.

### Итоговая архитектурная модель

```
                    ┌───────────────────┐
                    │   URL / History   │
                    │ addressable state │
                    └─────────┬─────────┘
                              │
                              ▼
┌──────────────┐       ┌───────────────┐       ┌───────────────┐
│ Server State │──────▶│ Application   │◀──────│ Local UI State│
│              │       │    State      │       │               │
└──────────────┘       └───────┬───────┘       └───────────────┘
                               │
                       ┌───────┴────────┐
                       ▼                ▼
                 EventTarget      Reactive layer
                       │          (framework/
                       │           library)
                       ▼                │
                 Other modules         ▼
                                  DOM / View

Cross-context synchronization:
BroadcastChannel / postMessage()
```

Эта модель не требует обязательного глобального store. Она требует только ясного ответа на четыре вопроса:

1. **Где хранится конкретное состояние?**
2. **Кто является его источником истины?**
3. **Как сообщается об изменении?**
4. **Как состояние синхронизируется с URL, сервером и интерфейсом?**

Если на эти вопросы есть однозначные ответы, приложение может оставаться простым даже без специализированной state-management библиотеки.

---

### Заключение

В 2026 году JavaScript ещё не получил единой встроенной системы управления состоянием и нативной реактивности. `EventTarget`, `URL`, `URLSearchParams`, `BroadcastChannel` и `Navigation API` являются зрелыми платформенными примитивами, но каждый решает конкретную задачу.

Signals представляют важное направление развития ECMAScript, однако предложение остаётся на Stage 1. Оно нацелено прежде всего на стандартизацию общего фундамента реактивности, который смогут использовать разные фреймворки и библиотеки. Называть Signals частью современного стандартного JavaScript пока преждевременно.

Поэтому современный подход к state management заключается не в полном отказе от библиотек. Он заключается в **разделении состояния по природе и жизненному циклу**:

- адресуемое состояние — в URL;
- данные сервера — в слое работы с серверными ресурсами;
- временное состояние интерфейса — локально;
- производные данные — вычисляются;
- события — передаются через стандартные механизмы;
- сложная реактивность и централизованное управление — добавляются только тогда, когда приложение действительно требует их возможностей.

Такой подход делает архитектуру меньше, понятнее и устойчивее к изменениям экосистемы, одновременно оставляя возможность перейти на стандартизированную реактивную модель, если Signals или другой механизм достигнет зрелой стадии ECMAScript в будущем.
