# Часть III. Работа с браузером

# Глава 10. Custom Elements: нативные веб-компоненты и архитектура интерфейсов

Современная Web Platform позволяет создавать собственные HTML-элементы, которые работают наравне со встроенными элементами браузера. Такие элементы называются **Custom Elements** и являются частью стандарта **Web Components**.

В отличие от компонентов, реализованных средствами отдельных фреймворков, пользовательские элементы работают непосредственно на уровне браузера. Они поддерживаются всеми современными движками, могут использоваться в любом приложении и не требуют собственного рантайма.

Custom Elements позволяют объединить структуру, поведение и внутреннее состояние компонента в единую инкапсулированную сущность, сохраняя при этом обычную модель работы HTML, CSS и JavaScript.

---

## 10.1. Web Components как основа современной архитектуры

Стандарт Web Components объединяет четыре взаимосвязанные технологии:

- **Custom Elements** — определение собственных HTML-элементов. Это основная технология, позволяющая создавать новые HTML-теги с собственным поведением.
- **Shadow DOM** — инкапсуляция структуры и стилей. Создаёт изолированное DOM-дерево, стили из которого не проникают наружу, а стили снаружи не влияют на компонент.
- **HTML Templates** — повторно используемые шаблоны интерфейса через элементы `<template>` и `<slot>`. Позволяют определять структуру компонента без немедленного добавления в DOM.
- **ES Modules** — модульная организация компонентов. Каждый компонент может быть импортирован как отдельный модуль, что упрощает управление зависимостями и позволяет использовать tree shaking.

Вместе они позволяют создавать независимые интерфейсные модули, которые одинаково работают:

- без использования фреймворков — напрямую в браузере;
- внутри React, Angular, Vue, Svelte и других библиотек через специальные обёртки или прямую интеграцию;
- в архитектурах микрофронтендов — каждый микрофронтенд может использовать собственные Web Components;
- в дизайн-системах — компоненты публикуются как независимые пакеты, работающие в любом проекте;
- в корпоративных библиотеках компонентов — единый набор компонентов используется во всех приложениях компании.

Именно поэтому Web Components стали стандартным способом публикации переиспользуемых UI-компонентов. Крупные компании (Google, Salesforce, Adobe, SAP) используют их для своих дизайн-систем.

## 10.2. Регистрация пользовательских элементов

Каждый пользовательский элемент представляет собой класс, наследующий `HTMLElement` (или его подкласс для расширения существующих элементов).

После объявления класс необходимо зарегистрировать в глобальном реестре компонентов с помощью метода `customElements.define()`.

```javascript
class UserCard extends HTMLElement {
  constructor() {
    super();
    // Инициализация компонента
  }
}

customElements.define('user-card', UserCard);
```

Регистрация выполняется через объект `customElements`, реализующий интерфейс `CustomElementRegistry`. Этот объект является глобальным и доступен во всех современных браузерах.

После регистрации браузер автоматически создаёт экземпляры класса при встрече соответствующего HTML-тега в документе.

```html
<user-card></user-card>
```

**Правила именования:**

- Имя пользовательского элемента обязательно должно содержать дефис (`-`). Например: `user-card`, `app-button`, `my-dialog`.
- Имя должно быть уникальным для каждого класса.
- Имя не может содержать заглавные буквы.
- Имя не может начинаться с чисел.

Такое ограничение гарантирует, что пользовательские элементы никогда не будут конфликтовать с существующими или будущими стандартными тегами HTML. Браузеры могут добавлять новые элементы (например, `<dialog>`), и пользовательское имя с дефисом никогда не совпадёт с ними.

**Проверка регистрации:**

```javascript
if (!customElements.get('user-card')) {
  customElements.define('user-card', UserCard);
}
```

**Ожидание определения элемента:**

```javascript
await customElements.whenDefined('user-card');
// Элемент зарегистрирован, можно создавать экземпляры
```

## 10.3. Автономные и встроенные пользовательские элементы

Стандарт определяет два типа компонентов.

### Autonomous Custom Elements (автономные элементы)

Создают полностью новый HTML-элемент, не связанный ни с одним существующим тегом.

```html
<user-card></user-card>
<app-header></app-header>
<my-button></my-button>
```

Это наиболее распространённый вариант, используемый практически всеми современными библиотеками компонентов. Автономные элементы наследуют от `HTMLElement` и могут иметь любую внутреннюю структуру. Технология входит в Baseline Widely Available и полностью кросс-браузерна.

### Customized Built-in Elements (встроенные элементы)

Позволяют расширять существующий HTML-элемент, сохраняя его поведение и добавляя собственную функциональность.

```html
<button is="confirm-button">Подтвердить</button>
```

Для создания такого компонента класс наследуется от `HTMLButtonElement`, а при регистрации указывается третий аргумент `{ extends: 'button' }`:

```javascript
class ConfirmButton extends HTMLButtonElement {
  constructor() {
    super();
    // Дополнительная логика
  }
}
customElements.define('confirm-button', ConfirmButton, { extends: 'button' });
```

Встроенные элементы сохраняют все свойства и методы базового элемента (например, `type`, `disabled`, `click()`), но добавляют собственную логику.

**Важная оговорка, которую стоит знать перед выбором этого подхода:** ограничение поддержки здесь — не вопрос качества интеграции с отдельными фреймворками, а принципиальная позиция WebKit. Команда Safari официально отказалась реализовывать `is=`-атрибут и связанный с ним механизм, назвав его потенциально вредным для долгосрочного здоровья веб-платформы, и на момент написания книги эта позиция не изменилась. Это значит, что встроенные элементы **не работают в Safari ни в каком виде** — не за флагом, не частично, а полностью отсутствуют, и единственный способ поддержать эту аудиторию — подключать полифил (например, `@ungap/custom-elements-builtin`).

**Практическое замечание:** именно поэтому на практике автономные элементы используются значительно чаще — они не просто проще интегрируются с инструментами, а являются единственным вариантом, работающим во всех современных браузерах без полифилов. Встроенные элементы стоит рассматривать только для проектов, не ориентированных на аудиторию Safari, либо при готовности постоянно поддерживать полифил.

## 10.7. Declarative Shadow DOM

Современная платформа поддерживает создание Shadow DOM непосредственно в HTML через Declarative Shadow DOM.

```html
<user-card>
  <template shadowrootmode="open">
    <style>
      :host { display: block; border: 1px solid #ccc; }
      .content { padding: 10px; }
    </style>
    <div class="content">
      <slot name="header">Заголовок</slot>
      <slot>Содержимое</slot>
    </div>
  </template>
</user-card>
```

При разборе документа браузер автоматически создаёт теневой DOM из содержимого шаблона, ещё до выполнения JavaScript. В отличие от Customized Built-in Elements из предыдущего раздела, эта технология полностью кросс-браузерна: она реализована во всех трёх основных движках (последним подключился Safari, начиная с версии 16.4) и достигла статуса **Baseline Newly Available** в августе 2024 года.

**Важные особенности:**

- Атрибут `shadowrootmode="open"` указывает браузеру создать Shadow DOM с открытым режимом.
- Содержимое шаблона становится Shadow DOM элемента.
- Обычный DOM-контент внутри элемента (после шаблона) распределяется по слотам.
- После создания Shadow DOM, шаблон удаляется из документа и не отображается.

**Преимущества Declarative Shadow DOM:**

- **Server Side Rendering (SSR)** — компонент рендерится на сервере с полной структурой Shadow DOM.
- **Статические сайты** — компоненты полностью работоспособны сразу после загрузки HTML, без выполнения JavaScript.
- **Микрофронтенды** — каждый микрофронтенд может включать свои компоненты с Shadow DOM, не конфликтуя с другими.
- **Потоковый рендеринг** — компоненты могут отображаться по мере поступления HTML, без ожидания загрузки JavaScript.
- **Ускорение первого отображения** — пользователь видит полностью стилизованный компонент до загрузки и выполнения скриптов.

Код для создания такого компонента может быть упрощён до пустого класса:

```javascript
class UserCard extends HTMLElement {}
customElements.define('user-card', UserCard);
```

Вся функциональность определяется в HTML-шаблоне, а JavaScript нужен только для регистрации элемента.

## 10.8. Интеграция с HTML-формами

Стандарт позволяет пользовательским элементам участвовать в работе обычных HTML-форм через интерфейс `ElementInternals`.

Для этого компонент должен:

1. Объявить статическое свойство `formAssociated = true`.
2. В конструкторе вызвать `this.attachInternals()` для получения объекта `ElementInternals`.

```javascript
class CustomInput extends HTMLElement {
  static formAssociated = true;
  
  #internals;
  
  constructor() {
    super();
    this.#internals = this.attachInternals();
  }
}
customElements.define('custom-input', CustomInput);
```

Важно: в отличие от Customized Built-in Elements, `ElementInternals` и связанный с ним механизм Form-Associated Custom Elements **полностью поддерживаются во всех основных браузерах**, включая Safari (начиная с версии 16.4) — статус Baseline Widely Available. Это принципиально разные технологии: обе решают задачу расширения возможностей элементов, но `is=`-атрибут расширяет *существующий* HTML-тег, а `ElementInternals` даёт *автономному* элементу возможности, свойственные встроенным элементам форм, — и именно поэтому второй подход развивается активнее и не имеет проблем с поддержкой.

После этого компонент получает возможность полноценно взаимодействовать с формами:

- **Участвовать в отправке формы** — значение компонента включается в `FormData` при отправке.
- **Поддерживать автозаполнение** — браузер может автоматически заполнять компонент.
- **Реагировать на сброс формы** — при вызове `form.reset()` компонент может сбросить своё состояние.
- **Использовать встроенную валидацию браузера** — форма проверяет компонент наравне с обычными элементами.
- **Устанавливать собственные сообщения об ошибках** через `setValidity()`.

**Основные методы ElementInternals:**

- `setValue(value)` — устанавливает значение компонента для формы.
- `setValidity(flags, message, anchor)` — устанавливает состояние валидации.
- `checkValidity()` — проверяет валидность компонента.
- `reportValidity()` — проверяет и показывает сообщение об ошибке.

```javascript
#updateValue(value) {
  this.#internals.setValue(value);
}

#validate() {
  if (this.#value.length < 3) {
    this.#internals.setValidity({
      tooShort: true,
      customError: true
    }, 'Минимальная длина 3 символа', this);
    return false;
  }
  this.#internals.setValidity({});
  return true;
}
```

С точки зрения браузера такой компонент становится полноценным элементом управления наравне с `<input>` или `<select>`. Он участвует в валидации, отправке форм и поддержке доступности.

## 10.9. События и взаимодействие компонентов

Компоненты взаимодействуют с внешним приложением через стандартную модель событий DOM. Для передачи информации наружу используется `CustomEvent`.

```javascript
this.dispatchEvent(new CustomEvent('user-selected', {
  detail: { id: 42, name: 'Alice' },
  bubbles: true,
  composed: true
}));
```

**Параметры CustomEvent:**

- `detail` — содержит пользовательские данные любого типа (объект, массив, примитив).
- `bubbles: true` — событие всплывает по дереву DOM, позволяя родительским элементам обрабатывать его.
- `composed: true` — событие покидает Shadow DOM и становится доступным внешнему приложению.

**Обработка событий снаружи:**

```html
<user-card id="card"></user-card>

<script>
document.getElementById('card').addEventListener('user-selected', (event) => {
  const { id, name } = event.detail;
  console.log(`Выбран пользователь ${name} (${id})`);
});
</script>
```

**Внутренняя обработка событий (внутри компонента):**

```javascript
connectedCallback() {
  const signal = this.#controller.signal;
  this.shadowRoot.querySelector('button').addEventListener('click', (event) => {
    this.dispatchEvent(new CustomEvent('user-selected', {
      detail: { id: this.#userId },
      bubbles: true,
      composed: true
    }));
  }, { signal });
}
```

Использование событий позволяет компонентам взаимодействовать друг с другом без прямых зависимостей и делает архитектуру более модульной. Родительский компонент не должен знать о внутренней структуре дочернего — он просто подписывается на его события.

## 10.10. Лучшие практики

Современная разработка рекомендует придерживаться нескольких правил при создании Custom Elements:

1. **Использовать ES Modules для публикации компонентов.** Каждый компонент должен быть отдельным модулем с явным импортом и экспортом.

```javascript
// user-card.js
export class UserCard extends HTMLElement { /* ... */ }
customElements.define('user-card', UserCard);
```

2. **По возможности применять Shadow DOM.** Это обеспечивает изоляцию стилей и структуры, предотвращая конфликты.

3. **Выполнять основную инициализацию в `connectedCallback()`.** Конструктор должен быть минимальным, только для создания Shadow DOM и внутренних полей.

4. **Освобождать все ресурсы в `disconnectedCallback()`.** Использовать `AbortController` для автоматического удаления обработчиков и отмены операций.

5. **Передавать информацию наружу через `CustomEvent`.** Использовать `bubbles: true` и `composed: true` для событий, которые должны быть доступны за пределами Shadow DOM.

6. **Использовать `ElementInternals` для компонентов форм.** Это позволяет компонентам участвовать в валидации и отправке форм наравне со встроенными элементами.

7. **Делать компоненты независимыми от конкретного фреймворка.** Не использовать в компонентах специфичные для фреймворков API. Компонент должен работать в любом окружении.

8. **Использовать Declarative Shadow DOM для SSR и статических сайтов.** Это улучшает производительность и SEO.

9. **Документировать публичное API компонента** — атрибуты, свойства, события и методы.

10. **Тестировать компоненты изолированно.** Использовать тестовые фреймворки для проверки жизненного цикла, атрибутов и событий.

Такие компоненты можно использовать практически в любом современном проекте без дополнительной адаптации, что делает их универсальным решением для переиспользуемых UI-элементов.

## Заключение главы

Custom Elements превратились в один из ключевых механизмов Web Platform для создания независимых пользовательских интерфейсов. Вместе с Shadow DOM, ES Modules, HTML Templates и ElementInternals они образуют законченную архитектуру веб-компонентов, позволяющую создавать инкапсулированные, переиспользуемые и масштабируемые элементы интерфейса.

Автономные элементы создают новые HTML-теги, независимые от существующих, в то время как встроенные элементы расширяют поведение существующих элементов. Жизненный цикл компонента полностью управляется браузером через конструктор, `connectedCallback()`, `disconnectedCallback()` и `adoptedCallback()`. Атрибуты обеспечивают реактивность через `observedAttributes` и `attributeChangedCallback()`. Shadow DOM предоставляет изоляцию стилей и структуры, а Declarative Shadow DOM позволяет рендерить компоненты на сервере без выполнения JavaScript. `ElementInternals` интегрирует компоненты с HTML-формами. События через `CustomEvent` обеспечивают взаимодействие между компонентами без прямых зависимостей.

В экосистеме JavaScript 2026 года веб-компоненты перестали быть альтернативой отдельным фреймворкам. Они стали фундаментальным уровнем платформы, на котором могут строиться как самостоятельные приложения, так и современные библиотеки компонентов, дизайн-системы и микрофронтенд-архитектуры.
