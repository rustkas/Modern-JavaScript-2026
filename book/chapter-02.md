# Глава 2. Архитектура современного JavaScript: как работает рантайм

После знакомства с историей языка пришло время разобраться, что происходит после запуска программы. Современный JavaScript — это не просто интерпретатор, а сложная система, объединяющая движок ECMAScript, рантайм-среду, сборщик мусора, механизм модулей, событийный цикл и интерфейсы Web Platform.

Понимание этой архитектуры позволяет объяснить поведение языка без заучивания исключений. Именно поэтому большинство сложных тем — от асинхронности до производительности — начинается не с синтаксиса, а с устройства рантайма.

## 2.1. Движок JavaScript и рантайм: кто за что отвечает

Первое распространённое заблуждение состоит в том, что JavaScript "умеет всё сам". На самом деле язык определяет только спецификация ECMAScript.

За выполнение программы отвечают две разные системы.

**JavaScript Engine (движок)** — это программа, которая читает и выполняет JavaScript-код. Движок отвечает за:

- **Разбор исходного кода (Parsing)** — преобразование текста программы в абстрактное синтаксическое дерево (AST).
- **Построение AST** — структурированное представление кода, с которым дальше работают компилятор и интерпретатор.
- **Компиляцию** — преобразование AST в машинный код или байт-код. Современные движки используют JIT-компиляцию (Just-In-Time), которая компилирует код во время выполнения.
- **Оптимизацию** — анализ и оптимизация горячего кода (часто выполняемых участков) для повышения производительности.
- **Выполнение инструкций** — непосредственное выполнение скомпилированного кода.
- **Управление памятью** — выделение и освобождение памяти, сборка мусора.

Типичные представители движков:

- **V8** — движок от Google, используется в Chrome, Node.js, Deno, Bun и Electron.
- **JavaScriptCore (JSC)** — движок от Apple, используется в Safari и WebKit.
- **SpiderMonkey** — движок от Mozilla, используется в Firefox.

---

**Runtime Environment (среда выполнения)** — это всё, что окружает движок и предоставляет возможности, не определённые в ECMAScript:

- **DOM (Document Object Model)** — API для работы с HTML-документом (доступен только в браузере).
- **Fetch API** — выполнение сетевых запросов.
- **Timers** — `setTimeout`, `setInterval`, `setImmediate` (в Node.js).
- **Streams** — работа с потоками данных.
- **WebSocket** — двунаправленная связь с сервером.
- **File System** — работа с файловой системой (доступно в Node.js, Deno, Bun).
- **Process API** — управление процессами (доступно в Node.js, Deno, Bun).
- **Worker Threads** — многопоточность (доступно в браузере и Node.js).

Один и тот же JavaScript-код может выполняться в разных средах, получая доступ к разным API:

- **Браузер** — DOM, Fetch, WebSocket, Canvas, WebGL, WebGPU.
- **Node.js** — File System, Process, HTTP, Crypto, Worker Threads.
- **Deno** — File System, Fetch (по умолчанию), Worker, Web Crypto.
- **Bun** — File System, HTTP, WebSocket, Worker.
- **Cloudflare Workers** — Fetch, KV Storage, Durable Objects, Email.

Например, код `fetch('https://api.example.com/data')` будет работать везде, где доступен Fetch API, но код `fs.readFileSync('./data.txt')` будет работать только в Node.js, Deno и Bun, поскольку в браузере нет прямого доступа к файловой системе.

## 2.2. Execution Context и области видимости

Любой исполняемый код работает внутри Execution Context (контекста выполнения). Execution Context — это среда, в которой выполняется JavaScript-код. Она определяет:

- **Текущую область видимости** — набор переменных и функций, доступных в текущем контексте.
- **Значение `this`** — объект, на который ссылается ключевое слово `this`.
- **Доступные переменные** — переменные, объявленные в текущей области видимости и во внешних областях.
- **Ссылки на внешние области видимости** — связь с родительскими контекстами для поиска переменных.

**Типы Execution Context:**

1. **Global Execution Context** — создаётся при запуске скрипта. Это корневой контекст, в котором выполняется код верхнего уровня.
2. **Function Execution Context** — создаётся при каждом вызове функции. Каждая функция получает свой контекст.
3. **Eval Execution Context** — создаётся при выполнении кода внутри `eval()`.

**Call Stack (стек вызовов)** — структура данных, которая хранит информацию о текущих выполняемых функциях. Во время работы программы формируется стек вызовов:

- Каждый вызов функции создаёт новый Execution Context и помещает его на вершину стека.
- Когда функция завершается, её контекст удаляется из стека.
- Если стек переполняется (например, при бесконечной рекурсии), возникает ошибка `RangeError: Maximum call stack size exceeded`.

```javascript
function a() { b(); }
function b() { c(); }
function c() { console.log('Done'); }
a();
// Call Stack: [global] → [a] → [b] → [c] → [global]
```

---

### Лексическое окружение (Lexical Environment)

Каждый Execution Context содержит Lexical Environment — структуру, которая хранит привязки между именами переменных и их значениями.

Lexical Environment состоит из:

1. **Environment Record** — объект, хранящий фактические привязки (переменные, функции).
2. **Ссылки на внешнее окружение** — ссылка на родительское Lexical Environment для поиска переменных во внешних областях.

**Как работает Lexical Environment:**

- При объявлении переменной с `let` или `const` она добавляется в Environment Record текущего контекста.
- При обращении к переменной движок сначала ищет её в текущем Environment Record, затем во внешнем, затем во внешнем внешнем, и так до глобального контекста.
- Если переменная не найдена нигде, возникает `ReferenceError`.

Lexical Environment обеспечивает работу:

- `let` и `const` — блочная область видимости, переменные существуют только внутри блока `{}`.
- `class` — классы и их методы имеют свою область видимости.
- Функций — каждая функция имеет доступ к переменным из внешней области.
- Замыканий — функция сохраняет ссылку на своё Lexical Environment даже после завершения внешней функции.

**Пример замыкания:**

```javascript
function createCounter() {
  let count = 0; // count находится в Lexical Environment функции createCounter
  return function() {
    count++; // Внутренняя функция сохраняет ссылку на Lexical Environment
    return count;
  };
}
const counter = createCounter();
console.log(counter()); // 1
console.log(counter()); // 2
// Переменная count продолжает существовать благодаря замыканию
```

Замыкания перестают выглядеть "магией", если понимать, что функция хранит ссылку на своё лексическое окружение даже после завершения внешней функции. Внутренняя функция, возвращённая из `createCounter`, имеет ссылку на Lexical Environment внешней функции, где хранится переменная `count`.

## 2.3. Модули как единицы выполнения

К 2026 году ES Modules (ESM) стали универсальным способом организации приложений. Модули загружаются и выполняются как независимые единицы, каждая из которых имеет свою область видимости.

Современный загрузчик модулей проходит несколько стадий:

1. **Resolution (разрешение)** — определение полного пути к модулю на основе спецификатора импорта (относительный путь, имя пакета, URL). В браузере спецификаторы разрешаются как URL, в Node.js — через `node_modules` и `package.json`.

2. **Loading (загрузка)** — получение исходного текста модуля. В браузере это HTTP-запрос, в Node.js — чтение файла.

3. **Parsing (парсинг)** — преобразование исходного текста в AST и извлечение инструкций `import` и `export`.

4. **Linking (связывание)** — построение графа зависимостей. Создаются Module Environment Records, проверяется существование экспортов, корректность импортов и циклические зависимости. На этом этапе обнаруживается большинство ошибок.

5. **Evaluation (выполнение)** — исполнение кода модуля. Модули выполняются строго в порядке зависимостей (от самых глубоких к корневым).

Такое разделение позволяет:

- **Обнаруживать циклические зависимости** — если модуль A импортирует модуль B, а модуль B импортирует модуль A, загрузчик может определить цикл и корректно обработать его на этапе Linking.
- **Выполнять tree shaking** — удаление неиспользуемых экспортов на основе статического анализа графа зависимостей.
- **Использовать статический анализ** — все импорты и экспорты известны до выполнения, что позволяет оптимизировать загрузку и компиляцию.
- **Поддерживать Top-Level Await** — использование `await` на верхнем уровне модуля, что приостанавливает выполнение зависимых модулей до завершения асинхронной операции.

**Module Graph (граф модулей)** — структура, показывающая все зависимости между модулями в приложении. Граф строится на этапе Linking и используется для оптимизации загрузки и выполнения.

**Live Bindings (живые привязки)** — механизм, при котором импортируемое значение является ссылкой на экспортируемую переменную, а не её копией. Изменение экспортируемого значения автоматически отражается во всех импортерах.

```javascript
// counter.js
export let count = 0;
export function increment() { count++; }

// app.js
import { count, increment } from './counter.js';
console.log(count); // 0
increment();
console.log(count); // 1 — значение обновлено благодаря Live Bindings
```

**Динамический `import()`** — функция, позволяющая загружать модули асинхронно во время выполнения. Возвращает Promise, который разрешается с объектом модуля.

```javascript
const module = await import('./dynamic-module.js');
module.default(); // Вызов экспорта по умолчанию
```

Динамический импорт используется для ленивой загрузки, разделения кода (code splitting) и условной загрузки модулей.

## 2.4. Event Loop и асинхронная модель

Асинхронность JavaScript строится вокруг Event Loop — бесконечного цикла, который управляет выполнением задач.

В современной среде существует несколько уровней очередей:

**Task Queue (очередь задач, макрозадач)** — очередь, в которую попадают задачи, готовые к выполнению: колбэки `setTimeout`, `setInterval`, события DOM, сетевые запросы. Event Loop забирает задачи из этой очереди по одной, когда Call Stack пуст.

**Microtask Queue (очередь микрозадач)** — очередь с более высоким приоритетом. Сюда попадают: колбэки `Promise.then`, `Promise.catch`, `Promise.finally`, `queueMicrotask()`, `MutationObserver`. После завершения каждой макрозадачи движок полностью очищает очередь Microtasks, прежде чем перейти к следующей макрозадаче.

**Animation Frame Queue** — очередь для `requestAnimationFrame`, которая выполняется перед рендерингом. Используется для анимаций и обновлений интерфейса.

**Rendering Pipeline** — процесс рендеринга, который выполняется между макрозадачами, после обработки всех микрозадач. Браузер стремится выполнять рендеринг с частотой 60 Гц (каждые 16.7 мс).

**Порядок выполнения:**

1. Выполняется весь синхронный код — Call Stack полностью очищается.
2. Обрабатывается вся очередь Microtasks — все `Promise.then`, `queueMicrotask` выполняются до конца.
3. (В браузере) Выполняется рендеринг — обновление интерфейса, если необходимо.
4. Берётся следующая задача из Task Queue — одна макрозадача.
5. Возврат к шагу 2.

```javascript
console.log('1. Синхронный код');
setTimeout(() => console.log('4. Макрозадача'), 0);
Promise.resolve().then(() => console.log('3. Микрозадача'));
queueMicrotask(() => console.log('2. Микрозадача'));
// Вывод: 1, 2, 3, 4
```

**Особенности Event Loop в разных средах:**

- **Браузер** — рендеринг между макрозадачами, обработка событий DOM, анимации через `requestAnimationFrame`.
- **Node.js** — дополнительные фазы: таймеры, ожидание I/O, опрос, проверка, закрытие. Используется `libuv` для управления асинхронными операциями.
- **Deno и Bun** — используют аналогичную Node.js модель, но с некоторыми оптимизациями и отличиями в реализации.

## 2.5. Память и производительность

Работа JavaScript напрямую зависит от эффективности управления памятью.

**Heap (куча)** — область памяти, где хранятся все объекты, массивы, функции и другие структуры данных. В отличие от стека, куча не имеет строгого порядка и может содержать данные с разным временем жизни.

**Stack (стек)** — область памяти для хранения примитивных значений и ссылок на объекты. Стек организован как LIFO (Last In, First Out) и используется для управления Call Stack.

**Reachability (достижимость)** — концепция, используемая сборщиком мусора для определения, какие объекты всё ещё используются программой. Объект считается достижимым, если до него можно добраться из глобального объекта или текущего стека вызовов через цепочку ссылок. Недостижимые объекты удаляются сборщиком мусора.

**Garbage Collection (сборка мусора)** — автоматическое освобождение памяти, занятой недостижимыми объектами. Сборщик мусора периодически сканирует память, находит недостижимые объекты и освобождает занимаемую ими память.

**Generational GC (поколенческая сборка мусора)** — стратегия, используемая в современных движках (V8, JavaScriptCore). Объекты делятся на поколения:

- **Young Generation** — новые объекты. Сборка происходит часто и быстро (Minor GC).
- **Old Generation** — объекты, пережившие несколько сборок. Сборка происходит реже и занимает больше времени (Major GC).

Эта стратегия основана на наблюдении, что большинство объектов умирают молодыми, поэтому их можно собирать быстро и часто, а старые объекты собирать реже.

**WeakRef** — слабые ссылки на объекты, которые не препятствуют сборке мусора. Используются для кеширования, когда объекты могут быть удалены при нехватке памяти.

```javascript
const ref = new WeakRef(someObject);
const obj = ref.deref(); // Получить объект, если он ещё существует
```

**FinalizationRegistry** — регистрация колбэков, вызываемых перед тем, как объект будет собран сборщиком мусора. Используется для очистки ресурсов.

```javascript
const registry = new FinalizationRegistry((heldValue) => {
  console.log(`Объект ${heldValue} собран`);
});
registry.register(obj, 'myObject');
```

**Практические причины утечек памяти:**

- **Потерянные подписки** — когда обработчик события не удаляется, и объект продолжает существовать.

```javascript
window.addEventListener('resize', handler); // Не удалён
// → handler продолжает существовать вместе с window
```

- **Глобальные ссылки** — объекты, добавленные в глобальный объект, никогда не собираются.

```javascript
window.cache = {};
window.cache.largeData = new Array(1000000);
// → largeData никогда не будет собран
```

- **Замыкания** — функция сохраняет ссылку на внешние переменные, которые могут занимать много памяти.

```javascript
function createHandler() {
  const largeData = new Array(1000000);
  return function() { console.log(largeData.length); };
}
// → largeData существует, пока существует возвращённая функция
```

- **DOM-узлы** — ссылки на удалённые из документа узлы.

```javascript
const elem = document.getElementById('to-remove');
document.body.removeChild(elem);
// → elem всё ещё содержит ссылку на узел, память не освобождена
```

- **Кеширование** — неограниченный рост кеша без стратегии очистки.

## 2.6. Многопоточность современной Web Platform

Хотя основной поток JavaScript остаётся однопоточным, современные приложения активно используют параллельные вычисления для повышения производительности.

**Web Workers** — изолированные потоки, выполняющие JavaScript в фоновом режиме. Не имеют доступа к DOM, общаются с основным потоком через `postMessage()` и `onmessage`.

```javascript
// main.js
const worker = new Worker('worker.js');
worker.postMessage({ data: largeArray });
worker.onmessage = (event) => {
  console.log('Результат:', event.data);
};

// worker.js
self.onmessage = (event) => {
  const result = heavyComputation(event.data);
  self.postMessage(result);
};
```

**Shared Workers** — разделяемые воркеры, которые могут использоваться несколькими окнами или вкладками одного происхождения. Используют порты для общения.

```javascript
// main.js
const sharedWorker = new SharedWorker('shared-worker.js');
sharedWorker.port.postMessage('Hello');
sharedWorker.port.onmessage = (event) => console.log(event.data);
```

**Service Workers** — специальные воркеры, работающие как прокси между приложением и сетью. Используются для кеширования, офлайн-режима, push-уведомлений. Живут независимо от страниц.

```javascript
// service-worker.js
self.addEventListener('install', (event) => {
  event.waitUntil(caches.open('v1').then(cache => cache.addAll(['/'])));
});
self.addEventListener('fetch', (event) => {
  event.respondWith(caches.match(event.request) || fetch(event.request));
});
```

**Worklets** — лёгкие скрипты, выполняющиеся на определённых этапах рендеринга. Важно понимать, что зрелость этих API сильно различается:

- **Paint Worklet** — кастомная отрисовка элементов (часть спецификации CSS Houdini). На момент написания книги эта технология реализована в Chromium-браузерах (Chrome, Edge) и частично в Safari (начиная с версии 16.4), но в Firefox доступна только за флагом. Технология **не входит в Baseline**, поэтому в продакшене её стоит использовать с прогрессивным улучшением или полифилом (например, `css-paint-polyfill`), а не как основной механизм отрисовки.
- **Animation Worklet** — кастомные анимации, синхронизированные с рендерингом. Поддержка ещё более ограничена, чем у Paint Worklet: реализация фактически ограничена Chromium-браузерами. Использовать в продакшн-коде, рассчитанном на широкую аудиторию, не рекомендуется без запасного варианта на `requestAnimationFrame`.
- **Audio Worklet** — обработка аудио в реальном времени. В отличие от двух предыдущих, это часть Web Audio API и имеет значительно более широкую кросс-браузерную поддержку.

**Worker Threads (Node.js)** — аналоги Web Workers для Node.js, позволяющие выполнять код в отдельных потоках. Используют `worker_threads` модуль.

```javascript
// main.js
const { Worker } = require('worker_threads');
const worker = new Worker('./worker.js');
worker.postMessage({ task: 'compute' });
worker.on('message', (result) => console.log(result));
```

**Какие задачи следует переносить за пределы Main Thread:**

- Тяжёлые вычисления — обработка больших массивов, сложные алгоритмы.
- Обработка данных — парсинг больших файлов, преобразование данных.
- Криптографические операции — хеширование, шифрование.
- Сетевые операции — загрузка больших объёмов данных.
- Фоновые задачи — синхронизация, кеширование.

**Взаимодействие между потоками** происходит через передачу сообщений (postMessage/onmessage). Большие объёмы данных можно передавать с помощью Transferable Objects (ArrayBuffer, MessagePort), которые перемещаются между потоками без копирования.

## 2.7. Rendering Pipeline и взаимодействие с браузером

JavaScript не рисует интерфейс самостоятельно. После изменения DOM запускается графический конвейер браузера — Rendering Pipeline.

**Последовательность этапов:**

1. **Style (стили)** — браузер вычисляет стили для каждого элемента на основе CSS-правил, каскада, специфичности и наследования.
2. **Layout (разметка, также Reflow)** — вычисление геометрии элементов: размеров и позиций на странице. Самый дорогой этап, затрагивает всё дерево документа.
3. **Paint (отрисовка)** — создание слоёв и заполнение их пикселями: цвета, фоны, тени, изображения.
4. **Composite (композитинг)** — объединение всех слоёв в финальное изображение для отображения на экране. Самый быстрый этап.

**Влияние JavaScript на производительность:**

- **Layout thrashing** — чередование чтения и записи геометрических свойств, вызывающее многократные перерасчёты Layout.

```javascript
// Плохо — layout thrashing
for (let i = 0; i < elements.length; i++) {
  const height = elements[i].offsetHeight; // Чтение → Layout
  elements[i].style.height = height + 10 + 'px'; // Запись → Layout
}

// Хорошо — пакетные операции
const heights = elements.map(el => el.offsetHeight); // Все чтения → 1 Layout
elements.forEach((el, i) => {
  el.style.height = heights[i] + 10 + 'px'; // Все записи → 1 Layout
});
```

- **Forced reflow (принудительный перерасчёт)** — когда чтение геометрического свойства после записи заставляет браузер немедленно выполнить Layout.

```javascript
element.style.width = '100px';
const height = element.offsetHeight; // Принудительный перерасчёт Layout
```

- **Batching изменений (пакетирование)** — группировка изменений DOM для минимизации количества перерасчётов.

```javascript
// Плохо — каждое изменение вызывает перерасчёт
element.style.width = '100px';
element.style.height = '200px';
element.style.margin = '10px';

// Хорошо — пакетное изменение
element.style.cssText = 'width: 100px; height: 200px; margin: 10px;';
```

- **`requestAnimationFrame()`** — планирование обновлений перед следующим рендерингом. Используется для анимаций и обновлений, которые должны быть синхронизированы с частотой обновления экрана. Технология входит в Baseline Widely Available и доступна во всех современных браузерах без ограничений.

```javascript
function animate() {
  // Обновление состояния
  updateAnimation();
  requestAnimationFrame(animate);
}
requestAnimationFrame(animate);
```

- **`requestIdleCallback()`** — планирование фоновых задач, когда браузер простаивает. Используется для не срочных операций. Важная оговорка: **Safari не поддерживает этот API** ни в одной стабильной версии (реализация доступна только за экспериментальным флагом), поэтому технология не имеет статуса Baseline. Для кода, ориентированного на все браузеры, необходим fallback на `setTimeout()` или полифил.

```javascript
requestIdleCallback((deadline) => {
  while (deadline.timeRemaining() > 0) {
    processNextTask();
  }
});
```

- **`scheduler.postTask()`** — API для планирования задач с приоритетами. Позволяет задавать приоритеты: `user-blocking`, `user-visible`, `background`. На момент написания книги поддерживается в Chrome, Edge и Firefox, но **не реализован в Safari**, из-за чего формально не входит в Baseline. Как и в случае с `requestIdleCallback`, для продакшен-кода стоит предусматривать проверку доступности (`'scheduler' in globalThis`) и запасной вариант через `setTimeout`.

```javascript
scheduler.postTask(() => {
  // Критичная для UI задача
  updateUI();
}, { priority: 'user-blocking' });
```

**Какие операции вызывают Layout (перерасчёт геометрии):**

- Чтение геометрических свойств: `offsetHeight`, `offsetWidth`, `clientHeight`, `clientWidth`, `getBoundingClientRect()`, `scrollTop`, `scrollLeft`.
- Изменение геометрических свойств: `width`, `height`, `margin`, `padding`, `display`, `position`, `top`, `left`.
- Добавление или удаление элементов из DOM.

**Какие операции вызывают только Paint (без Layout):**

- Изменение цветов: `color`, `backgroundColor`, `borderColor`.
- Изменение `boxShadow`, `textShadow`.

**Какие операции выполняются только на этапе Composite (без Layout и Paint):**

- Изменение `transform` (translate, scale, rotate, skew).
- Изменение `opacity`.
- Изменение `will-change`.

## Заключение главы

Современный JavaScript — это не только язык ECMAScript, но и архитектура выполнения, объединяющая движок, рантайм, систему модулей, модель памяти, событийный цикл и графический конвейер браузера. Движок JavaScript (V8, JavaScriptCore, SpiderMonkey) выполняет компиляцию, оптимизацию и управление памятью, а Runtime Environment предоставляет доступ к платформенным API (DOM, Fetch, File System). Execution Context и Lexical Environment определяют области видимости и замыкания. ES Modules организуют код в независимые единицы с собственным жизненным циклом. Event Loop управляет асинхронным выполнением через очереди макро- и микрозадач. Память управляется через поколенческую сборку мусора, а утечек можно избежать, понимая механизмы достижимости. Многопоточность реализована через Web Workers, Shared Workers и Service Workers. Rendering Pipeline связывает JavaScript с графическим конвейером браузера, где изменения DOM проходят через Style, Layout, Paint и Composite. Именно понимание этих компонентов позволяет объяснить поведение асинхронного кода, оптимизировать производительность приложений и принимать инженерные решения на основе устройства платформы, а не эмпирических правил.
