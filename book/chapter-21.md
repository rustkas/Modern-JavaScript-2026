# Часть VI. Современная архитектура

## Глава 21. Современные Web Components: изоляция, композиция и независимость от фреймворков

В 2026 году Web Components представляют собой зрелый набор стандартов Web Platform для создания пользовательских элементов интерфейса без обязательной зависимости от конкретного JavaScript-фреймворка.

Web Components — это не отдельный фреймворк и не одна технология. Архитектура состоит из нескольких независимых механизмов:

- **Custom Elements** позволяют определять собственные HTML-элементы и связывать их с JavaScript-классами;
- **Shadow DOM** изолирует внутреннюю структуру компонента и его стили;
- **HTML Templates** позволяют описывать повторно используемую структуру DOM;
- **Slots** обеспечивают композицию компонента через содержимое, переданное из внешнего документа;
- **Custom Events** обеспечивают коммуникацию между компонентом и окружающим приложением;
- **Declarative Shadow DOM** позволяет создавать Shadow DOM непосредственно из HTML;
- **Scoped Custom Element Registries** решают проблему конфликтов имён между независимыми наборами компонентов, но в 2026 году ещё не имеют полной межбраузерной поддержки.

Поэтому современный Web Component следует воспринимать не просто как «кастомный HTML-тег», а как **самостоятельную границу архитектуры интерфейса**.

Такая граница особенно полезна для design systems, библиотек UI-компонентов, встраиваемых виджетов, микрофронтендов и приложений, в которых отдельные части интерфейса должны иметь независимые жизненные циклы.

При этом Web Components не отменяют React, Vue, Angular, Svelte или другие фреймворки. Компонент может быть создан без фреймворка и затем использоваться внутри приложения, построенного на фреймворке. Поэтому основное архитектурное преимущество Web Components заключается не в «замене фреймворков», а в **стандартизированной границе между компонентом и приложением**.

## 21.1. Custom Elements: JavaScript-класс становится HTML-элементом

Основой Web Components является API **Custom Elements**. Разработчик создаёт класс, наследующий `HTMLElement`, а затем регистрирует его в `CustomElementRegistry`:

```javascript
class UserCard extends HTMLElement {
  connectedCallback() {
    this.textContent = 'User card';
  }
}

customElements.define('user-card', UserCard);
```

После регистрации браузер распознаёт:

```html
<user-card></user-card>
```

как экземпляр `UserCard`.

Имя пользовательского элемента должно содержать дефис (`user-card`, `my-button`, `app-header`). Это правило позволяет браузеру отличать пользовательские элементы от стандартных HTML-элементов (`div`, `button`, `section`), которые никогда не содержат дефис в имени.

### Жизненный цикл элемента

Custom Elements предоставляют набор lifecycle callbacks:

- `constructor()` вызывается при создании экземпляра. В нём следует создавать Shadow DOM и инициализировать внутреннее состояние. Не следует обращаться к атрибутам или DOM — они могут быть ещё не готовы.

- `connectedCallback()` вызывается при добавлении элемента в DOM. Здесь выполняется основная инициализация: чтение атрибутов, загрузка данных, регистрация обработчиков событий, запуск таймеров.

- `disconnectedCallback()` вызывается при удалении элемента из DOM. Здесь освобождаются все ресурсы: таймеры, обработчики событий, наблюдатели. Компонент не должен оставлять после себя активные ресурсы после удаления из документа.

- `attributeChangedCallback(name, oldValue, newValue)` вызывается при изменении отслеживаемого атрибута. Какие атрибуты отслеживать, определяется статическим геттером `observedAttributes`.

- `adoptedCallback()` вызывается при перемещении элемента в другой `Document` (например, при переносе между вкладками). Встречается редко.

**Пример управления ресурсами:**

```javascript
class TimerElement extends HTMLElement {
  connectedCallback() {
    this.timer = setInterval(() => {
      this.dispatchEvent(new Event('tick'));
    }, 1000);
  }

  disconnectedCallback() {
    clearInterval(this.timer); // Обязательное освобождение ресурса
  }
}

customElements.define('x-timer', TimerElement);
```

### Атрибуты и свойства

HTML-атрибуты и JavaScript-свойства — не одно и то же.

**Атрибуты** — это строки в HTML-разметке, доступные через `getAttribute()` и `setAttribute()`. Они подходят для декларативной конфигурации:

```html
<user-card name="Anatoly" theme="dark"></user-card>
```

```javascript
this.getAttribute('name'); // 'Anatoly'
this.getAttribute('theme'); // 'dark'
```

**Свойства** — это поля JavaScript-объекта, доступные через точечную нотацию. Они подходят для программного API и могут содержать сложные объекты, массивы, функции:

```javascript
card.user = { id: 42, name: 'Anatoly' };
card.onSelect = (user) => console.log(user);
```

**Синхронизация атрибутов и свойств:** Часто необходимо синхронизировать атрибут и свойство, чтобы изменение через любой из каналов отражалось в другом. Обычно свойство обновляет атрибут через `setAttribute()`, а атрибут вызывает `attributeChangedCallback()`.

Это важное правило проектирования API Web Component: **HTML задаёт декларативную конфигурацию, JavaScript-свойства предоставляют программный интерфейс**.

## 21.2. Shadow DOM: изоляция внутреннего устройства компонента

Custom Element сам по себе не изолирует DOM. Если компонент просто добавляет обычные дочерние элементы, его внутреннюю структуру можно изменять из внешнего документа.

Shadow DOM создаёт отдельное DOM-дерево:

```javascript
class UserCard extends HTMLElement {
  constructor() {
    super();

    const shadow = this.attachShadow({ mode: 'open' });

    shadow.innerHTML = `
      <style>
        :host {
          display: block;
          border: 1px solid #ccc;
          padding: 1rem;
        }
        .card {
          padding: 0.5rem;
        }
      </style>
      <div class="card">
        <slot></slot>
      </div>
    `;
  }
}

customElements.define('user-card', UserCard);
```

Внешний документ видит:

```html
<user-card>Anatoly</user-card>
```

а внутренняя структура компонента находится в Shadow Tree и не доступна для изменения через стандартные DOM-селекторы извне.

**Режимы Shadow DOM:**

- `mode: 'open'` — внешний код может получить доступ к Shadow DOM через `element.shadowRoot`. Это позволяет инструментам разработки и тестированию взаимодействовать с компонентом.
- `mode: 'closed'` — `element.shadowRoot` возвращает `null`. Используется для полной инкапсуляции, но делает компонент сложнее для отладки.

### Что даёт Shadow DOM

Shadow DOM решает несколько архитектурных проблем:

**Изоляция CSS.** Внешние селекторы не начинают автоматически управлять внутренней структурой Shadow Tree. Например, `user-card div` не будет стилизовать внутренний `div`, потому что он находится в Shadow DOM.

**Изоляция DOM.** Внутренние элементы компонента не являются обычными дочерними узлами внешнего дерева. Они не видны через `document.querySelectorAll('*')` и не влияют на селекторы внешнего документа.

**Ясная граница ответственности.** Компонент самостоятельно управляет своей внутренней структурой, а приложение работает с его публичным API (атрибуты, свойства, события, слоты).

При этом Shadow DOM не является абсолютной «стеной безопасности». JavaScript самого компонента может взаимодействовать с внешним миром, а открытый Shadow Root доступен через `element.shadowRoot`. Поэтому правильнее говорить об **инкапсуляции структуры и стилей**, а не о безопасности.

## 21.3. Slots: композиция вместо жёстко зашитой разметки

Shadow DOM изолирует внутреннюю структуру, но компоненту необходим способ принимать содержимое от приложения. Для этого используется `<slot>`.

**Определение слотов в компоненте:**

```html
<div class="card">
  <header>
    <slot name="title">Default Title</slot>
  </header>
  <main>
    <slot>Default content</slot>
  </main>
</div>
```

**Использование компонента с содержимым:**

```html
<user-card>
  <span slot="title">Developer</span>
  <p>JavaScript engineer with 10 years of experience</p>
</user-card>
```

**Что происходит:**

- Содержимое с атрибутом `slot="title"` помещается в `<slot name="title">`.
- Остальное содержимое (без указания слота) помещается в `<slot>` без имени (default slot).
- Если для слота нет переданного содержимого, отображается содержимое по умолчанию внутри тега `<slot>`.

В результате компонент контролирует структуру своего интерфейса, а приложение контролирует передаваемое содержимое.

Это создаёт важную архитектурную модель: **компонент владеет структурой, приложение владеет данными и контентом.**

Slots особенно полезны для библиотек UI-компонентов, потому что позволяют создавать компоненты без необходимости заранее предусматривать каждую возможную комбинацию содержимого. Например, карточка, диалог, панель инструментов могут иметь гибкое содержимое через слоты.

## 21.4. Стилизация Web Components: граница между изоляцией и кастомизацией

Изоляция не должна означать невозможность настройки компонента. Web Platform предоставляет несколько механизмов для создания контролируемого публичного API стилизации.

**CSS Custom Properties (переменные CSS):**

Компонент определяет переменные с значениями по умолчанию:

```css
:host {
  --user-card-padding: 1rem;
  --user-card-background: #f5f5f5;
  --user-card-border-color: #ccc;
}

.card {
  padding: var(--user-card-padding);
  background: var(--user-card-background);
  border: 1px solid var(--user-card-border-color);
}
```

Приложение изменяет значения:

```css
user-card {
  --user-card-padding: 2rem;
  --user-card-background: #ffffff;
  --user-card-border-color: #007bff;
}
```

**`::part()` — стилизация внутренних элементов:**

Компонент помечает элементы атрибутом `part`:

```html
<div part="header">Header</div>
<div part="content">Content</div>
<div part="footer">Footer</div>
```

Внешний CSS может стилизовать эти части:

```css
user-card::part(header) {
  font-weight: 700;
  font-size: 1.2rem;
}

user-card::part(footer) {
  border-top: 1px solid #eee;
  padding-top: 0.5rem;
}
```

**`::slotted()` — стилизация распределённого содержимого:**

```css
::slotted(.highlight) {
  color: red;
  font-weight: bold;
}
```

**`:host` и `:host(selector)` — стилизация самого компонента:**

```css
:host {
  display: block;
}

:host([theme="dark"]) {
  background: #333;
  color: #fff;
}

:host-context(.dark-theme) {
  /* Стили, когда родитель имеет класс dark-theme */
}
```

Такой подход значительно лучше полного открытия внутренней DOM-структуры: компонент сохраняет контроль над реализацией, но предоставляет стабильные точки расширения.

**Архитектурный принцип:** Внутреннее устройство компонента должно быть скрыто, а точки расширения должны быть частью его публичного контракта.

## 21.5. Custom Events: коммуникация без зависимости от фреймворка

Web Component должен взаимодействовать с приложением через стандартную событийную модель.

**Компонент отправляет событие:**

```javascript
this.dispatchEvent(
  new CustomEvent('user-selected', {
    detail: {
      id: 42,
      name: 'Anatoly'
    },
    bubbles: true,
    composed: true
  })
);
```

**Приложение подписывается:**

```javascript
document.querySelector('user-card').addEventListener('user-selected', (event) => {
  console.log('Selected user:', event.detail.name);
});
```

`CustomEvent` особенно важен для Web Components, потому что он не требует Redux, RxJS, EventEmitter конкретного фреймворка или другого стороннего механизма. Это стандартный DOM-механизм, работающий в любом браузере.

### `bubbles` и `composed`

Для Shadow DOM особенно важно различать два свойства:

- **`bubbles: true`** позволяет событию подниматься по DOM-дереву от целевого элемента к корню документа.
- **`composed: true`** разрешает событию пересекать границу Shadow DOM и выходить во внешний документ.

Поэтому компонент, который должен уведомлять внешнее приложение о пользовательском действии, обычно явно задаёт оба параметра:

```javascript
new CustomEvent('user-selected', {
  detail: user,
  bubbles: true,
  composed: true
});
```

Компонент таким образом публикует **событие**, а не передаёт наружу свою внутреннюю реализацию. Внешнее приложение не знает, какая кнопка была нажата — оно знает только, что пользователь был выбран.

## 21.6. Declarative Shadow DOM: Shadow DOM без обязательного JavaScript

Обычный Shadow DOM создаётся программно:

```javascript
element.attachShadow({ mode: 'open' });
```

Declarative Shadow DOM позволяет описывать его непосредственно в HTML:

```html
<user-card>
  <template shadowrootmode="open">
    <style>
      :host {
        display: block;
        border: 1px solid #ccc;
        padding: 1rem;
      }
    </style>
    <div class="card">
      <slot></slot>
    </div>
  </template>
  Anatoly
</user-card>
```

**Как это работает:**

1. Браузер при разборе HTML встречает `<template shadowrootmode="open">`.
2. Создаёт Shadow DOM для родительского элемента (`<user-card>`).
3. Содержимое шаблона становится Shadow DOM.
4. Шаблон удаляется из документа.
5. Обычное содержимое (`Anatoly`) распределяется по слотам.

Это особенно важно для серверного рендеринга. Сервер может отправить браузеру уже готовую HTML-структуру с Shadow Tree. Браузер способен создать Shadow DOM во время разбора HTML, не требуя предварительного выполнения JavaScript для самого факта создания дерева.

Declarative Shadow DOM имеет статус **Baseline Widely Available** с 2024 года, что означает поддержку во всех современных браузерах.

### Почему это важно для архитектуры

Declarative Shadow DOM уменьшает зависимость первичного отображения компонента от JavaScript. Это полезно для:

- **SSR** — серверный рендеринг с полноценной структурой компонента.
- **Серверно генерируемых страниц** — статические страницы с компонентами.
- **Progressive enhancement** — компонент работает до загрузки JavaScript.
- **Приложений с частичной гидратацией** — только часть компонентов требует JavaScript.

Корректнее сформулировать принцип так: Declarative Shadow DOM позволяет браузеру получить структуру компонента непосредственно из HTML и тем самым уменьшает необходимость создавать эту структуру исключительно через JavaScript.

## 21.7. Scoped Custom Element Registries: решение проблемы глобальных имён

У традиционных Custom Elements есть архитектурное ограничение:

```javascript
customElements.define('my-button', ButtonV1);
```

Имя `my-button` регистрируется глобально. Если другая библиотека попытается зарегистрировать другой класс с тем же именем:

```javascript
customElements.define('my-button', ButtonV2);
```

возникнет ошибка `NotSupportedError: the name "my-button" has already been used with this registry`.

**Scoped Custom Element Registries** позволяют создавать независимые реестры:

```javascript
const registry = new CustomElementRegistry();

registry.define('my-button', ButtonV2);
```

Один registry может содержать одну реализацию `my-button`, другой — другую. Это позволяет нескольким версиям библиотеки существовать одновременно в разных областях DOM.

**Использование scoped registry с корневым элементом:**

```javascript
const root = document.createElement('div');
const registry = new CustomElementRegistry();
registry.define('my-button', ButtonV2);

// Связываем реестр с корневым элементом
root.attachShadow({ mode: 'open', registry });
root.shadowRoot.innerHTML = '<my-button>Click me</my-button>';
```

В 2026 году эта возможность уже реализована в Chrome/Edge 146 и Safari 26, но Firefox её пока не поддерживает. Поэтому Web Platform Features Explorer классифицирует её как **Limited availability**, а Baseline остаётся заблокированным отсутствием Firefox.

**Практический архитектурный вывод:** Scoped registries уже можно использовать в контролируемой Chromium/Safari-среде, но нельзя считать их универсальным браузерным фундаментом для приложения, которое должно одинаково работать в Firefox. Поэтому приложение, рассчитанное на все основные браузеры, должно либо использовать fallback-архитектуру, либо не делать scoped registries обязательной частью своего контракта.

## 21.8. Web Components и микрофронтенды

Web Components особенно хорошо подходят для архитектурных границ между независимыми командами.

Например, приложение может состоять из:

```html
<account-panel></account-panel>
<payment-form></payment-form>
<recommendation-list></recommendation-list>
```

Каждый элемент может быть отдельным продуктовым модулем.

При этом контейнеру не обязательно знать:

- какой фреймворк использует компонент;
- как устроен его внутренний DOM;
- какие внутренние состояния он хранит;
- какие библиотеки используются для его реализации.

Контракт может ограничиваться:

- HTML-атрибутами (декларативная конфигурация);
- JavaScript-свойствами (программный API);
- Custom Events (уведомления о событиях);
- Слотами (передача содержимого);
- CSS Custom Properties (настройка стилей);
- `::part()` (стилизация внутренних элементов).

Это делает Web Component удобной **архитектурной границей**, особенно если жизненный цикл команд и компонентов различается.

**Однако Web Components не устраняют все проблемы микрофронтендов.** Они не решают автоматически вопросы:

- общего состояния приложения;
- маршрутизации;
- загрузки ресурсов;
- авторизации;
- версионирования API;
- обмена данными между командами;
- согласования дизайн-систем.

Web Component решает прежде всего задачу **границы пользовательского интерфейса**, а не всей архитектуры приложения.

## 21.9. Web Components внутри React, Angular, Vue и других фреймворков

Независимость от фреймворка не означает изоляцию от фреймворков. Web Component может использоваться внутри приложения на React, Angular, Vue или другом UI-стеке.

Это позволяет разделить архитектуру на два уровня: внешнее приложение отвечает за маршрутизацию, состояние, бизнес-логику и композицию; Web Component отвечает за автономный пользовательский интерфейс и собственный DOM.

**Пример использования Web Component в React:**

```jsx
function App() {
  const userCardRef = useRef(null);

  useEffect(() => {
    // Установка свойств через JavaScript
    if (userCardRef.current) {
      userCardRef.current.user = { id: 42, name: 'Anatoly' };
    }

    // Подписка на события
    const handler = (event) => console.log(event.detail);
    const element = userCardRef.current;
    element?.addEventListener('user-selected', handler);

    return () => element?.removeEventListener('user-selected', handler);
  }, []);

  return <user-card ref={userCardRef}></user-card>;
}
```

Но такое взаимодействие не всегда является полностью бесшовным. JavaScript-объекты удобнее передавать через свойства элемента, а не сериализовать в HTML-атрибут:

```javascript
// ✅ Хорошо — через свойство
element.user = { id: 42, name: 'Anatoly' };

// ❌ Плохо — через атрибут (сериализация)
element.setAttribute('user', JSON.stringify({ id: 42, name: 'Anatoly' }));
```

Custom Events также требуют адаптации в некоторых фреймворках. Например, в React события на кастомных элементах не всегда работают через пропсы в JSX, поэтому требуется использование `ref` и ручная подписка.

Поэтому Web Components следует рассматривать как **стандартизированный межфреймворковый контракт**, а не как обещание отсутствия интеграционных затрат.

---

## 21.10. Declarative Custom Elements: пока не стандарт Web Platform

Следующий логический шаг — возможность описывать не только Shadow DOM, но и сам Custom Element декларативно. Такой подход позволил бы приблизить модель HTML-компонента к полноценному компоненту, определяемому без обязательной предварительной регистрации JavaScript-класса.

Однако в 2026 году Declarative Custom Elements нельзя описывать как готовую браузерную технологию. В отличие от Declarative Shadow DOM, для Declarative Custom Elements нет завершённого кросс-браузерного стандарта и массовой браузерной реализации. Направление остаётся предметом обсуждений и экспериментальных предложений Web Components Community Group/WICG.

Поэтому следующие утверждения нельзя считать установленными свойствами современной Web Platform:

- браузеры уже автоматически создают полноценные Custom Elements из декларативного HTML;
- SEO автоматически получает преимущества от такой модели;
- screen readers автоматически получают улучшенную семантику;
- существующие фреймворки уже могут отказаться от JavaScript-классов благодаря этому механизму.

Это возможные цели будущего дизайна, но не гарантированные свойства платформы 2026 года.

Для практической разработки Declarative Custom Elements следует считать **экспериментальным направлением**, а не API, на котором следует строить основной production-контракт.

---

## 21.11. Что действительно является современным фундаментом Web Components в 2026 году

Для практической разработки полезно разделить технологии Web Components на три уровня зрелости.

### Зрелый фундамент (production-ready)

В production-коде можно уверенно использовать:

- Custom Elements (регистрация, жизненный цикл);
- Shadow DOM (`open` режим);
- Slots (именованные и анонимные);
- Custom Events (с `bubbles` и `composed`);
- CSS Custom Properties;
- `::part()` и `::slotted()`;
- Declarative Shadow DOM.

Эти механизмы образуют основной стандартный фундамент Web Components.

### Новая, но ещё не полностью кросс-браузерная возможность

Scoped Custom Element Registries уже имеют реализации в Chrome/Edge и Safari, но Firefox пока отсутствует. Поэтому их следует использовать только после проверки требований к браузерам.

### Экспериментальное направление

Declarative Custom Elements пока не являются универсальным браузерным API. Их нельзя ставить в один ряд с Custom Elements или Declarative Shadow DOM.

Такое разделение зрелости особенно важно для книги о JavaScript 2026: **современность технологии определяется не тем, насколько интересно звучит предложение, а тем, какой статус оно имеет в спецификации и какие браузеры реально его реализуют.**

## 21.12. Архитектурная модель Web Component 2026

Современный Web Component можно представить как объект с несколькими уровнями ответственности:

```
HTML
 │
 ├── attributes ───────► configuration (декларативная настройка)
 │
 ├── slots ────────────► external content (внешнее содержимое)
 │
 ▼
Custom Element
 │
 ├── properties ───────► programmatic API (программный интерфейс)
 │
 ├── Shadow DOM ───────► internal structure (внутренняя структура)
 │
 ├── lifecycle ────────► resource management (управление ресурсами)
 │
 └── Custom Events ────► external communication (внешняя коммуникация)
        │
        ▼
   Application
```

Такая архитектура создаёт чёткий контракт:

- **HTML-атрибуты** описывают декларативную конфигурацию.
- **Properties** предоставляют программный API.
- **Slots** позволяют приложению передавать содержимое.
- **Shadow DOM** скрывает внутреннюю реализацию.
- **Custom Events** сообщают приложению о событиях компонента.
- **CSS Custom Properties и `::part()`** определяют контролируемые точки визуальной кастомизации.

Именно эта модель делает Web Components устойчивыми к смене фреймворка.

## 21.13. Заключение: Web Components как архитектурный контракт

В 2026 году Web Components следует воспринимать не как альтернативу React, Angular, Vue или Svelte, а как **стандартный механизм создания независимых элементов пользовательского интерфейса**.

Их сила состоит в комбинации нескольких возможностей:

- Custom Elements дают компоненту собственное имя и жизненный цикл;
- Shadow DOM изолирует внутреннюю реализацию;
- Slots обеспечивают композицию;
- Custom Events создают независимый механизм коммуникации;
- CSS Custom Properties и `::part()` предоставляют контролируемую стилизацию;
- Declarative Shadow DOM позволяет создавать Shadow Tree непосредственно из HTML;
- Scoped Custom Element Registries решают проблему конфликтующих наборов компонентов там, где браузер их поддерживает.

При этом необходимо строго разделять зрелые стандарты и перспективные предложения.

- **Declarative Shadow DOM** — современная production-технология.
- **Scoped Custom Element Registries** — уже реализованная, но пока не полностью кросс-браузерная возможность.
- **Declarative Custom Elements** — перспективное направление, а не готовый стандарт.

Поэтому главный архитектурный вывод Modern JavaScript 2026 звучит так:

> **Web Components ценны не потому, что позволяют отказаться от фреймворков, а потому, что позволяют создать устойчивую границу между пользовательским интерфейсом и технологическим стеком, который находится за этой границей.**

Это особенно важно для библиотек компонентов, design systems, микрофронтендов и долгоживущих веб-продуктов, где отдельные части приложения могут менять внутренний JavaScript-стек, не меняя публичный контракт компонента.
