# Часть II. Современный язык JavaScript

# Глава 7. ES Modules: современная модульная архитектура JavaScript

Модульная система — одна из главных причин, по которой современный JavaScript перестал быть языком отдельных файлов и превратился в язык крупных инженерных систем.

К 2026 году **ECMAScript Modules (ESM)** стали универсальным форматом организации программ практически во всех средах выполнения: браузерах, Node.js, Deno, Bun, Cloudflare Workers и Edge Runtime. Большинство современных инструментов разработки рассматривают ESM не как дополнительную возможность языка, а как его фундаментальную архитектурную модель.

В отличие от прежних систем модулей, ESM является частью самого стандарта ECMAScript. Благодаря этому браузеры, серверные рантаймы, сборщики проектов и средства статического анализа используют единый механизм построения графа зависимостей, разрешения импортов и исполнения программы.

---

## 7.1. Почему ESM стали стандартом всей экосистемы

История JavaScript знала множество модульных систем:

- **IIFE (Immediately Invoked Function Expression)** — паттерн, использовавшийся для создания изолированных областей видимости до появления официальных модулей. Код оборачивался в функцию, которая сразу же выполнялась, создавая приватную область видимости.

- **AMD (Asynchronous Module Definition)** — разработан для браузеров с асинхронной загрузкой зависимостей. Библиотека RequireJS была самым известным реализацией AMD.

- **UMD (Universal Module Definition)** — гибридный формат, работавший одновременно с AMD и CommonJS. Он проверял, какая среда загружает модуль, и адаптировался под неё.

- **CommonJS** — синхронная модульная система, ставшая стандартом в Node.js. Модули загружаются с помощью `require()` и экспортируются через `module.exports`. Эта система работает синхронно, что приемлемо на сервере, но не подходит для браузеров.

- **SystemJS** — универсальный загрузчик модулей, использовавшийся для динамической загрузки. Он позволял загружать модули в любом формате (CommonJS, AMD, ESM) в браузере.

Все они решали одну и ту же проблему — организацию зависимостей, но делали это по-разному, что приводило к фрагментации экосистемы.

ES Modules стали первым решением, встроенным непосредственно в язык. Это означает, что для работы с модулями не нужно подключать сторонние библиотеки — браузер и рантайм понимают `import` и `export` из коробки.

Сегодня именно они обеспечивают:

- единый синтаксис во всех средах;
- статический анализ зависимостей;
- эффективную оптимизацию;
- безопасную загрузку;
- поддержку современными браузерами без транспиляции.

В большинстве новых проектов CommonJS рассматривается исключительно как механизм поддержки существующего кода. Новые пакеты публикуются в формате ESM, а поддержка CommonJS сохраняется для обратной совместимости.

## 7.2. Статическая природа модульной системы

Главная особенность ESM — декларативность.

Все зависимости известны ещё до начала выполнения программы. Это возможно потому, что `import` и `export` являются ключевыми словами языка, а не функциями, вызываемыми во время выполнения (в отличие от `require()` в CommonJS).

Статическая структура позволяет:

- построить полный граф модулей — браузер или сборщик может определить все зависимости, просто проанализировав исходный код;
- заранее обнаружить ошибки импорта — если модуль не найден или экспорт отсутствует, ошибка возникает на этапе загрузки, а не во время выполнения;
- выполнить Tree Shaking — удалить неиспользуемый код, поскольку известно, какие экспорты действительно используются;
- организовать параллельную загрузку зависимостей — браузер может загружать модули одновременно, так как знает все зависимости заранее;
- оптимизировать компиляцию — движки могут компилировать модули до их фактического выполнения.

Статический анализ стал одной из причин высокой производительности современных инструментов разработки. Сборщики, такие как Vite, Rollup и Webpack, используют статическую природу ESM для оптимизации сборки.

## 7.3. Экспорт и импорт как живые связи (Live Bindings)

Одной из фундаментальных особенностей ESM являются **живые привязки (Live Bindings)**.

Экспортируемое значение не копируется между файлами. Импорт получает ссылку на исходную привязку, а не копию значения.

Когда модуль, который экспортирует значение, изменяет его, все импортирующие модули видят новое значение автоматически. Это отличается от CommonJS, где `require()` возвращает копию экспортируемого объекта.

**Как работают живые привязки:**

```javascript
// counter.js
export let count = 0;
export function increment() {
  count++;
}

// app.js
import { count, increment } from './counter.js';
console.log(count); // 0
increment();
console.log(count); // 1 — значение обновлено, потому что импорт — это ссылка
```

Именованные экспорты всегда являются живыми привязками. Экспорт по умолчанию (`export default`) также является живой привязкой, но с одним важным отличием: при импорте значения по умолчанию можно использовать любое имя, и оно всё равно будет ссылаться на тот же объект.

**Различие между `export default value` и `export { value }`:**

```javascript
// module1.js
export default 42;

// module2.js
export const value = 42;
```

При импорте:

```javascript
// Для export default
import anyName from './module1.js'; // anyName === 42

// Для именованного экспорта
import { value } from './module2.js'; // value === 42
```

Основная ошибка возникает, когда разработчики пытаются использовать синтаксис `export default` для экспорта нескольких значений или путают его с именованным экспортом. `export default` предназначен для единственного основного экспорта модуля, а именованные экспорты — для дополнительных.

Доступны следующие формы экспорта и импорта:

- `export` — именованный экспорт одного или нескольких значений: `export const name = 'value'`
- `export default` — экспорт по умолчанию: `export default class MyClass {}`
- re-export — переэкспорт из других модулей: `export { something } from './other.js'`
- namespace import — импорт всех экспортов в один объект: `import * as Module from './module.js'`
- `import.meta` — доступ к метаданным модуля, включая его URL и параметры

## 7.4. Жизненный цикл Module Record

Спецификация ECMAScript рассматривает каждый модуль как объект **Module Record**. Module Record — это абстрактное представление модуля, содержащее его код, зависимости и состояние выполнения.

Каждый модуль проходит три последовательных этапа.

### Loading (Загрузка)

На этом этапе происходит получение исходного текста модуля. Браузер или рантайм определяет спецификатор модуля (путь или URL), загружает файл и парсит его для извлечения инструкций `import` и `export`.

На этапе загрузки разрешаются спецификаторы модулей — то есть определяются реальные URL или пути для каждого импорта. Спецификатор `'./utils.js'` превращается в полный путь к файлу, а `'lodash'` может разрешаться через `node_modules` или Import Map.

### Linking (Связывание)

На этом этапе строится граф зависимостей. Создаются Module Environment Records — структуры, связывающие имена экспортов с их значениями. Проверяется, что все импортируемые имена действительно существуют в соответствующих модулях.

Выполняются следующие проверки:

- существование экспортов — каждый импорт должен соответствовать реальному экспорту в другом модуле;
- циклические зависимости — определяется, есть ли замкнутые циклы в графе зависимостей;
- корректность импортов — проверяется синтаксическая правильность всех инструкций импорта.

Большинство ошибок обнаруживается именно на этапе Linking. Если модуль импортирует несуществующее имя, ошибка возникает до выполнения любого кода.

### Evaluation (Выполнение)

После успешного связывания модули выполняются. Модули вычисляются строго в порядке зависимостей — от самых глубоких к корневым. Это гарантирует, что к моменту выполнения модуля все его зависимости уже инициализированы.

При использовании Top-Level Await порядок выполнения изменяется. Модуль, содержащий `await` на верхнем уровне, приостанавливает выполнение всех модулей, которые от него зависят, пока ожидаемая операция не завершится.

**Пример с Top-Level Await:**

```javascript
// data.js
const response = await fetch('/api/data');
export const data = await response.json();

// app.js
import { data } from './data.js'; // Ждёт завершения data.js
console.log(data); // Данные доступны только после загрузки
```

Top-Level Await позволяет выполнять асинхронную инициализацию модулей на верхнем уровне, что упрощает код и устраняет необходимость в фабричных функциях или обёртках.

## 7.5. Разрешение модулей в различных рантаймах

Хотя спецификация ECMAScript описывает модель модулей, конкретные правила поиска файлов определяются хост-средой. Это приводит к различиям в том, как один и тот же импорт может работать в разных средах.

**Браузеры** используют URL для разрешения импортов. Спецификатор модуля является URL или относительным путём, который разрешается относительно текущего URL страницы.

```javascript
import { foo } from './module.js'; // Относительно текущего URL
import { bar } from 'https://cdn.com/module.js'; // Абсолютный URL
```

**Node.js** использует файловую систему и `node_modules`. Если спецификатор начинается с `/`, `./` или `../`, он считается относительным путём. Иначе он ищется в `node_modules`.

Node.js также требует явного указания расширений файлов для относительных путей: `import './module.js'` работает, а `import './module'` — нет (если только не используется разрешение с расширениями).

Стоит уточнить историю поддержки ESM в Node.js, поскольку она развивалась поэтапно, а не одномоментно: экспериментальная реализация появилась ещё в Node.js 8.5 (2017 год), в 12-й версии она оставалась за флагом `--experimental-modules` с предупреждением в консоли, флаг убрали в 13.2, но полностью стабильной (без экспериментального статуса) реализация стала лишь в диапазоне Node.js 13.14–14.0 (первая половина 2020 года). Ещё одно важное для 2026 года изменение — в Node.js 20.19+ и 22.12+, а также стабильно в Node.js 24, `require()` из CommonJS-файла научился напрямую загружать синхронные ESM-модули (`require(esm)`), что заметно упростило миграцию смешанных проектов; для модулей с top-level await по-прежнему нужен `import()`.

**Deno** использует URL-подход, как браузеры. Импорты разрешаются по полным URL или относительным путям, и Deno может загружать модули прямо из интернета.

**Bun** поддерживает гибридный подход, работая и с файловой системой, и с URL.

**Package exports и package imports** — механизмы, определённые в `package.json`, которые позволяют управлять тем, как импортируются пакеты.

Поле `exports` определяет точку входа в пакет:

```json
{
  "exports": {
    ".": "./index.js",
    "./utils": "./src/utils.js"
  }
}
```

Это позволяет использовать импорт `import { something } from 'package'` вместо `import { something } from 'package/dist/index.js'`.

Условные экспорты позволяют выбирать разные файлы в зависимости от среды:

```json
{
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "browser": "./dist/browser.js"
    }
  }
}
```

Node.js использует поля `type` в `package.json` для определения формата модулей по умолчанию: `"type": "module"` означает, что все `.js` файлы трактуются как ESM, а `"type": "commonjs"` — как CommonJS.

Поля `main` (устаревшая точка входа), `module` (используется сборщиками для ESM-версии) и `exports` (современный стандарт) взаимодействуют между собой. Если указано `exports`, оно имеет приоритет над `main` и `module`.

## 7.6. Динамический импорт и разделение приложения

Конструкция `await import(...)` — это динамическая версия статического импорта. Она возвращает Promise, который разрешается с объектом модуля.

Динамический импорт не является заменой обычному `import`. Он дополняет его, позволяя загружать модули в тех случаях, когда статический импорт невозможен или нежелателен:

- ленивая загрузка — код загружается только когда он действительно нужен, например, при открытии диалога или переходе на страницу;
- микрофронтенды — независимые приложения загружаются динамически в рантайме;
- Feature Flags — функциональность включается или отключается в зависимости от условий, и соответствующий код загружается динамически;
- локализация — языковые файлы загружаются только для выбранного языка;
- плагинная архитектура — плагины загружаются динамически в зависимости от конфигурации;
- условная загрузка больших библиотек — например, загрузка графовой библиотеки только при отображении графика.

**Пример динамического импорта:**

```javascript
const openDialog = async () => {
  const { Dialog } = await import('./components/Dialog.js');
  const dialog = new Dialog();
  dialog.show();
};
```

Динамический импорт влияет на производительность и построение графа модулей. Поскольку зависимости динамического импорта не известны на этапе статического анализа, сборщики не включают их в основной чанк, а создают отдельные фрагменты (chunks), которые загружаются по требованию.

## 7.7. Import Maps и управление пространством имён

Import Maps позволяют перенести разрешение модулей на уровень платформы. Вместо того чтобы указывать полные пути в каждом файле, разработчик определяет соответствие между логическими именами и реальными URL в одном месте.

Без Import Maps:

```javascript
import { Button } from '../node_modules/ui-library/dist/button.js';
```

С Import Maps:

```javascript
import { Button } from 'ui';
```

Соответствие имени реальному URL определяется единожды в Import Map, которая задаётся в HTML через тег `<script type="importmap">`:

```html
<script type="importmap">
  {
    "imports": {
      "ui": "/node_modules/ui/index.js",
      "react": "/node_modules/react/index.js",
      "lodash": "/node_modules/lodash-es/index.js"
    }
  }
</script>
```

Import Maps значительно упрощают:

- сопровождение проекта — если путь к библиотеке меняется, обновление требуется только в одном месте;
- миграцию библиотек — можно заменить реализацию библиотеки, не изменяя код приложения;
- управление версиями — разные версии одной библиотеки могут использовать разные имена;
- разработку без сборщика — можно использовать модули напрямую в браузере без инструментов сборки.

Браузеры поддерживают Import Maps нативно с 2023 года — Chrome реализовал их раньше, ещё в версии 89 (март 2021), Firefox добавил поддержку в версии 108 (декабрь 2022), а замыкающим стал Safari 16.4 (март 2023), после чего технология стала по-настоящему кросс-браузерной и получила статус Baseline. На момент написания книги остаётся один нюанс, полезный для читателей, работающих с несколькими независимыми Import Maps на одной странице: поддержка нескольких карт импорта в одном документе уже реализована в Chromium и WebKit, но пока отсутствует в Firefox.

## 7.8. Производительность современного графа модулей

ESM открывают возможности для глубокой оптимизации, недоступные для других модульных систем.

Современные браузеры и сборщики используют:

- **`modulepreload`** — предварительная загрузка модулей. Указывает браузеру начать загрузку модуля до того, как он будет запрошен импортом:

```html
<link rel="modulepreload" href="/src/app.js" />
```

- **предварительная компиляция** — браузеры могут компилировать модули фоном, до того как они понадобятся для выполнения;
- **параллельная загрузка** — поскольку граф зависимостей известен заранее, браузер может загружать модули параллельно, а не последовательно;
- **Tree Shaking** — удаление неиспользуемого кода. Сборщик анализирует граф зависимостей и удаляет экспорты, которые не используются нигде в приложении;
- **code splitting** — разделение кода на чанки. Приложение разбивается на несколько файлов, которые загружаются по требованию;
- **chunk optimization** — оптимизация размера чанков. Сборщик объединяет модули в чанки оптимального размера для эффективной загрузки;
- **дедупликация зависимостей** — если несколько модулей используют одну и ту же зависимость, она загружается только один раз.

Влияние структуры графа модулей на время запуска приложения: чем глубже и сложнее граф, тем больше времени требуется на его загрузку и выполнение. Использование динамического импорта и code splitting позволяет уменьшить начальную загрузку.

## 7.9. ESM как основа современной Web Platform

Сегодня ESM лежат в основе практически всей современной экосистемы JavaScript.

Именно они обеспечивают единый механизм работы для:

- браузеров — нативная поддержка, без сборщиков и транспиляции;
- Node.js — начиная с версии 12, ESM поддерживается стабильно;
- Deno — ESM используется по умолчанию;
- Bun — полная поддержка ESM и CommonJS;
- Web Workers — модули могут загружаться в воркерах;
- Service Workers — модули поддерживаются для сервис-воркеров;
- Edge Functions — Cloudflare Workers и подобные платформы поддерживают ESM;
- Cloud Runtime — большинство современных облачных сред поддерживают ESM.

Благодаря общей модели модулей один и тот же код может использоваться практически без изменений в различных средах выполнения. Это делает ESM фундаментальным компонентом современной Web Platform, а не просто языковой возможностью.

## Заключение главы

ES Modules — это не просто современный синтаксис `import` и `export`. Это архитектурная модель, определяющая способ организации программ на JavaScript. Статический анализ позволяет строить полный граф зависимостей до выполнения, что даёт возможность обнаруживать ошибки на этапе загрузки, выполнять Tree Shaking и оптимизировать производительность. Живые привязки обеспечивают автоматическую синхронизацию состояния между модулями. Разрешение модулей отличается в разных средах, но единая модель Module Record делает поведение предсказуемым. Динамический импорт и Import Maps добавляют гибкости, позволяя загружать код по требованию и управлять пространством имён на уровне платформы. Все эти возможности делают ESM фундаментом современного JavaScript, обеспечивая единый механизм работы в браузерах, серверных рантаймах, облачных средах и edge-платформах.
