# Часть V. Производительность

# Глава 16. JavaScript и Rendering Pipeline: архитектура плавного интерфейса

К 2026 году производительность веб-приложений определяется не скоростью выполнения отдельных инструкций JavaScript, а тем, насколько эффективно приложение взаимодействует с механизмами браузера. Даже очень быстрый код может привести к заметным задержкам, если он заставляет браузер многократно пересчитывать стили, геометрию страницы или выполнять лишнюю отрисовку.

Современный JavaScript выступает координатором работы Web Platform. Он изменяет состояние приложения, а браузер самостоятельно выполняет все ресурсоёмкие операции по вычислению стилей, построению макета страницы, рисованию элементов и выводу изображения на экран.

Главная задача разработчика — изменять DOM и CSS таким образом, чтобы браузер мог выполнить эти операции минимальное количество раз.

---

## 16.1. Полный жизненный цикл: от JavaScript до изображения на экране

После загрузки страницы браузер последовательно проходит несколько этапов. Первые три относятся к работе JavaScript-движка, остальные — к Rendering Pipeline.

### Этап 1. Parse (Разбор)


Браузер получает JavaScript-код и преобразует его из текста во внутреннее структурированное представление.

На этом этапе происходят:

* лексический анализ исходного текста (разбиение текста на токены);
* распознавание синтаксической структуры;
* построение внутренних представлений (программы построение синтаксического дерева (AST)).
* проверка корректности программы (синтаксические ошибки).

```javascript
// Исходный код
function greet(name) {
  console.log('Hello', name);
}

// После парсинга — AST (упрощённо)
{
  type: 'FunctionDeclaration',
  name: 'greet',
  params: ['name'],
  body: { type: 'BlockStatement', /* ... */ }
}
```

Современные движки выполняют потоковый разбор (Streaming Parsing), не дожидаясь полной загрузки большого файла. Браузер начинает обрабатывать полученные байты по мере их поступления, не дожидаясь полной загрузки скрипта. Это особенно важно для модульных приложений, в которых код поступает несколькими сетевыми ресурсами.


---

### Этап 2. Compile (Компиляция)

После успешного разбора JavaScript-движок компилирует программу. Современные движки используют многоуровневую схему:

1. **Генерация байткода** — преобразование AST в промежуточный байт-код (например, Ignition в V8).
2. **Интерпретация** — выполнение байткода интерпретатором для быстрого старта.
3. **JIT-компиляция** — наиболее часто выполняемые участки программы (горячий код) компилируются в машинный код для ускорения.
4. **Оптимизация** — горячий код дополнительно оптимизируется на основе профилирования (например, TurboFan в V8).

```javascript
// Функция, вызываемая много раз — становится горячим кодом
function calculate(a, b) {
  return a + b;
}
// JIT-компилятор может оптимизировать её, предполагая, что a и b — числа
```

Если приложение использует ES Modules, браузер способен заранее загрузить и подготовить модули с помощью `<link rel="modulepreload">`, что уменьшает задержку перед первым выполнением кода.

```html
<link rel="modulepreload" href="/src/app.js">
<link rel="modulepreload" href="/src/utils.js">
```

### Этап 3. Execute (Выполнение)

На этапе выполнения JavaScript изменяет состояние приложения. Типичные операции:

- изменение DOM (`appendChild`, `removeChild`, `setAttribute`);
- изменение CSS-классов (`classList.add`, `classList.remove`);
- сетевые запросы через Fetch API;
- запуск анимаций (`requestAnimationFrame`);
- обработка событий (клики, ввод, скролл).

**Long Tasks (Долгие задачи):** Задачи, выполняющиеся более 50 мс. Пока JavaScript занимает главный поток, браузер не может перейти к следующим этапам Rendering Pipeline. Пользователь в этот момент не увидит обновления интерфейса и не сможет взаимодействовать со страницей.

```javascript
// Плохо — блокирует главный поток на 200 мс
function heavyComputation() {
  for (let i = 0; i < 1000000000; i++) {
    // тяжёлая операция
  }
}

// Хорошо — разбивка на части с использованием scheduler
function heavyComputation() {
  scheduler.postTask(() => {
    // часть работы
  }, { priority: 'background' });
}
```

После завершения выполнения JavaScript управление передаётся браузеру.

---

### Этап 4. Style Recalculation (Пересчёт стилей)

Если JavaScript изменил DOM или CSS, браузер должен заново вычислить стили затронутых элементов. На этом этапе определяется:

- какие CSS-правила подходят элементу (селекторы и каскад);
- результат каскада (приоритет правил);
- наследование (передача свойств от родителя к дочерним элементам);
- вычисленные значения всех свойств (например, `auto` → конкретное значение).

```javascript
element.classList.add('active');
// Браузер должен пересчитать стили для элемента и его потомков
// Проверить, какие правила применяются к .active
// Вычислить финальные значения свойств
```

Чем меньше элементов затронуто изменением, тем быстрее проходит этот этап. Изменение стиля на самом верхнем элементе может затронуть все дочерние элементы.

---

### Этап 5. Layout (Разметка, также Reflow)

После вычисления стилей браузер определяет геометрию документа. На этом этапе вычисляются:

- размеры элементов (`width`, `height`);
- положение элементов (`top`, `left`, `margin`);
- перенос текста (как строки располагаются внутри элементов);
- размеры таблиц (автоматические расчёты колонок);
- положение flex- и grid-контейнеров.

Layout относится к наиболее дорогим операциям Rendering Pipeline. Он может затронуть всё дерево документа при изменении размеров корневого элемента.

**Чтение геометрических свойств:** Когда JavaScript читает свойства, требующие геометрии, браузер должен выполнить Layout немедленно.

```javascript
// Эти свойства вызывают принудительный Layout
const height = element.offsetHeight;
const width = element.offsetWidth;
const rect = element.getBoundingClientRect();
const scrollTop = element.scrollTop;
```

**Forced Synchronous Layout (Принудительный синхронный Layout):** Ситуация, когда JavaScript чередует чтение и запись геометрических свойств.

```javascript
// Плохо — принудительный Layout на каждой итерации
const elements = document.querySelectorAll('.item');
for (let i = 0; i < elements.length; i++) {
  const height = elements[i].offsetHeight; // Чтение → Layout
  elements[i].style.height = height + 10 + 'px'; // Запись → планирует Layout
}
// Каждая итерация вызывает Layout из-за чередования чтения и записи
```

**Layout Thrashing (Трепетание Layout):** Многократное выполнение Layout из-за постоянного чередования чтения и записи геометрических свойств. Одна из самых распространённых причин потери производительности.

```javascript
// Хорошо — пакетные операции
const elements = document.querySelectorAll('.item');
const heights = [];
for (let i = 0; i < elements.length; i++) {
  heights.push(elements[i].offsetHeight); // Все чтения → 1 Layout
}
for (let i = 0; i < elements.length; i++) {
  elements[i].style.height = heights[i] + 10 + 'px'; // Все записи → 1 Layout
}
// Всего 2 Layout вместо N
```

Современная практика состоит в том, чтобы сначала выполнять все чтения геометрии, а затем все изменения DOM, или использовать `requestAnimationFrame()` для разделения фаз.

---

### Этап 6. Paint (Отрисовка)

После вычисления геометрии браузер рисует элементы. На этапе Paint происходит:

- рисование текста (шрифты, размеры, цвета);
- заливка фона (`background-color`, `background-image`);
- отображение границ (`border`);
- построение теней (`box-shadow`, `text-shadow`);
- прорисовка изображений (`<img>`, `background-image`);
- применение фильтров (`filter`, `backdrop-filter`).

**Когда Paint не требует Layout:** Если изменяется только цвет текста (`color`), браузеру обычно не требуется заново выполнять Layout. Достаточно повторно нарисовать элемент. Это значительно дешевле.

```javascript
// Только Paint (без Layout)
element.style.color = 'red';
element.style.backgroundColor = 'blue';

// Layout + Paint
element.style.width = '100px';
element.style.height = '200px';
```

---

### Этап 7. Composite (Композиция)

Последний этап — композиция изображения. Браузер объединяет подготовленные слои страницы и передаёт результат графическому процессору (GPU).

Некоторые CSS-свойства позволяют выполнить изменение только на этом этапе, без Layout и Paint. Наиболее известные:

- `transform` — перемещение, масштабирование, поворот, наклон.
- `opacity` — прозрачность.
- `will-change` — подсказка браузеру, что свойство будет меняться.

```css
/* Только Composite (без Layout и Paint) */
element.style.transform = 'translateX(100px)';
element.style.opacity = '0.5';
```

**Почему это эффективно:** `transform` перемещает уже отрисованный слой, не требуя перерисовки содержимого. Браузер может выполнить эту операцию на GPU, что значительно быстрее, чем перерисовка на CPU.

Следует помнить, что это значительно снижает нагрузку на Rendering Pipeline, но не гарантирует постоянную частоту 60 FPS. Итоговая производительность зависит от сложности сцены, количества одновременно анимируемых элементов и возможностей устройства пользователя.

## 16.2. Синхронизация JavaScript с Rendering Pipeline

Браузер обновляет изображение дискретно — перед выводом очередного кадра (обычно каждые 16.7 мс при 60 FPS). Чтобы изменения интерфейса происходили максимально эффективно, JavaScript должен синхронизироваться с этим циклом.

**`requestAnimationFrame()`** — планирует выполнение кода непосредственно перед построением следующего кадра. Технология имеет статус Baseline Widely Available и поддерживается во всех современных браузерах без ограничений.

```javascript
function updateAnimation(timestamp) {
  // Обновление состояния анимации
  element.style.transform = `translateX(${x}px)`;
  x += 1;
  
  // Планирование следующего кадра
  requestAnimationFrame(updateAnimation);
}
requestAnimationFrame(updateAnimation);
```

Такой подход позволяет:

- объединить несколько изменений DOM в один пакет перед рендерингом;
- избежать лишних перерасчётов Layout (браузер выполняет Layout один раз для всех изменений);
- выполнять анимации синхронно с частотой обновления экрана (сглаживание джиттера);
- автоматически приостанавливать анимацию при переключении вкладок (экономия ресурсов).

**`requestIdleCallback()`** — планирует выполнение фоновых задач, когда браузер простаивает.

```javascript
requestIdleCallback((deadline) => {
  while (deadline.timeRemaining() > 0 && tasks.length > 0) {
    const task = tasks.pop();
    task();
  }
});
```

Используется для не критичных к времени операций: отправка аналитики, предзагрузка данных, очистка кеша. Здесь важна та же оговорка, что уже звучала в главе про архитектуру рантайма: **Safari не поддерживает `requestIdleCallback()`** ни в одной стабильной версии — API доступен только за экспериментальным флагом. Это значит, что технология формально не входит в Baseline, и код, ориентированный на все браузеры, должен предусматривать fallback на `setTimeout()`:

```javascript
const scheduleIdleTask = window.requestIdleCallback
  ? window.requestIdleCallback
  : (callback) => setTimeout(() => callback({ timeRemaining: () => 50 }), 1);
```

**`scheduler.postTask()`** — современный API для управления приоритетами задач.

```javascript
// Критичная для UI задача — выполняется перед рендерингом
scheduler.postTask(() => {
  updateUI();
}, { priority: 'user-blocking' });

// Фоновая задача — выполняется в свободное время
scheduler.postTask(() => {
  syncData();
}, { priority: 'background' });
```

Как и `requestIdleCallback()`, эта технология **не реализована в Safari** и поэтому также не входит в Baseline (поддерживается в Chrome, Edge и Firefox). Перед использованием в продакшене стоит проверять доступность API (`'scheduler' in globalThis`) и предусматривать запасной вариант.

Для фоновых вычислений, не связанных с отрисовкой, лучше использовать асинхронные операции, Web Workers или другие механизмы, не блокирующие главный поток.

## 16.3. Минимизация работы Rendering Pipeline

Большинство современных рекомендаций по оптимизации производительности сводятся к уменьшению объёма работы браузера.

**На практике это означает:**

1. **Изменять DOM как можно реже** — вместо множества отдельных изменений группировать их.

```javascript
// Плохо — каждое изменение вызывает перерасчёт
list.appendChild(item1);
list.appendChild(item2);
list.appendChild(item3);

// Хорошо — использование DocumentFragment
const fragment = document.createDocumentFragment();
fragment.appendChild(item1);
fragment.appendChild(item2);
fragment.appendChild(item3);
list.appendChild(fragment);
```

2. **Группировать несколько изменений в одну операцию** — использовать `classList` вместо отдельных стилей.

```javascript
// Плохо
element.style.width = '100px';
element.style.height = '200px';
element.style.margin = '10px';

// Хорошо — использование CSS-классов
element.className = 'large-element';
// CSS: .large-element { width: 100px; height: 200px; margin: 10px; }
```

3. **Избегать принудительного Layout** — не чередовать чтение и запись геометрических свойств.

4. **Использовать CSS-анимации для визуальных эффектов** — браузер может оптимизировать их на уровне композитинга.

5. **Анимировать преимущественно свойства `transform` и `opacity`** — они выполняются только на этапе Composite.

6. **Переносить тяжёлые вычисления в Web Workers** — освобождать главный поток.

```javascript
const worker = new Worker('heavy-task.js');
worker.postMessage({ data: largeArray });
worker.onmessage = (event) => {
  console.log('Результат:', event.data);
};
```

7. **Обрабатывать большие объёмы данных потоками через Streams API** вместо полной загрузки в память.

```javascript
const response = await fetch('/api/large-data');
const reader = response.body.getReader();
// Обработка по частям без загрузки всего файла
```

8. **Применять виртуализацию списков при отображении тысяч элементов** — рендерить только видимые элементы.

```javascript
// Библиотеки: react-window, react-virtualized, virtual-list
import { FixedSizeList } from 'react-window';
// Рендерит только видимые строки
```

Чем меньше этапов Rendering Pipeline приходится выполнять браузеру после каждого изменения состояния приложения, тем выше остаётся отзывчивость интерфейса.

## Заключение главы

Производительность современных веб-приложений определяется совместной работой JavaScript и Rendering Pipeline. Parse, Compile и Execute относятся к работе JavaScript-движка. Style Recalculation, Layout, Paint и Composite — к графическому конвейеру браузера. JavaScript изменяет состояние приложения, а браузер самостоятельно выполняет вычисление стилей, построение макета страницы, рисование элементов и композицию изображения. Чем реже приложение заставляет браузер выполнять дорогостоящие этапы Style Recalculation, Layout и Paint, тем быстрее интерфейс реагирует на действия пользователя.

Современные практики производительности включают: группировку изменений DOM, избегание принудительного Layout и Layout Thrashing, использование `requestAnimationFrame()` для синхронизации с рендерингом, применение CSS-анимаций для визуальных эффектов, анимацию только `transform` и `opacity`, перенос тяжёлых вычислений в Web Workers, потоковую обработку данных через Streams API и виртуализацию списков.

В современной разработке основное внимание уделяется не микрооптимизации отдельных инструкций языка, а правильной организации взаимодействия с Web Platform. Именно такой подход позволяет создавать приложения, которые остаются плавными и отзывчивыми даже при работе с большими объёмами данных и сложными пользовательскими интерфейсами.
