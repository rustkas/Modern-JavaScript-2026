# Часть VII. JavaScript и современные фреймворки

## Глава 26. Vue 3.6: новая реактивность и Vapor Mode

Vue 3.6 показывает важное направление развития современных JavaScript-фреймворков: оптимизация всё чаще переносится из runtime в компилятор, а реактивность становится более гранулярной.

При этом Vue 3.6 не превращается в «нативный JavaScript-фреймворк» и не использует стандартные Signals ECMAScript. Его реактивность остаётся частью самого Vue. В версии 3.6 команда проекта существенно переработала внутренний пакет `@vue/reactivity`, перенеся в него архитектурные идеи и оптимизации из `alien-signals`. Публичная модель Vue при этом сохраняет знакомые разработчикам API `ref()`, `computed()`, `watch()` и другие механизмы реактивности.

Второе крупное направление Vue 3.6 — **Vapor Mode**. Это альтернативная стратегия компиляции Single-File Components, которая позволяет отказаться от Virtual DOM для выбранных компонентов и генерировать код, работающий непосредственно с реальным DOM.

Таким образом, Vue 3.6 не заменяет одну архитектуру другой. Он предоставляет две модели рендеринга:

- традиционный **VDOM Mode**, использующий виртуальное дерево и существующую модель Vue;
- **Vapor Mode**, компилирующий компонент в более прямой и гранулярный DOM-ориентированный код.

Именно сочетание этих двух подходов является главным архитектурным изменением Vue 3.6.

## 26.1. Composition API: модульная организация логики

**Composition API** является основным способом организации переиспользуемой логики в современных приложениях на Vue 3.

Вместо разделения кода компонента на секции `data`, `methods`, `computed` и `watch`, разработчик группирует связанные операции в обычных JavaScript-функциях и composables.

**Пример создания composable:**

```javascript
import { ref, computed } from 'vue';

export function useCounter() {
  const count = ref(0);

  const doubled = computed(() => count.value * 2);

  function increment() {
    count.value++;
  }

  return {
    count,
    doubled,
    increment
  };
}
```

**Компонент может использовать эту логику без наследования, базовых классов или специальной иерархии компонентов:**

```javascript
import { useCounter } from './composables/useCounter';

export default {
  setup() {
    const { count, doubled, increment } = useCounter();

    return { count, doubled, increment };
  }
};
```

Такой подход особенно удобен для больших приложений, потому что бизнес-логику можно отделять от конкретного интерфейса и повторно использовать в нескольких компонентах.

### TypeScript

Composition API хорошо сочетается с TypeScript, поскольку composable представляет собой обычную типизированную функцию JavaScript/TypeScript.

**Пример с TypeScript:**

```typescript
import { ref, computed, Ref } from 'vue';

export function useCounter(initial: number = 0): {
  count: Ref<number>;
  increment: () => void;
  doubled: Ref<number>;
} {
  const count = ref(initial);

  const doubled = computed(() => count.value * 2);

  function increment() {
    count.value++;
  }

  return { count, increment, doubled };
}
```

Это позволяет определять типы входных параметров и возвращаемых значений непосредственно средствами TypeScript. В результате Vue не требует отдельной системы типов для Composition API: разработчик использует стандартные механизмы TypeScript поверх обычных функций и объектов JavaScript.

## 26.2. Реактивность Vue 3.6: `@vue/reactivity` и `alien-signals`

В Vue 3 реактивность строится вокруг dependency tracking: система отслеживает, какие вычисления зависят от реактивных данных, а затем повторно выполняет только необходимые вычисления после изменения этих данных.

**Базовые механизмы реактивности Vue:**

- **`ref()`** — создаёт реактивную ссылку на значение. Доступ к значению осуществляется через `.value`.

```javascript
const count = ref(0);
count.value = 10; // Триггерит обновление зависимостей
```

- **`reactive()`** — создаёт реактивную копию объекта. Все свойства объекта становятся реактивными.

```javascript
const state = reactive({ name: 'Vue', version: 3 });
state.name = 'Vue 3'; // Триггерит обновление
```

- **`computed()`** — создаёт производное значение, кеширующее результат и пересчитывающее его при изменении зависимостей.

```javascript
const doubled = computed(() => count.value * 2);
```

- **`watch()`** — отслеживает изменения реактивных источников и выполняет колбэк при их изменении.

```javascript
watch(count, (newVal, oldVal) => {
  console.log(`Count changed from ${oldVal} to ${newVal}`);
});
```

В Vue 3.6 внутренняя реализация `@vue/reactivity` была существенно переработана на основе архитектуры **`alien-signals`**. Согласно release notes, это изменение направлено прежде всего на повышение производительности реактивности и снижение потребления памяти.

### Vue Signals — не Signals ECMAScript

Vue 3.6 не получил какой-либо встроенный в JavaScript или браузер механизм Signals.

Конструкции `ref()`, `computed()`, `watch()`, `effect()` относятся к API Vue. Они используют собственную реализацию реактивности Vue, которая развивается независимо от предложения **TC39 Signals**. Наличие общего архитектурного понятия «сигнал» не означает, что Vue реализует уже стандартизированный примитив ECMAScript.

**Корректно говорить:**

> Vue использует современную сигналоподобную модель гранулярной реактивности.

**Некорректно говорить:**

> Vue 3.6 использует нативные ECMAScript Signals.

Это различие принципиально для книги о современном JavaScript: **паттерн может стать индустриальным стандартом задолго до того, как получит статус стандарта языка.**

## 26.3. Vapor Mode: рендеринг без Virtual DOM

**Vapor Mode** — альтернативная стратегия компиляции Vue Single-File Components.

В обычном режиме Vue компилирует шаблон в код, работающий с Virtual DOM. При изменении состояния Vue обновляет реактивные зависимости и выполняет необходимые операции обновления интерфейса через обычный rendering pipeline Vue.

Vapor Mode использует другую модель. Компилятор анализирует шаблон заранее и генерирует код, который работает непосредственно с реальными DOM-узлами. Virtual DOM для такого компонента не создаётся.

**Сравнение архитектур:**

```
Обычный Vue (VDOM Mode)
Template
   ↓
Vue Compiler (генерация render-функции)
   ↓
Render Function (создание VNode-дерева)
   ↓
Virtual DOM (виртуальное дерево)
   ↓
Diff/Patch (сравнение и обновление)
   ↓
DOM (реальный DOM)

Vapor Mode
Template
   ↓
Vue Compiler (анализ зависимостей)
   ↓
Direct DOM Operations (генерация кода обновления DOM)
   ↓
DOM (реальный DOM)
```

Это уменьшает количество runtime-работы, необходимой для обновления интерфейса, и позволяет компилятору заранее определить значительную часть структуры компонента.

**Пример компонента в Vapor Mode:**

```vue
<script setup>
import { ref } from 'vue';

const count = ref(0);
</script>

<template>
  <button @click="count++">
    {{ count }}
  </button>
</template>
```

Компилятор Vapor Mode анализирует, что `count` изменяется только при клике, и генерирует код, который при клике обновляет только текстовое содержимое кнопки, а не пересоздаёт весь компонент.

Официальные материалы Vue указывают две основные цели Vapor Mode: уменьшение baseline bundle size и повышение производительности. В сторонних бенчмарках режим демонстрировал результаты, сопоставимые с Solid и Svelte 5, однако такие результаты нельзя автоматически переносить на любое реальное приложение.

## 26.4. Vapor Mode не является полной заменой обычному Vue

Важнейшая архитектурная особенность Vapor Mode — **он не поддерживает весь API обычного Vue**.

На этапе Vue 3.6 RC официальная документация прямо указывает, что Vapor Mode поддерживает только подмножество существующих возможностей Vue.

**Что не поддерживается в Vapor Mode:**

- **Options API** — Vapor Mode рассчитан на компоненты, использующие `<script setup>`; Options API в этом режиме не поддерживается.
- **`app.config.globalProperties`** — глобальные свойства не доступны.
- **`getCurrentInstance()`** — нормальное использование не поддерживается.
- **`v-memo`** — директива для мемоизации не работает.
- **Component template refs** — часть возможностей ограничена.
- **Некоторые особенности, связанные с Virtual DOM** — поскольку Virtual DOM отсутствует.

**Что поддерживается в Vapor Mode:**

- `<script setup>` — основной способ написания компонентов.
- `ref()`, `computed()`, `reactive()` — все реактивные API.
- Базовые директивы — `v-if`, `v-for`, `v-bind`, `v-on`, `v-model`.
- Слоты — передача содержимого в компоненты.
- Композиция компонентов — импорт и использование других компонентов.

Поэтому Vapor Mode нельзя описывать как простой переключатель:

```
Vue → Vapor
```

Точнее говорить:

```
Vue Application
│
├── VDOM Components (обычные компоненты)
│
└── Vapor Components (компоненты, скомпилированные в Vapor Mode)
```

Vue 3.6 проектирует эти две модели как совместимые архитектурные варианты. При наличии interop-механизма Vapor-компоненты могут взаимодействовать с обычными VDOM-компонентами. Однако команда Vue рекомендует не строить чрезмерно сложные деревья, в которых два режима постоянно чередуются: на границах между ними существуют дополнительные ограничения и особенности.

## 26.5. Инкрементальное внедрение Vapor Mode

Практическое значение Vapor Mode заключается не только в его потенциальной производительности, но и в возможности **не переписывать существующее приложение целиком**.

Команда может оставить большую часть приложения в обычном VDOM-режиме и использовать Vapor Mode для новых или особенно чувствительных к производительности компонентов.

**Пример гибридного приложения:**

```
Application
│
├── Header             → VDOM (обычный режим)
├── Navigation         → VDOM (обычный режим)
├── ProductList        → Vapor (высокая производительность)
├── ProductCard        → Vapor (высокая производительность)
├── Checkout           → VDOM (сложная логика с ограничениями)
└── AnalyticsPanel     → VDOM (не критичен к производительности)
```

**Преимущества инкрементального внедрения:**

- **Постепенная миграция** — можно переводить компоненты по одному, без полной перестройки приложения.
- **Снижение рисков** — новый режим тестируется на ограниченном наборе компонентов.
- **Избирательная оптимизация** — Vapor Mode используется только там, где он даёт наибольший эффект.

Такой подход особенно полезен для больших приложений, где полная миграция на новую rendering architecture была бы слишком дорогой.

**Важно:** Vapor Mode не следует воспринимать как безусловную оптимизацию каждого компонента. Преимущество зависит от структуры интерфейса, количества обновлений, размера дерева, характера данных и стоимости самих DOM-операций.

## 26.6. Статус Vapor Mode в 2026 году

Для книги, описывающей именно **Modern JavaScript 2026**, статус технологии важнее маркетингового описания её возможностей.

На этапе `Vue 3.6.0-rc.2` Vapor Mode уже был объявлен feature-complete (функционально завершённым). Однако официальные release notes всё ещё характеризуют его как режим, который следует применять прежде всего:

- **частично в существующих приложениях** — например, на производительно-критичных страницах;
- **в небольших новых приложениях** — полностью построенных на Vapor Mode.

Это означает, что в 2026 году Vapor Mode следует рассматривать как **новую готовую к практическому экспериментированию архитектуру Vue, но не как обязательный стандарт для каждого production-приложения**.

Для книги это существенно точнее, чем утверждение «Vue 3.6 перешёл на Vapor Mode». Vue не отказался от Virtual DOM. Он сделал Virtual DOM **одним из двух доступных rendering pipelines**.

## 26.7. Архитектурное значение Vue 3.6

Vue 3.6 демонстрирует более общий сдвиг в современной разработке JavaScript.

Раньше основной вопрос звучал примерно так:

> Какой runtime должен выполнить мой код быстрее?

Современный подход всё чаще задаёт другой вопрос:

> Какую часть работы можно выполнить заранее во время компиляции?

Vapor Mode является примером именно такого переноса ответственности:

```
Runtime-centric architecture (рантайм-ориентированная)

Template
    ↓
Runtime (выполняется в браузере)
    ↓
VDOM (создание виртуального дерева)
    ↓
Diff (сравнение с предыдущим деревом)
    ↓
DOM (применение изменений)

Compiler-centric architecture (компилятор-ориентированная)

Template
    ↓
Compiler (анализирует зависимости на этапе сборки)
    ↓
Known dependencies (известные связи данных и DOM)
    ↓
Direct DOM operations (прямые операции обновления DOM)
```

Чем больше информации компилятор получает о структуре компонента и его зависимостях, тем меньше работы необходимо выполнять во время взаимодействия пользователя с приложением.

В этом отношении Vapor Mode находится в одном архитектурном направлении с другими компилируемыми подходами современного frontend-развития (Svelte, Solid), но сохраняет при этом модель компонентов и API Vue.

## Заключение

Vue 3.6 не превращает Vue в «нативную часть Web Platform» и не внедряет в него стандартизированные Signals ECMAScript. Его значение заключается в другом.

**Во-первых**, внутренняя реактивность Vue получила существенную переработку на основе `alien-signals`, направленную на повышение производительности и снижение потребления памяти. При этом публичная модель Vue остаётся совместимой с привычными механизмами `ref()`, `computed()` и другими API реактивности. `ref()` создаёт реактивные значения, `computed()` — производные значения, `watch()` — отслеживание изменений.

**Во-вторых**, Vapor Mode добавляет альтернативный компиляторный путь, позволяющий компонентам работать без Virtual DOM и обновлять DOM более непосредственно. Компилятор анализирует шаблоны на этапе сборки и генерирует код, который работает напрямую с DOM, минуя виртуальное дерево.

**В-третьих**, Vue не заставляет разработчика выбирать одну модель для всего приложения. Обычный VDOM и Vapor Mode могут сосуществовать, что делает постепенное внедрение новой архитектуры возможным. Компоненты в разных режимах могут взаимодействовать друг с другом, хотя на границах между ними существуют ограничения.

Поэтому главную идею Vue 3.6 лучше сформулировать так:

> **Современный фреймворк не обязательно должен становиться меньше. Он должен выполнять больше работы на этапе компиляции и оставлять runtime только ту работу, которую действительно невозможно выполнить заранее.**

Это важнее самого Vapor Mode. Vue 3.6 показывает направление развития современной JavaScript-архитектуры: **меньше работы во время выполнения, более точная реактивность, больше ответственности у компилятора и возможность выбирать rendering strategy для конкретной части приложения.**
