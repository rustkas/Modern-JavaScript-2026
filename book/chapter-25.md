# Часть VII. JavaScript и современные фреймворки

## Глава 25. Angular 2026: Signals, Zoneless и управление стоимостью интерфейса

Angular 2026 года заметно отличается от Angular предыдущих поколений. Фреймворк постепенно уменьшает количество глобальных механизмов, необходимых для обнаружения изменений, и переносит управление обновлениями ближе к конкретным данным и конкретным компонентам.

Главные элементы этой архитектуры:

- **Signals** — реактивные значения, которые позволяют Angular отслеживать зависимости компонентов;
- **OnPush** — модель, ограничивающая ненужные проверки поддеревьев;
- **Zoneless Change Detection** — обнаружение изменений без зависимости от `Zone.js`;
- **SSR и hydration** — серверный рендеринг с последующим восстановлением интерактивности;
- **Incremental Hydration** — постепенная гидратация отдельных частей страницы;
- **Deferrable Views (`@defer`)** — декларативная загрузка кода только тогда, когда он действительно нужен.

В результате Angular движется от модели «фреймворк периодически проверяет приложение» к модели:

> **данные изменились → Angular знает, какие компоненты затронуты → обновляется только необходимая часть приложения.**

При этом Angular не превращается в часть JavaScript или Web Platform. Signals, шаблонный синтаксис, dependency injection и система change detection остаются механизмами Angular. Фреймворк лишь всё активнее использует стандартные возможности браузера и JavaScript вместо глобальных перехватов и избыточных проверок.

## 25.1. Angular Signals: гранулярная реактивность фреймворка

Signals — центральный механизм современной реактивности Angular.

**Базовые примитивы Angular:**

```javascript
const count = signal(0);

const doubled = computed(() => count() * 2);

effect(() => {
  console.log(count());
});
```

- **`signal(value)`** — создаёт реактивное значение. У сигнала есть текущее значение, которое можно прочитать вызовом `signal()`. Чтение сигнала регистрирует зависимость, а изменение значения (`signal.set(newValue)`) уведомляет связанные с ним потребители.

- **`computed(fn)`** — создаёт производное значение. `computed` кеширует результат и пересчитывает его только тогда, когда изменяются зависимости.

```javascript
const price = signal(100);
const quantity = signal(3);
const total = computed(() => price() * quantity());
// total = 300
price.set(120);
// total автоматически пересчитывается в 360
```

`total` зависит от `price` и `quantity`. Если изменяется `price`, Angular знает, что результат `total` потенциально изменился.

- **`effect(fn)`** — предназначен для выполнения побочных действий, зависящих от сигналов. Angular автоматически отслеживает сигналы, прочитанные во время выполнения эффекта.

```javascript
effect(() => {
  console.log(`Current total: ${total()}`);
});
// Выводится при каждом изменении total
```

### Signals не являются частью ECMAScript

Это важнейшее архитектурное различие.

Angular Signals — **framework-specific API**:

```javascript
signal()
computed()
effect()
```

не являются конструкциями языка JavaScript и не определяются спецификацией ECMA-262.

Параллельно TC39 обсуждает отдельное предложение Signals. Его задача — потенциально создать общий языковой примитив реактивности, который в будущем смогут использовать разные фреймворки и библиотеки.

Но эти два факта нельзя смешивать:

```
Angular Signals
      │
      └── готовая реализация Angular

TC39 Signals proposal
      │
      └── предложение стандартизировать общий примитив
```

Если TC39 когда-либо доведёт своё предложение до ECMAScript Standard, это ещё не означает автоматического превращения существующего Angular API в стандарт JavaScript.

Поэтому в книге следует называть Angular Signals **нативной реактивностью Angular**, но не **нативной реактивностью JavaScript**.

### Signals и компоненты

Когда Angular-компонент читает сигнал в шаблоне, Angular фиксирует эту зависимость. При изменении сигнала компонент получает уведомление и может быть обновлён при следующем цикле change detection.

```angular
@Component({
  template: `<div>{{ count() }}</div>`
})
export class MyComponent {
  count = signal(0);
}
```

Это особенно важно для OnPush-компонентов.

Вместо абстрактной проверки всего приложения Angular получает конкретную информацию:

```
signal
  │
  ▼
component template reads signal
  │
  ▼
Angular records dependency
  │
  ▼
signal changes
  │
  ▼
component is marked for update
```

Таким образом, Signals становятся фундаментом для перехода Angular к более адресной модели обновления.

## 25.2. Signals + OnPush: переход от проверки дерева к адресным уведомлениям

Signals наиболее эффективно раскрываются вместе с `OnPush`.

В старой модели change detection фреймворк мог выполнять большое количество проверок, даже если фактически изменился только небольшой участок приложения.

`OnPush` ограничивает область автоматических проверок компонента. Компонент с `OnPush` проверяется только в определённых случаях: изменяются его `@Input()`, возникает событие внутри компонента, или вызывается `markForCheck()`.

Signals дополняют эту модель информацией о зависимостях.

Если шаблон компонента читает:

```javascript
count()
```

Angular знает, что компонент зависит от `count`.

Когда значение меняется, Angular может пометить соответствующий компонент для обновления.

Получается архитектурная цепочка:

```
Signal
   │
   ▼
Dependency tracking
   │
   ▼
OnPush component marked
   │
   ▼
Targeted change detection
```

Это не означает, что Angular буквально обновляет один DOM-узел и никогда не проверяет ничего вокруг него. Правильнее говорить, что Signals позволяют Angular **точнее определять, какие части component tree необходимо обновить**.

Такое уточнение важно: гранулярность Signals не следует путать с архитектурой полностью независимых DOM-узлов, характерной для некоторых signal-based UI-систем (например, Solid.js).

## 25.3. Zoneless: Angular больше не должен следить за всеми асинхронными операциями

`Zone.js` исторически позволял Angular обнаруживать асинхронную активность через перехват API браузера.

Упрощённо модель выглядела так:

```
setTimeout()
Promise
DOM event
XHR
   │
   ▼
Zone.js (monkey-patching)
   │
   ▼
Angular change detection
```

Это было удобно: разработчику не требовалось явно сообщать Angular о каждом изменении состояния.

Но такой подход имел архитектурную цену:

- `Zone.js` изменяет поведение глобальных API посредством monkey-patching (заменяет нативные методы браузера своими обёртками).
- Не каждый асинхронный механизм можно эффективно перехватить таким способом.
- Angular прямо указывает, что некоторые API, включая `async`/`await`, не могут быть эффективно обработаны ZoneJS без дополнительного преобразования кода.

**Современный Angular использует другой подход:**

```
Application state changes
        │
        ▼
Angular notification (через сигналы, события, input)
        │
        ▼
Change detection (только затронутые компоненты)
```

Фреймворк получает уведомление непосредственно от механизмов Angular, а не через глобальный перехват асинхронных операций.

## 25.4. Zoneless стал стандартной моделью Angular

`provideZonelessChangeDetection()` получил статус **stable в Angular 20.2**. Начиная с Angular 21, zoneless change detection включён по умолчанию.

Для нового приложения поэтому больше не требуется специально включать zoneless:

```javascript
bootstrapApplication(AppComponent);
```

Angular использует zoneless-поведение по умолчанию, если приложение не переопределяет его через `provideZoneChangeDetection`.

**Angular запускает change detection в ответ на конкретные уведомления, включая:**

- изменение сигнала, прочитанного в шаблоне;
- `ChangeDetectorRef.markForCheck()`;
- изменение input через `ComponentRef.setInput()`;
- выполнение template или host listener;
- присоединение view, которая была помечена как dirty;
- удаление view;
- определённые render hooks.

Таким образом, Angular больше не должен рассуждать следующим образом:

> «Что-то асинхронное произошло. Возможно, состояние изменилось. Проверю приложение».

Вместо этого используется модель:

> «Angular получил уведомление об изменении. Проверю связанные с ним части приложения».

### Что происходит с ZoneJS в существующих проектах

Переход не является автоматическим удалением `Zone.js` из всех старых приложений.

Angular 21 делает zoneless поведением по умолчанию для новых приложений, но существующие приложения могут продолжать использовать ZoneJS. Для полноценного перехода Angular рекомендует удалить `zone.js` из build и testing configuration, если приложение действительно переводится на zoneless.

Поэтому миграция существующего крупного приложения остаётся инженерной задачей, требующей поэтапного подхода.

## 25.5. Почему Zoneless важен для архитектуры

Преимущество Zoneless заключается не просто в уменьшении размера бандла (исключение ZoneJS экономит ~30-50KB).

Главное изменение — **изменяется модель ответственности за обновление интерфейса**.

ZoneJS создавал глобальную связь:

```
any async activity
       ↓
ZoneJS (monkey-patching)
       ↓
Angular (полная проверка приложения)
```

Zoneless строит более адресную связь:

```
state / input / event
       ↓
Angular notification (конкретное уведомление)
       ↓
relevant view (только затронутые компоненты)
```

**Архитектурные преимущества:**

1. **Меньше глобального вмешательства** — Angular больше не должен изменять глобальное поведение браузерных API через ZoneJS.

2. **Более понятные причины обновления** — изменение состояния связано с конкретным Angular-механизмом, который вызвал уведомление.

3. **Лучшее взаимодействие с современным JavaScript** — приложение меньше зависит от того, насколько хорошо сторонний API совместим с monkey-patching.

Angular прямо связывает удаление ZoneJS с уменьшением сложности, устранением monkey-patching и улучшением долгосрочной совместимости с экосистемой.

Поэтому переход к Zoneless следует рассматривать прежде всего как **архитектурное изменение механизма реактивности**, а не как небольшую оптимизацию размера JavaScript.

## 25.6. SSR: HTML сначала, JavaScript потом

Современный Angular активно использует серверный рендеринг (SSR).

Сервер может выполнить Angular-приложение и передать браузеру уже сформированный HTML:

```
Server
  │
  │ Angular render (на сервере)
  ▼
HTML (полная страница)
  │
  ▼
Browser (получает готовый HTML)
  │
  │ hydration (восстановление интерактивности)
  ▼
Interactive Angular application
```

Это позволяет браузеру получить содержимое страницы до того, как весь клиентский JavaScript будет загружен и выполнен.

**Различие между SSR и hydration:**

- **SSR** создаёт HTML на сервере.
- **Hydration** связывает уже существующий HTML с клиентским Angular-кодом (восстанавливает обработчики событий, состояние компонентов).
- **Incremental Hydration** позволяет выполнять эту работу постепенно, а не для всей страницы сразу.

---

## 25.7. Incremental Hydration: не оживлять всю страницу сразу

Полная hydration может быть дорогой для больших приложений. Если страница содержит множество независимых компонентов, нет необходимости обязательно делать все части интерактивными одновременно.

**Структура страницы с инкрементальной гидратацией:**

```
Initial HTML (полная разметка с сервера)
│
├── Header             hydrated (немедленно)
├── Article            hydrated (немедленно)
├── Comments           dehydrated (отложена)
└── Recommendations    dehydrated (отложена)
                         │
                         ▼
                    user interaction
                    (скролл к комментариям)
                         │
                         ▼
                    hydration (подгрузка JavaScript и восстановление)
```

Incremental Hydration позволяет оставить некоторые участки приложения dehydrated и гидратировать их тогда, когда они действительно нужны. Angular описывает эту возможность как расширение обычной hydration, позволяющее уменьшить начальный объём JavaScript и отложить активацию отдельных частей страницы.

Это особенно интересно в сочетании с `@defer`.

Таким образом, Angular может доставить пользователю полноценный HTML, но не заставлять браузер немедленно выполнять весь JavaScript страницы.

## 25.8. Deferrable Views: `@defer` как декларативный code splitting

`@defer` позволяет описывать отложенную загрузку прямо в Angular template:

```angular
@defer {
  <comments />
}
```

Angular выделяет код компонентов, директив и pipes внутри defer-блока в отдельный JavaScript-файл (chunk) и загружает его только после наступления заданного условия.

Это отличается от ручного:

```javascript
import('./comments.js');
```

Разработчик описывает **условие загрузки**, а Angular и его сборочная система решают, какой код должен оказаться в отдельном chunk.

### Основные триггеры

Angular поддерживает:

```
idle — загрузить, когда браузер простаивает
viewport — загрузить, когда элемент попадает в область просмотра
interaction — загрузить при взаимодействии пользователя
hover — загрузить при наведении курсора
immediate — загрузить сразу после гидратации
timer(5s) — загрузить через указанное время
when(condition) — загрузить при выполнении условия
```

**Примеры:**

```angular
@defer (on viewport) {
  <comments />
}
```

означает: загрузить компонент, когда соответствующий элемент попадёт в область просмотра.

Для `viewport` Angular использует `IntersectionObserver`. Для idle-триггера используется механизм определения состояния простоя браузера (requestIdleCallback).

```angular
@defer (on interaction) {
  <heavy-editor />
}
```

Компонент редактора не требуется загружать, пока пользователь не начнёт с ним взаимодействовать.

### Placeholder, loading и error

`@defer` поддерживает несколько состояний, позволяющих декларативно описать весь жизненный цикл отложенного фрагмента:

```angular
@defer (on viewport) {
  <comments />
}
@placeholder {
  <p>Comments will appear here</p>
}
@loading {
  <p>Loading comments...</p>
}
@error {
  <p>Could not load comments.</p>
}
```

- **Placeholder** — отображается до начала загрузки.
- **Loading** — отображается во время загрузки.
- **Error** — отображается при ошибке загрузки.

### Prefetching

Angular также позволяет отделить **загрузку кода** от **его отображения**.

Например, браузер может заранее загрузить chunk, пока пользователь ещё не взаимодействовал с компонентом:

```angular
@defer (on interaction; prefetch on idle) {
  <editor />
}
```

Получается двухэтапная модель:

```
idle (браузер простаивает)
 │
 └── prefetch JavaScript (загрузка в фоне)

user interaction (пользователь кликает)
 │
 └── render component (мгновенное отображение, код уже загружен)
```

Это позволяет уменьшить задержку в момент фактического взаимодействия.

## 25.9. `@defer` и Core Web Vitals: оптимизация не гарантирует улучшение

Deferrable Views уменьшают размер начального JavaScript и могут улучшить начальную загрузку и Core Web Vitals. Angular прямо указывает на возможное улучшение LCP и TTFB.

**Однако `@defer` нельзя использовать механически.**

Если отложить компонент, который должен быть виден пользователю сразу, появление его содержимого может вызвать layout shift (изменение макета), что негативно влияет на CLS (Cumulative Layout Shift).

Angular поэтому рекомендует не откладывать элементы, находящиеся в первоначальном viewport, без необходимости и правильно проектировать placeholder, чтобы сохранять место под будущее содержимое.

**Следовательно:** `@defer` — не «ускоритель страницы», а инструмент управления моментом загрузки JavaScript. Его эффективность зависит от того, **какой код откладывается, когда он нужен пользователю и что показывается до его загрузки**.

## 25.10. Signals + Zoneless + `@defer`: единая архитектура Angular 2026

Три механизма особенно хорошо показывают направление развития Angular.

**Signals** — управляют зависимостями данных:

```
state (данные приложения)
 │
 ▼
Signal (реактивное значение)
 │
 ▼
dependent component (компонент, использующий сигнал)
```

**Zoneless** — управляет моментом запуска change detection:

```
Angular notification (уведомление об изменении)
 │
 ▼
change detection (только затронутые компоненты)
```

**`@defer`** — управляет моментом доставки JavaScript:

```
trigger (условие загрузки)
 │
 ▼
download chunk (загрузка JavaScript)
 │
 ▼
render component (отображение компонента)
```

Вместе они образуют единую модель:

```
             Application state (состояние приложения)
                    │
                    ▼
                 Signals (реактивность)
                    │
                    ▼
              affected views (определение затронутых компонентов)
                    │
                    ▼
              Zoneless CD (change detection только для них)
                    │
                    ▼
             render what changed (обновление DOM)

             @defer controls what
             code arrives when (управление загрузкой кода)
                    │
                    ▼
             smaller initial JavaScript (меньше начального кода)
```

Это гораздо более важная архитектурная тенденция, чем отдельное появление каждого API.

Angular постепенно разделяет три разные задачи:

1. **Что изменилось** — Signals.
2. **Что необходимо обновить** — change detection (Zoneless).
3. **Какой код вообще должен быть загружен сейчас** — `@defer`.

## 25.11. Angular 2026 и Web Platform

Современный Angular не заменяет браузерные API. Он использует их как фундамент:

- **HTML** — структура документа.
- **CSS** — визуальное представление.
- **DOM** — интерфейс документа.
- **Fetch** — сетевые запросы.
- **Streams** — потоковые данные.
- **`IntersectionObserver`** — определение появления элементов в viewport (используется в `@defer (on viewport)`).
- **Browser scheduling** — выполнение задач в подходящие моменты (используется в `@defer (on idle)`).

`@defer` особенно хорошо демонстрирует эту модель: Angular предоставляет декларативный API, а браузер выполняет низкоуровневую работу через стандартные механизмы Web Platform. Например, viewport-триггер основан на `IntersectionObserver`, idle-триггер — на `requestIdleCallback`.

Поэтому современный Angular следует понимать не как альтернативу Web Platform, а как **архитектурный слой, который координирует JavaScript, шаблоны, DOM и браузерные API**.

## 25.12. Что действительно изменилось в Angular

Основной переход Angular 2026 года можно выразить следующим образом.

### Старый подход (Angular до 20)

```
Browser activity (любая асинхронная операция)
       │
       ▼
    ZoneJS (monkey-patching)
       │
       ▼
Change Detection (полная проверка)
       │
       ▼
Check application (проверить всё приложение)
```

### Современный подход (Angular 21+)

```
State / input / event (конкретное изменение)
       │
       ▼
Angular notification (уведомление)
       │
       ▼
Relevant component tree (только затронутые компоненты)
       │
       ▼
DOM update (обновление только необходимых частей)
```

И параллельно:

```
Application code (код приложения)
       │
       ▼
      @defer (декларативное разделение)
       │
       ▼
split JavaScript (разделение на чанки)
       │
       ▼
load when necessary (загрузка по требованию)
```

А для SSR:

```
Server (сервер)
  │
  ▼
HTML (полный HTML)
  │
  ▼
partial / incremental hydration (частичная гидратация)
  │
  ▼
interactive application (интерактивное приложение)
```

Таким образом, Angular оптимизирует не только скорость выполнения JavaScript. Он управляет **тем, когда код загружается, когда он выполняется и какие части интерфейса действительно требуют обновления**.

## Заключение

Angular 2026 года нельзя описывать просто как «старый Angular без ZoneJS». Изменился сам принцип организации приложения.

**Signals** дают Angular информацию о зависимостях между состоянием и интерфейсом. `computed()` создаёт производные значения, `effect()` выполняет побочные действия. Signals не являются частью ECMAScript — это framework-specific API Angular.

**OnPush** позволяет ограничивать область проверки компонентов, а Signals дополняют эту модель, отмечая компоненты для обновления при изменении зависимостей.

**Zoneless** устраняет необходимость глобального отслеживания асинхронной активности через `Zone.js` и переводит запуск change detection на конкретные уведомления Angular. В Angular 21+ эта модель используется по умолчанию.

**SSR и hydration** разделяют генерацию HTML и последующее включение интерактивности. **Incremental Hydration** позволяет активировать части приложения постепенно.

**`@defer`** позволяет контролировать, когда браузер вообще должен загрузить JavaScript определённого компонента, используя триггеры: viewport, interaction, idle, hover, timer.

Именно это является главным архитектурным изменением:

> **Angular всё меньше пытается постоянно проверять всё приложение и всё больше пытается точно определить, что изменилось, что необходимо обновить и какой код действительно нужен пользователю прямо сейчас.**

При этом Angular Signals нельзя называть частью ECMAScript, а Zoneless нельзя сводить только к «уменьшению бандла». В первом случае речь идёт о собственной реактивной модели Angular; во втором — о фундаментальном изменении механизма change detection.

Для инженера 2026 года знание Angular поэтому означает не только знание его template syntax и DI. Необходимо понимать **реактивность, стоимость change detection, браузерное планирование, SSR, hydration, code splitting и Web Platform API**, потому что именно на пересечении этих механизмов строится современное Angular-приложение.
