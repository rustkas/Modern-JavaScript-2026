# Часть V. Производительность

## Глава 19. Современная память: слабые ссылки, сборка мусора и управление временем жизни

В JavaScript память управляется автоматически: разработчик создаёт объекты, а движок определяет, какие из них больше недостижимы для программы и могут быть удалены сборщиком мусора (*Garbage Collector*). Код JavaScript не управляет конкретным моментом освобождения памяти напрямую.

Современный JavaScript предоставляет несколько механизмов, позволяющих описывать отношение объектов к сборке мусора: `WeakMap`, `WeakSet`, `WeakRef` и `FinalizationRegistry`. Они не заменяют обычное управление состоянием и не превращают сборку мусора в детерминированный процесс. Их назначение значительно точнее: позволить хранить метаданные, строить необязательные кеши и выполнять дополнительную очистку объектов, не удерживая их от сборки мусора.

Главный принцип этой главы прост:

> **слабая ссылка позволяет объекту исчезнуть из памяти, но не позволяет программе управлять моментом его исчезновения.**

## 19.1. `WeakMap` и `WeakSet`: данные, не продлевающие жизнь объектов

`WeakMap` и `WeakSet` предназначены для ситуаций, когда служебные данные должны существовать только пока существует соответствующий объект.

### `WeakMap`

`WeakMap` хранит пары «ключ — значение», но ключ удерживается слабой ссылкой. Ключом может быть объект или **незарегистрированный символ**, созданный через `Symbol()`.

```javascript
const metadata = new WeakMap();

const button = document.querySelector('button');

metadata.set(button, {
  clicks: 0,
  createdAt: Date.now()
});
```

Если `button` больше нигде не доступен программе, запись, связанная с ним через `WeakMap`, больше не должна препятствовать сборке этого объекта.

Это особенно полезно для библиотек и инфраструктурного кода, который добавляет собственные метаданные к чужим объектам:

```javascript
const cache = new WeakMap();

function getMetadata(object) {
  let data = cache.get(object);

  if (!data) {
    data = createMetadata(object);
    cache.set(object, data);
  }

  return data;
}
```

Такой кеш не требует ручного удаления записи одновременно с удалением объекта.

`WeakMap` намеренно **не является итерируемым**. У него нет `keys()`, `values()` или `entries()`. Это принципиальное свойство API: результат перечисления зависел бы от того, успел ли сборщик мусора удалить отдельные объекты, а момент сборки мусора не является детерминированным.

**Доступные методы:**

- `set(key, value)` — добавляет или обновляет запись.
- `get(key)` — возвращает значение или `undefined`.
- `has(key)` — проверяет существование ключа.
- `delete(key)` — удаляет запись.

### Незарегистрированные и зарегистрированные символы

В современном JavaScript ключом `WeakMap` может быть не только объект, но и незарегистрированный символ:

```javascript
const key = Symbol('cache-key');

const map = new WeakMap();

map.set(key, 'data');
```

При этом символ, созданный через `Symbol.for()`, использовать нельзя:

```javascript
const key = Symbol.for('cache-key');

const map = new WeakMap();

map.set(key, 'data'); // TypeError: WeakMap key must be an object or an unregistered symbol
```

Причина связана с глобальным реестром символов. `Symbol.for()` возвращает зарегистрированный символ, который имеет постоянную идентичность через глобальный реестр и поэтому не подходит для слабого удержания. В спецификации это выражено через абстрактную операцию `CanBeHeldWeakly`. Незарегистрированные символы не имеют глобальной идентичности и могут быть собраны, когда на них нет ссылок.

### Новые методы `WeakMap` в 2026 году

Современный `WeakMap` получил удобные операции ленивой инициализации:

```javascript
const cache = new WeakMap();

// Метод getOrInsert — если ключ существует, возвращает значение,
// если нет — сохраняет переданное значение и возвращает его
const value = cache.getOrInsert(object, defaultValue);

// Метод getOrInsertComputed — для дорогого вычисления значения
// Функция вызывается только тогда, когда записи для ключа ещё нет
const value = cache.getOrInsertComputed(
  object,
  () => createExpensiveValue(object)
);
```

Здесь стоит быть точнее в формулировке статуса. Предложение (изначально известное как Upsert, до этого рассматривались названия `emplace` и `upsert`) достигло Stage 4 на заседании TC39 в январе 2026 года и вошло в стандарт ES2026 — как для `Map`, так и для `WeakMap`. Реализации появились в браузерах практически сразу: Chrome 145, Firefox 144/148, Safari 18.4. Тем не менее статус Baseline для этих методов — **Newly Available с февраля 2026 года**, а не Widely Available: возможность стала кросс-браузерной совсем недавно, и версии браузеров ниже указанных её не поддерживают. Поэтому для проектов, которым необходима поддержка чуть более старых версий браузеров (что при выпуске книги — обычная практика), стоит либо проверять актуальную статистику использования нужных версий, либо подключать полифил (например, из core-js, где методы доступны начиная с версии, добавленной по итогам январского заседания TC39 2026 года), а не считать возможность безусловно доступной «во всех современных браузерах».


### `WeakSet`

`WeakSet` хранит набор объектов или незарегистрированных символов без сильного удержания этих значений:

```javascript
const processed = new WeakSet();

function process(object) {
  if (processed.has(object)) {
    return;
  }

  processed.add(object);

  // обработка объекта
}
```

`WeakSet` удобно использовать для отметки состояния объектов, когда сама отметка не должна продлевать их время жизни. Например, для отслеживания уже обработанных DOM-элементов или предотвращения повторной инициализации объектов.

Как и `WeakMap`, `WeakSet` не предоставляет перечисления элементов. Программа может проверить наличие конкретного значения, но не может получить список всех ещё живых элементов.

**Доступные методы:**

- `add(value)` — добавляет значение.
- `has(value)` — проверяет существование значения.
- `delete(value)` — удаляет значение.

## 19.2. `WeakRef`: ссылка, которая не удерживает объект

`WeakRef` позволяет сохранить ссылку на объект, не препятствуя его сборке мусора.

```javascript
const object = createLargeObject();
const reference = new WeakRef(object);
```

Получить объект можно методом `deref()`:

```javascript
const value = reference.deref();

if (value !== undefined) {
  use(value);
}
```

Если объект всё ещё доступен, `deref()` возвращает его. Если сборщик мусора уже освободил объект, результатом становится `undefined`.

Это делает `WeakRef` подходящим инструментом для **необязательных кешей**:

```javascript
const cache = new Map();

function getCached(key) {
  return cache.get(key)?.deref();
}

function setCached(key, value) {
  cache.set(key, new WeakRef(value));
}

// Использование
const user = getCached('user:123');
if (user !== undefined) {
  // Объект ещё жив, используем его
} else {
  // Объект собран, пересоздаём
  const newUser = fetchUser('123');
  setCached('user:123', newUser);
}
```

Такой кеш может содержать ссылки на большие объекты, но не обязан удерживать их в памяти только ради возможности повторного использования.

### `deref()` не является проверкой состояния сборщика мусора

Нельзя использовать `WeakRef` как механизм синхронизации:

```javascript
if (reference.deref() === undefined) {
  // нельзя считать это гарантированным событием
  // сборка мусора могла произойти, но не обязана
}
```

JavaScript не сообщает программе, когда именно объект будет собран. На это влияют реализация движка, объём доступной памяти, текущая нагрузка и другие внутренние обстоятельства.

Спецификация также обеспечивает определённую согласованность наблюдения внутри одной выполняемой задачи: если успешный `deref()` получил объект, последующие обращения к той же слабой ссылке в пределах этой задачи не должны неожиданно потерять этот объект из-за сборки мусора в середине выполнения. Это позволяет безопасно работать с результатом `deref()` внутри текущей операции.

Практическое правило значительно проще:

> **`WeakRef` подходит для оптимизации, но не для корректности программы.**

Если программа обязана выполнить действие в определённый момент, `WeakRef` для этого не подходит.

## 19.3. `FinalizationRegistry`: уведомление после сборки мусора

`FinalizationRegistry` позволяет зарегистрировать объект и получить уведомление после того, как объект станет недостижимым и будет собран сборщиком мусора.

```javascript
const registry = new FinalizationRegistry((heldValue) => {
  console.log(`Объект с идентификатором ${heldValue} был собран`);
});

const object = {};
registry.register(object, 'object-42');
```

Второй аргумент — `heldValue`. Это значение передаётся callback-функции после финализации объекта. `heldValue` не является слабой ссылкой — это обычное значение, которое хранится в реестре.

**Несколько объектов с разными heldValue:**

```javascript
const registry = new FinalizationRegistry((id) => {
  console.log(`Object ${id} was collected`);
});

const user = { name: 'Alice' };
const config = { theme: 'dark' };

registry.register(user, 'user-alice');
registry.register(config, 'config-dark');
```

**Отмена регистрации:**

При необходимости регистрацию можно отменить с помощью `unregister()`. Для этого при регистрации передаётся третий аргумент — **unregistration token** (обычно сам объект):

```javascript
const object = {};
const token = {};

registry.register(object, 'object-42', token);

// Если объект больше не нужно отслеживать
registry.unregister(token);
```

Unregistration token может быть любым объектом. При вызове `unregister(token)` удаляются все регистрации, связанные с этим токеном.

### Когда callback будет вызван?

Точного ответа нет. JavaScript **не гарантирует**, что callback будет вызван сразу после того, как объект станет недостижимым. Более того, спецификация не гарантирует, что callback будет вызван вообще. Если процесс завершится раньше, чем сборщик мусора и механизм финализации успеют выполнить необходимые действия, callback не запустится.

**Факторы, влияющие на время вызова:**

- Реализация сборщика мусора в конкретном движке (V8, JavaScriptCore, SpiderMonkey).
- Доступный объём памяти — при нехватке памяти сборка может происходить чаще.
- Текущая нагрузка на систему и браузер.
- Настройки оптимизации движка (например, в Node.js можно настроить параметры GC).

Поэтому следующий код архитектурно неверен:

```javascript
const registry = new FinalizationRegistry(() => {
  closeFile(); // ❌ Не должно зависеть от GC
});
registry.register(fileHandle, 'file');
```

если закрытие файла является обязательным условием корректности программы.

`FinalizationRegistry` может использоваться только как дополнительный механизм очистки, когда пропуск или задержка очистки не нарушает корректность приложения.

**Пример допустимого использования — очистка кеша:**

```javascript
const cache = new Map();
const registry = new FinalizationRegistry((key) => {
  // Очистка кеша после сборки объекта
  cache.delete(key);
});

function cacheObject(key, object) {
  cache.set(key, object);
  registry.register(object, key);
}
```

Здесь если объект собран, кеш очищается, но если объект не собран, кеш продолжает работать. Это не нарушает корректность приложения — просто может временно хранить больше данных.

Для обязательного освобождения ресурсов нужен детерминированный механизм:

```javascript
// Использование с гарантированным освобождением
const resource = acquireResource();
try {
  useResource(resource);
} finally {
  releaseResource(resource);
}
```

`try...finally` гарантирует выполнение блока `finally` при завершении текущей операции, тогда как `FinalizationRegistry` такой гарантии не предоставляет.

## 19.4. Сильные и слабые ссылки: главное различие

Чтобы правильно выбирать между `Map` и `WeakMap`, а также между обычными ссылками и `WeakRef`, необходимо различать **сильное** и **слабое** удержание.

Обычная ссылка является сильной:

```javascript
const object = {};
const map = new Map();

map.set(object, 'data');
```

Пока `map` доступен программе, его ключ продолжает быть частью графа достижимых объектов. Само наличие ключа в `Map` препятствует его сборке. Даже если переменная `object` будет удалена, объект продолжит существовать, потому что он находится в `Map`.

`WeakMap` работает иначе:

```javascript
const object = {};
const map = new WeakMap();

map.set(object, 'data');
```

Наличие записи в `WeakMap` само по себе не должно препятствовать сборке ключа. Если переменная `object` будет удалена, объект может быть собран, и запись из `WeakMap` исчезнет.

`WeakRef` идёт ещё дальше: программа получает возможность непосредственно хранить слабую ссылку и попытаться получить объект через `deref()`.

Эти механизмы можно представить следующим образом:

| Механизм               | Удерживает объект от GC? | Можно перечислить элементы? | Основное назначение                         |
| ---------------------- | -----------------------: | --------------------------: | ------------------------------------------- |
| `Map`                  |                       Да |                          Да | Обычное хранение данных                     |
| `Set`                  |                       Да |                          Да | Обычное множество объектов                  |
| `WeakMap`              |           Нет для ключей |                         Нет | Метаданные и привязанные кеши               |
| `WeakSet`              |                      Нет |                         Нет | Слабая маркировка объектов                  |
| `WeakRef`              |                      Нет |                Не применимо | Необязательные ссылки и кеши                |
| `FinalizationRegistry` |           Нет для target |                Не применимо | Необязательная пост-финализационная очистка |

Главное различие заключается не в том, что `WeakMap` или `WeakRef` «управляют памятью». Они лишь **не мешают сборщику мусора принимать собственные решения**.

## 19.5. Что действительно означает «объект жив»

Для практического программирования объект следует считать живым, если выполнение программы всё ещё может получить к нему доступ через сильные ссылки.

**Пример достижимости:**

```javascript
let user = {
  name: 'Alice',
  address: {
    city: 'Moscow'
  }
};
```

Пока переменная `user` доступна и содержит ссылку на объект, объект достижим. Объект `address` также достижим, потому что на него ссылается `user`.

После:

```javascript
user = null;
```

если других сильных ссылок на объект нет, он становится кандидатом на сборку мусора. Объект `address` также становится недостижимым, поскольку на него больше нет ссылок.

При этом наличие `WeakRef` не делает объект живым:

```javascript
let user = {
  name: 'Alice'
};

const reference = new WeakRef(user);

user = null;
```

Теперь `reference` может существовать, но объект всё равно может быть собран, потому что `WeakRef` не является сильной ссылкой.

**Сборка мусора не детерминирована:** Между `user = null` и фактической сборкой объекта может пройти время, и `reference.deref()` может возвращать объект в течение некоторого периода после удаления сильной ссылки.

Именно поэтому программа не должна строить корректность своего поведения на предположении, что объект обязательно будет существовать или обязательно исчезнет в определённый момент.

## 19.6. Практическая архитектура управления памятью

Современный JavaScript следует использовать в соответствии с назначением каждого механизма.

### Используйте `Map` и `Set`, когда данные должны жить явно

Если запись должна существовать до тех пор, пока программа сама её не удалит, используйте обычные коллекции:

```javascript
const cache = new Map();

cache.set(id, value);

// Когда данные больше не нужны:
cache.delete(id);
```

Это предсказуемая модель, и разработчик явно управляет временем жизни данных.

### Используйте `WeakMap`, когда данные принадлежат объекту

Если служебная информация имеет смысл только вместе с конкретным объектом, `WeakMap` часто является естественным выбором:

```javascript
const state = new WeakMap();

function initialize(element) {
  state.set(element, {
    initialized: true,
    listeners: []
  });
}

function addListener(element, listener) {
  const s = state.get(element);
  if (s) {
    s.listeners.push(listener);
  }
}
```

Удаление `element` из основной архитектуры не требует отдельного удаления его служебной записи — она исчезнет автоматически.

### Используйте `WeakRef`, когда отсутствие значения допустимо

`WeakRef` подходит для кешей, где объект можно пересоздать:

```javascript
const cache = new Map();

function getData(key) {
  const ref = cache.get(key);
  const cached = ref?.deref();
  
  if (cached !== undefined) {
    return cached;
  }
  
  const fresh = fetchData(key);
  cache.set(key, new WeakRef(fresh));
  return fresh;
}
```

Если объект исчез, приложение должно продолжить работу без него, пересоздав данные при необходимости.

### Используйте `FinalizationRegistry` только для необязательной очистки

Финализация подходит для вспомогательных операций, диагностики и оптимизации памяти:

```javascript
const registry = new FinalizationRegistry((name) => {
  console.log(`[DEBUG] Object ${name} collected`);
});

// Для отладки утечек памяти
registry.register(largeObject, 'LargeObject');
```

Она не должна быть единственным механизмом закрытия обязательных ресурсов — для этого используйте явные конструкции вроде `try...finally`.

## 19.7. Главный принцип Modern JavaScript 2026

Современная модель памяти JavaScript не предоставляет разработчику ручного управления сборщиком мусора. Вместо этого язык позволяет описывать **силу связи между объектами**.

`Map` и `Set` создают обычные сильные связи — объекты не будут собраны, пока они есть в коллекции. `WeakMap` и `WeakSet` позволяют хранить данные без продления жизни объектов — объект может быть собран, даже если он есть в коллекции. `WeakRef` позволяет получить слабую ссылку на объект, не препятствующую сборке. `FinalizationRegistry` позволяет выполнить необязательное действие после сборки объекта.

Эти возможности особенно полезны для долгоживущих приложений, больших клиентских кешей, UI-библиотек, инфраструктурных библиотек и систем, работающих с большими графами объектов. Например, в SPA-приложениях `WeakMap` используется для хранения состояния компонентов, в кешировании API-ответов — для хранения результатов запросов без удержания объектов в памяти, в системах событий — для хранения подписчиков.

Но они не отменяют фундаментальное правило:

> **сборка мусора остаётся автоматической и недетерминированной.**

Поэтому современная архитектура должна разделять три задачи:

1. **Управление временем жизни ресурсов** — выполняется явно и детерминированно через API самого ресурса и конструкции вроде `try...finally`. Например, закрытие соединений с базой данных, очистка таймеров, отписка от событий.

2. **Оптимизация удержания объектов в памяти** — выполняется с помощью `WeakMap`, `WeakSet` и `WeakRef`. Например, кеширование, хранение метаданных, маркировка объектов.

3. **Необязательная пост-финализационная уборка** — выполняется через `FinalizationRegistry`. Например, очистка кеша, логирование, отладочная информация.

Так JavaScript использует сборщик мусора не как инструмент, которым разработчик пытается управлять вручную, а как автоматическую подсистему, с которой архитектура приложения корректно взаимодействует.

---

### Итог

`WeakMap`, `WeakSet`, `WeakRef` и `FinalizationRegistry` — это не четыре варианта одного механизма. Они решают четыре разных архитектурных задачи:

- **`WeakMap`** — связать метаданные с объектом, не удерживая объект. Используется для приватных данных, кешей, состояний компонентов.
- **`WeakSet`** — пометить объект, не удерживая объект. Используется для отслеживания обработанных объектов, предотвращения повторной обработки.
- **`WeakRef`** — получить необязательную слабую ссылку. Используется для оптимизационных кешей, где данные могут быть пересозданы.
- **`FinalizationRegistry`** — выполнить необязательную очистку после сборки объекта. Используется для дополнительной очистки, отладки, логирования.

Их правильное применение позволяет уменьшать длительное удержание ненужных объектов в памяти, но не даёт разработчику контроля над моментом работы Garbage Collector. Именно это различие является ключом к безопасной работе с памятью в Modern JavaScript 2026.
