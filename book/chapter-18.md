# Глава 18. Off Main Thread: многопоточная архитектура и кластеры агентов

JavaScript традиционно воспринимается как однопоточный язык. Для браузерного приложения это упрощённая модель.

Современная Web Platform предоставляет несколько независимых вычислительных контекстов, которые могут выполнять работу параллельно. Главный поток обслуживает интерфейс и значительную часть взаимодействия с DOM, а Web Workers, Service Workers и Worklets выполняют специализированные задачи в других контекстах.

Поэтому современное приложение можно рассматривать как **кластер взаимодействующих агентов**, а не как один поток выполнения.

---

## 18.1. Web Workers: вычисления за пределами главного потока

`Web Worker` позволяет выполнять JavaScript в отдельном контексте исполнения.

Главный поток и Worker:

* не используют общий обычный JavaScript-объектный граф;
* не имеют прямого доступа к DOM друг друга;
* взаимодействуют через сообщения;
* могут передавать определённые бинарные данные без копирования.

Типичный обмен выглядит так:

```js
// main.js
const worker = new Worker("./worker.js");

worker.postMessage({
  numbers: [10, 20, 30]
});

worker.onmessage = event => {
  console.log(event.data);
};
```

Worker:

```js
self.onmessage = event => {
  const result = event.data.numbers.reduce(
    (sum, value) => sum + value,
    0
  );

  self.postMessage(result);
};
```

Такой подход полезен для задач, которые занимают значительное процессорное время:

* математических расчётов;
* обработки изображений;
* анализа больших массивов данных;
* кодирования и декодирования;
* локального AI-инференса;
* сложной обработки текста.

Главный поток при этом освобождается для интерфейса и обработки пользовательских событий.

---

## 18.2. Передача данных между агентами

Обычный `postMessage()` использует структурированное клонирование. Для больших данных копирование может оказаться дорогим.

Для бинарных буферов можно использовать **Transferable Objects**:

```js
const buffer = new ArrayBuffer(1024 * 1024);

worker.postMessage(buffer, [buffer]);
```

После передачи `ArrayBuffer` становится отсоединённым в исходном контексте:

```js
console.log(buffer.byteLength); // 0
```

Это позволяет передавать владение буфером без копирования всего блока памяти.

Такой механизм особенно полезен для:

* больших `ArrayBuffer`;
* TypedArray;
* потоков бинарных данных;
* обработки изображений;
* AI-моделей и тензорных данных.

---

## 18.3. SharedArrayBuffer и общая память

В некоторых задачах передача владения недостаточна. Нескольким агентам требуется работать с одной областью памяти.

Для этого существуют:

* `SharedArrayBuffer`;
* `Atomics`.

`SharedArrayBuffer` предоставляет разделяемую память, а `Atomics` обеспечивает безопасные атомарные операции и механизмы синхронизации.

Однако эта возможность **не включается автоматически**.

Современные браузеры требуют cross-origin isolation. Для типичного документа необходимо настроить HTTP-заголовки:

```http
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

Состояние можно проверить программно:

```js
console.log(crossOriginIsolated);
```

Если значение равно `false`, приложение не находится в требуемом изолированном состоянии.

### Почему cross-origin isolation влияет на архитектуру

`Cross-Origin-Embedder-Policy: require-corp` влияет не только на JavaScript. Кросс-доменные ресурсы, которые страница пытается загрузить, должны соответствовать правилам совместного использования.

Поэтому включение cross-origin isolation может потребовать проверки:

* сторонних скриптов;
* шрифтов;
* iframe;
* рекламных систем;
* платёжных интеграций;
* OAuth-интеграций;
* сторонних виджетов.

`SharedArrayBuffer` следует рассматривать не как небольшую оптимизацию, а как архитектурную возможность, требующую соответствующей конфигурации приложения и инфраструктуры.

## 18.4. Shared Workers: общий Worker для нескольких контекстов

`SharedWorker` позволяет нескольким контекстам одного origin подключаться к одному Worker.

Это отличается от обычного `Worker`, который принадлежит конкретному контексту.

Shared Worker может использоваться для координации:

* нескольких вкладок;
* окон приложения;
* iframe одного origin;
* общей фоновой логики.

Каждое подключение получает собственный `MessagePort`, через который происходит обмен сообщениями.

При этом жизненный цикл Shared Worker зависит от наличия подключённых контекстов и поведения браузера. Не следует считать, что Worker гарантированно продолжит работу бесконечно после закрытия интерфейса или что браузер никогда не выгрузит его ради экономии ресурсов.

---

## 18.5. Service Workers: фоновой сетевой слой

`Service Worker` решает другую задачу. Он не предназначен прежде всего для тяжёлых вычислений, а предоставляет программируемый слой между веб-приложением и сетевыми ресурсами.

Service Worker может:

* перехватывать `fetch`-запросы;
* работать с Cache API;
* реализовывать offline-first;
* обслуживать кэшированные ресурсы;
* участвовать в фоновой синхронизации;
* принимать Push-события.

Например, приложение может использовать Service Worker, чтобы при отсутствии сети вернуть ранее сохранённый ресурс из кэша.

Таким образом, Service Worker становится частью сетевой архитектуры приложения, а не просто «фоновым потоком JavaScript».

Его жизненный цикл также отличается от жизненного цикла обычной вкладки. Браузер может запускать и останавливать Service Worker по мере необходимости.

---

## 18.6. Worklets: специализированные вычислительные контексты

Worklets предназначены не для произвольных фоновых задач, а для специализированного взаимодействия JavaScript с внутренними подсистемами браузера.

### `AudioWorklet`

`AudioWorklet` позволяет выполнять обработку звука в контексте, предназначенном для аудиообработки в реальном времени.

Он подходит для:

* синтеза звука;
* цифровой обработки сигнала;
* пользовательских аудиоэффектов;
* интерактивных музыкальных приложений.

### `PaintWorklet`

`PaintWorklet` является частью CSS Paint API. JavaScript определяет алгоритм генерации визуального содержимого, которое затем используется CSS.

Это позволяет создавать программно генерируемые визуальные эффекты без ручного изменения DOM для каждого графического элемента.

### `AnimationWorklet`

`AnimationWorklet` нельзя ставить в один ряд с этими зрелыми и широко используемыми механизмами.

К 2026 году Animation Worklet остаётся экспериментальной технологией и не является универсальным кросс-браузерным решением.

Для многих сценариев, ради которых он создавался, современные браузеры предоставляют CSS Scroll-Driven Animations. Поэтому для прокрутки и других декларативных сценариев анимации предпочтительнее использовать стандартизированные CSS-механизмы, когда они решают задачу без JavaScript.

## 18.7. Как выбрать подходящий контекст

Разные задачи требуют разных механизмов.

| Механизм                        | Основная задача                                            |
| ------------------------------- | ---------------------------------------------------------- |
| Main Thread                     | DOM, UI, пользовательские события и координация приложения |
| Web Worker                      | Независимые CPU-интенсивные вычисления                     |
| Shared Worker                   | Общая фоновая логика нескольких контекстов                 |
| Service Worker                  | Сетевой слой, кэш, offline и Push                          |
| AudioWorklet                    | Обработка аудио в реальном времени                         |
| PaintWorklet                    | Программируемое CSS-рисование                              |
| `SharedArrayBuffer` + `Atomics` | Разделяемая память и синхронизация между агентами          |
| Transferable Objects            | Передача больших бинарных данных без копирования           |

Эта классификация важнее самого факта существования Web Workers. Производительность улучшается только тогда, когда работа передаётся правильному механизму.

---

## 18.8. Стоимость многопоточности

Off Main Thread не означает «бесплатное ускорение».

У многопоточной архитектуры есть собственные расходы:

* создание Worker;
* передача сообщений;
* сериализация и клонирование данных;
* синхронизация;
* управление жизненным циклом агентов;
* дополнительное потребление памяти;
* усложнение отладки.

Поэтому переносить в Worker каждую небольшую функцию бессмысленно.

Хороший кандидат для Off Main Thread — задача, которая:

1. требует значительного CPU-времени;
2. может выполняться независимо от DOM;
3. работает достаточно долго, чтобы стоимость коммуникации стала небольшой относительно самой задачи.

---

## 18.9. JavaScript как оркестратор кластера агентов

Современное JavaScript-приложение может объединять несколько специализированных контекстов:

```text
                    ┌──────────────────────┐
                    │      Main Thread     │
                    │ UI + DOM + события   │
                    └──────────┬───────────┘
                               │
             ┌─────────────────┼─────────────────┐
             │                 │                 │
             ▼                 ▼                 ▼
       Web Worker       Service Worker     AudioWorklet
       CPU / AI         Network / Cache       Audio
             │
             ▼
      SharedArrayBuffer
         + Atomics
```

JavaScript в такой архитектуре выполняет роль координатора:

* определяет, где должна выполняться работа;
* передаёт данные между агентами;
* выбирает между копированием и передачей владения;
* при необходимости использует разделяемую память;
* оставляет специализированным подсистемам те задачи, для которых они предназначены.

---

## 18.10. Итог

Off Main Thread — это не отдельная оптимизация, а архитектурный принцип.

Главный поток должен оставаться достаточно свободным для:

* пользовательского ввода;
* обновления интерфейса;
* координации приложения;
* работы Rendering Pipeline.

CPU-интенсивные задачи можно передавать Web Workers, сетевую инфраструктуру — Service Workers, а специализированную обработку — Worklets.

При этом нельзя считать многопоточность автоматически безопасной и бесплатной. `SharedArrayBuffer` требует cross-origin isolation, обмен данными имеет стоимость, а экспериментальные API нельзя использовать как универсальную основу приложения.

Главный принцип Modern JavaScript 2026:

**JavaScript-приложение должно распределять работу между подходящими агентами, оставляя главному потоку только ту работу, которая действительно требует его участия.**
