# Часть VII. JavaScript и современные фреймворки

## Глава 24. React 19 и далее: компилятор, серверные компоненты и Web Platform

React в 2026 году — это уже не только библиотека для преобразования состояния в интерфейс. Современная архитектура React объединяет несколько уровней:

1. **JavaScript** описывает поведение приложения;
2. **React** управляет компонентной моделью и процессом рендеринга;
3. **React Compiler** оптимизирует компоненты во время сборки;
4. **Server Components и Server Functions** позволяют переносить часть вычислений и работы с данными на сервер;
5. **Web Platform** предоставляет HTML, Forms, Fetch, Streams, DOM и другие базовые механизмы;
6. **фреймворк и сборщик** связывают эти части в готовое приложение.

Поэтому современный React правильнее рассматривать не как замену Web Platform, а как **архитектурный слой над ней**.

При этом React не превращает автоматически любой веб-проект в full-stack приложение. Server Components, Server Functions, streaming SSR и маршрутизация требуют соответствующей инфраструктуры фреймворка или сборщика. Сам React предоставляет примитивы, а конкретная интеграция зависит от окружения.

В 2025–2026 годах изменилась и институциональная сторона проекта. В феврале 2026 года React Foundation официально запустилась как независимая организация под эгидой Linux Foundation. React, React Native и JSX больше не принадлежат Meta. Техническое направление React при этом должно определяться независимой технической структурой, а не советом самой Foundation.

## 24.1. React Compiler: оптимизация JavaScript во время сборки

React Compiler 1.0 вышел 7 октября 2025 года. Это стабильный компилятор, который анализирует React-компоненты и хуки во время сборки и автоматически выполняет оптимизацию мемоизации. Он поддерживает как React, так и React Native и официально объявлен production-ready.

Это меняет традиционную модель оптимизации React.

Раньше разработчик сам решал, где применять:

```js
useMemo(...)
useCallback(...)
React.memo(...)
```

Теперь значительную часть этой работы может выполнить компилятор.

### Автоматическая мемоизация

React Compiler анализирует поток данных, зависимости и изменяемость значений внутри компонента. На этой основе он может автоматически сохранять результаты вычислений и функции там, где это безопасно и полезно.

При этом компилятор не является просто автоматическим генератором `useMemo` и `useCallback`. Он работает на более низком уровне: преобразует AST в собственное промежуточное представление и выполняет анализ потока данных. Поэтому он способен оптимизировать случаи, которые невозможно выразить обычным ручным `useMemo` или `useCallback`.

### Что происходит с ручной мемоизацией

React не требует удалить существующие `useMemo`, `useCallback` и `React.memo`.

Официальная рекомендация для нового кода состоит в том, чтобы **в первую очередь полагаться на Compiler**, используя ручную мемоизацию там, где требуется сознательно контролировать конкретное поведение. Для существующего кода React рекомендует не удалять ручную мемоизацию механически: её изменение способно изменить результат компиляции и поведение зависимых эффектов.

Таким образом, React 2026 года постепенно переводит оптимизацию из области ручного микроменеджмента разработчика в область **статического анализа JavaScript**.

Это важный архитектурный сдвиг:

> разработчик описывает правильную декларативную логику, а компилятор пытается определить оптимальный способ её выполнения.

### Производительность

React приводит реальные результаты использования Compiler в Meta Quest Store: первичная загрузка и переходы между страницами улучшались до 12%, а отдельные интеракции — более чем в 2,5 раза. Это результаты конкретного приложения, а не универсальная гарантия ускорения любого React-проекта.

Поэтому корректная формулировка для инженерной практики такова:

**React Compiler снижает необходимость ручной оптимизации, но не отменяет измерение производительности.**

## 24.2. Server Components: разделение вычислений между сервером и браузером

React Server Components (RSC) позволяют выполнять часть компонентов в отдельной серверной среде и не отправлять их JavaScript-код в браузер.

Это принципиально отличается от обычного SSR.

При SSR компонент сначала выполняется на сервере для получения HTML, после чего клиент обычно загружает JavaScript, необходимый для интерактивной версии интерфейса.

Server Component может вообще не становиться частью клиентского JavaScript-бандла.

Например, серверный компонент может:

1. получить данные из базы;
2. выполнить преобразование данных;
3. построить интерфейс;
4. передать клиентскому компоненту только необходимые результаты.

Таким образом, архитектура приложения получает естественную границу:

```text
                 SERVER
┌─────────────────────────────────────┐
│ Server Components                   │
│ database / filesystem / backend     │
│ data fetching                       │
└──────────────────┬──────────────────┘
                   │
                   │ serialized result
                   ▼
┌─────────────────────────────────────┐
│ CLIENT                              │
│ Client Components                   │
│ DOM / events / browser APIs         │
│ interactive state                   │
└─────────────────────────────────────┘
```

### RSC не являются просто «новым SSR»

React 19 сделал Server Components стабильными как часть React API. Однако React прямо предупреждает: **низкоуровневые API, необходимые для создания RSC-бандлеров и фреймворков, не имеют той же гарантии стабильности и могут изменяться между минорными версиями React 19**. Поэтому разработчику приложения следует различать стабильность самой концепции RSC и стабильность инфраструктуры, которая её реализует.

Именно поэтому в реальных проектах RSC обычно используются через фреймворк или специально настроенную сборочную инфраструктуру, а не собираются вручную из низкоуровневых React API.

### RSC и Web Platform

Современная серверная архитектура React тесно связана с Web Platform, особенно с:

* `fetch`;
* `Request` и `Response`;
* Web Streams;
* `URL`;
* `FormData`;
* стандартными механизмами HTTP.

Это позволяет переносить часть архитектурных решений между браузером и сервером.

Однако универсальность нельзя преувеличивать. Browser API вроде DOM, Clipboard API или некоторых возможностей File System Access API не становятся доступными на сервере только потому, что серверный код написан на JavaScript.

## 24.3. Server Functions и Actions: мутация данных как часть UI-модели

React 19 ввёл более декларативную модель работы с асинхронными изменениями состояния — **Actions**.

Action — это асинхронная операция, выполнение которой React способен связать с состояниями:

* pending;
* success;
* error;
* optimistic update.

Например, изменение имени пользователя может быть представлено как Action:

```js
startTransition(async () => {
  await updateName(name);
});
```

React способен автоматически отслеживать состояние такой операции. Для распространённых сценариев React 19 предоставляет `useActionState`, `useOptimistic`, `useTransition`, а `react-dom` интегрирует Actions с HTML-формами.

### Actions и HTML Forms

React 19 позволяет передавать функцию непосредственно в `action` формы:

```jsx
<form action={submitAction}>
  <input name="name" />
  <button type="submit">Save</button>
</form>
```

React связывает такую форму с Action и автоматически предоставляет механизмы обработки pending-состояния, результата и ошибок. Для неконтролируемых полей после успешного Action форма может быть автоматически сброшена.

Это важный пример архитектурной конвергенции React и Web Platform:

> React не заменяет HTML Forms, а расширяет их программной моделью.

### Server Functions

Server Functions позволяют клиентскому компоненту вызвать асинхронную функцию, которая выполняется на сервере.

В экосистеме React директива:

```js
"use server";
```

используется для обозначения серверных функций. При вызове такой функции клиентский код не выполняет её непосредственно: инфраструктура приложения организует сетевой вызов серверной функции и возвращает результат.

Важно не смешивать два понятия:

* **Server Component** — компонент, выполняемый в серверной среде;
* **Server Function / Server Action** — функция, которую можно вызвать для выполнения серверной операции.

`"use server"` относится к Server Functions, а **не является директивой, обозначающей Server Component**.

### Progressive Enhancement

Интеграция Actions с HTML-формами особенно важна для progressive enhancement.

Базовая операция может оставаться связанной с обычной моделью HTML-формы, а React добавляет:

* состояние отправки;
* оптимистическое обновление;
* обработку результата;
* отображение ошибок;
* клиентскую интерактивность.

Это соответствует фундаментальной идее современной Web Platform: **JavaScript расширяет платформу, а не обязательно заменяет её базовые механизмы.**

## 24.4. `use`: JavaScript Promise становится частью модели рендеринга

React 19 добавил API `use`, позволяющий читать Promise непосредственно во время render:

```js
const data = use(dataPromise);
```

Если Promise ещё не завершён, React приостанавливает соответствующую часть дерева и передаёт управление ближайшему `Suspense`. Когда Promise разрешается, React продолжает работу с полученным значением.

Это создаёт важный мост между обычной моделью JavaScript:

```js
const value = await promise;
```

и моделью декларативного UI:

```js
const value = use(promise);
```

Однако это **не означает, что любой Promise можно создавать непосредственно в render**.

React предупреждает, что Promise, созданный непосредственно внутри Client Component или hook во время render, не поддерживается без Suspense-совместимой библиотеки или фреймворка. Источник данных должен предоставлять стабильный, кешируемый Promise.

Следовательно, `use` — не универсальный заменитель `await`. Это API интеграции асинхронного ресурса с системой рендеринга React.

## 24.5. `Suspense`: граница асинхронности и потокового HTML

`Suspense` позволяет определить участок интерфейса, который может временно отсутствовать до готовности данных или другого ресурса:

```jsx
<Suspense fallback={<Loading />}>
  <Comments />
</Suspense>
```

Если дочернее дерево при рендеринге приостанавливается, React показывает `fallback`, а затем заменяет его готовым содержимым.

Но `Suspense` следует понимать не как общий механизм ожидания JavaScript Promise, а как **часть координации React-рендеринга**.

Он может взаимодействовать с:

* `lazy`;
* `use` и Suspense-совместимыми источниками данных;
* Server Components;
* streaming server rendering;
* загрузкой стилей, которые React связывает с соответствующим деревом.

### Streaming SSR

При потоковом SSR сервер не обязан ждать готовности всей страницы.

React может сначала отправить HTML основного каркаса:

```text
Page shell
├── Header
├── Navigation
├── Main
│   ├── ready content
│   └── Loading...
└── Footer
```

а затем передать HTML для отложенной части, когда она станет готовой.

React документирует такой сценарий через `renderToReadableStream()` и `renderToPipeableStream()`. При этом `Suspense` определяет границы, которые могут быть показаны позже.

Это означает, что потоковая передача HTML может начать работать **до того, как JavaScript клиента загрузится и приложение станет интерактивным**.

Именно здесь React особенно тесно соприкасается с Web Platform: React формирует HTML, а браузер получает его через обычный HTTP-поток и постепенно строит интерфейс.

## 24.6. React 19.2: React становится системой координации ресурсов

React 19.2 продолжил эту архитектурную линию.

В релиз вошли:

* `<Activity />`;
* `useEffectEvent`;
* `cacheSignal`;
* Performance Tracks;
* Partial Pre-rendering;
* улучшения потокового SSR;
* поддержка Web Streams для SSR в Node.js.

Это показывает направление развития React точнее, чем просто список новых компонентов.

React постепенно становится системой, которая координирует:

```text
JavaScript
    │
    ▼
React component model
    │
    ├── Compiler
    │
    ├── Suspense
    │
    ├── Actions
    │
    ├── Server Components
    │
    └── Resource scheduling
            │
            ▼
      Web Platform
      ├── HTML
      ├── Forms
      ├── Fetch
      ├── Streams
      ├── DOM
      └── Browser APIs
```

Поэтому современный React нельзя оценивать только по количеству новых Hooks. Его основная эволюция происходит на уровне **архитектуры выполнения приложения**.

## 24.7. Web Platform остаётся фундаментом, а React — надстройкой

Важно не сделать из этой архитектуры противоположную ошибку: React не отменяет Web Platform.

Современное приложение по-прежнему использует:

* HTML для структуры;
* CSS для представления;
* Forms для пользовательского ввода;
* Fetch для HTTP;
* Streams для потоковых данных;
* DOM для взаимодействия с документом;
* URL и History для навигационного состояния;
* Web Components для независимых элементов интерфейса;
* JavaScript для прикладной логики.

React добавляет собственную модель поверх этих механизмов.

Поэтому компетентный React-разработчик 2026 года должен понимать не только React API, но и фундамент, на котором React работает.

## 24.8. Новая граница оптимизации: компилятор вместо ручного микроменеджмента

Главное изменение React 2026 года можно сформулировать следующим образом.

В классической модели разработчик вручную управлял значительной частью оптимизации:

```text
Developer
   │
   ├── useMemo
   ├── useCallback
   ├── React.memo
   └── dependency arrays
```

В современной модели:

```text
Developer
   │
   │  declarative JavaScript
   ▼
React Compiler
   │
   │  static analysis
   ▼
optimized React program
```

Это не означает, что производительность больше не требует инженерного анализа.

Разработчик всё ещё отвечает за:

* структуру приложения;
* объём передаваемых данных;
* сетевые запросы;
* количество JavaScript;
* архитектуру серверных и клиентских границ;
* стоимость вычислений;
* количество DOM-узлов;
* пользовательский опыт.

Compiler оптимизирует определённый класс проблем, но не способен сделать плохую архитектуру хорошей автоматически.

## 24.9. Безопасность Server Components — часть современной архитектуры

Состояние React в 2026 году нельзя описывать только через новые возможности и преимущества.

3 декабря 2025 года React-команда раскрыла критическую уязвимость **CVE-2025-55182** в инфраструктуре React Server Components — небезопасную десериализацию в обработке протокола Flight, получившую в отрасли неформальное имя **«React2Shell»**. Уязвимость получила максимальную оценку **CVSS 10.0**: эксплуатация не требовала аутентификации, взаимодействия пользователя и вела напрямую к удалённому выполнению кода на сервере одним специально сформированным HTTP-запросом. Первый патч вышел в версиях 19.0.1, 19.1.2 и 19.2.1.

Уже 11 декабря 2025 года исследователи, пытаясь эксплуатировать вышедший патч, обнаружили две дополнительные уязвимости — Denial of Service (CVE-2025-55184) и Source Code Exposure (CVE-2025-55183), закрытые в версиях 19.0.2, 19.1.3 и 19.2.2. Наконец, 26 января 2026 года выяснилось, что и это исправление DoS-уязвимости было неполным — React выпустил ещё один раунд патчей (CVE-2026-23864), окончательно закрывший проблему в версиях **19.0.4, 19.1.5 и 19.2.4**.

Эта последовательность из трёх раундов патчей за неполные два месяца — важный практический урок для архитектуры, а не просто исторический факт: разработчику недостаточно обновиться один раз после объявления об уязвимости — нужно отслеживать последующие уточнения того же advisory, поскольку первый патч не всегда закрывает проблему полностью.

Это имеет непосредственное архитектурное значение.

Server Components и Server Functions расширяют границу приложения:

```text
Browser
   │
   │ network request
   ▼
Server Function
   │
   ├── application code
   ├── database
   ├── filesystem
   └── privileged resources
```

Следовательно, серверные функции нельзя воспринимать как обычные локальные JavaScript-функции.

Они являются **сетевыми границами доверия**.

При их использовании необходимо учитывать:

* аутентификацию;
* авторизацию;
* проверку входных данных;
* ограничения размера запросов;
* обработку ошибок;
* защиту от DoS;
* безопасную сериализацию;
* своевременное обновление React Server Components инфраструктуры — причём не разово, а с отслеживанием последующих обновлений того же advisory.

Таким образом, современный React требует уже не только frontend-инженерии, но и полноценного понимания серверной безопасности.

## Заключение

React 19 и развитие экосистемы в 2025–2026 годах показывают важный переход в архитектуре JavaScript-приложений.

React движется сразу по нескольким направлениям:

**1. Компилятор**

React Compiler переносит значительную часть оптимизации из ручного кода в статический анализ.

**2. Сервер**

Server Components позволяют не отправлять часть компонентного JavaScript в браузер.

**3. Данные**

Actions, Server Functions и `use` интегрируют асинхронные операции с моделью рендеринга.

**4. HTML**

Actions работают непосредственно с HTML Forms, а streaming SSR передаёт браузеру HTML постепенно.

**5. Web Platform**

Fetch, Streams, DOM, HTML и другие платформенные API остаются фундаментом, на котором React строит более высокоуровневую модель.

**6. Безопасность**

Server Components и Server Functions расширяют поверхность атаки и требуют такого же серьёзного отношения к безопасности, как любой другой серверный API.

Главная идея React 2026 года поэтому заключается не в том, что «React заменяет Web Platform».

Она противоположна:

> **современный React старается использовать возможности Web Platform и переносить всё больше работы из ручного JavaScript-кода в компилятор, сервер и браузерный runtime.**

Именно поэтому изучать React после React 19 следует не как набор новых Hooks, а как **архитектуру выполнения JavaScript-приложения, распределённую между компилятором, сервером, React runtime и Web Platform**.

Для книги *Modern JavaScript 2026* это принципиально важно: современный JavaScript-разработчик должен понимать не только синтаксис языка, но и то, **где именно выполняется его код, кто управляет его оптимизацией и какие части работы можно передать платформе**.
