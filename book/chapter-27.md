# Часть VII. JavaScript и современные фреймворки

## Глава 27. Svelte 5: Runes, компиляция и минимизация runtime

Svelte 5 представляет другой подход к построению JavaScript-интерфейсов. В React, Vue и многих других UI-системах значительная часть архитектуры приложения реализуется через runtime-библиотеку, которая работает в браузере. Svelte переносит большую часть этой работы на этап компиляции.

Исходный `.svelte`-компонент содержит HTML, CSS и JavaScript. Компилятор анализирует этот код и генерирует JavaScript, который непосредственно создаёт и обновляет DOM. Благодаря этому Svelte не нуждается в Virtual DOM как в обязательном промежуточном представлении интерфейса.

Однако утверждение «Svelte не имеет runtime» было бы неправильным. Скомпилированный код использует runtime-механизмы Svelte для реактивности, событий, жизненного цикла и других операций. Правильнее говорить о **минимизации и специализации runtime**, а не о его полном исчезновении.

Svelte 5 дополнил эту архитектуру новой моделью реактивности — **Runes**. Она сделала реактивность более явной и позволила применять её не только в компонентах, но и в переиспользуемом JavaScript-коде.

## 27.1. Runes: явная модель реактивности

В Svelte 5 реактивность строится вокруг специальных конструкций, называемых **Runes**. Они выглядят как функции, но не являются обычными JavaScript-функциями. Svelte распознаёт их как часть собственной модели языка и обрабатывает при компиляции.

**Основные Runes:**

- **`$state`** — создаёт реактивное состояние. При изменении значения все зависимые вычисления и DOM-узлы обновляются автоматически.

```javascript
let count = $state(0);
let user = $state({ name: 'Anatoly', age: 30 });
```

- **`$derived`** — описывает значение, вычисляемое из другого состояния. Результат кешируется и пересчитывается только при изменении зависимостей.

```javascript
let doubled = $derived(count * 2);
let userDisplay = $derived(`${user.name} (${user.age})`);
```

- **`$effect`** — запускает побочный эффект при изменении используемых реактивных значений. Используется для синхронизации с внешними системами, логирования, API-вызовов.

```javascript
$effect(() => {
  console.log(`Count changed to ${count}`);
  localStorage.setItem('count', String(count));
});
```

- **`$props`** — объявляет свойства компонента, которые могут передаваться из родительского компонента.

```javascript
let { id, title, onClose } = $props();
```

- **`$bindable`** — позволяет явно обозначить свойства, участвующие в двусторонней привязке (когда компонент может изменять значение, переданное из родителя).

```javascript
let { value = $bindable() } = $props();
```

**Пример компонента с Runes:**

```svelte
<script>
  let count = $state(0);
  let doubled = $derived(count * 2);

  $effect(() => {
    console.log(`Count is ${count}`);
  });
</script>

<button onclick={() => count++}>
  {count}
</button>

<p>Doubled: {doubled}</p>
```

**Главное отличие от старой модели Svelte (3/4):**

В Svelte 3/4 простое объявление `let count = 0;` в компоненте могло становиться реактивным благодаря специальным правилам компилятора. Производные значения и эффекты описывались через `$:`. Это был неявный механизм, работающий только внутри компонентов.

В Svelte 5 эти задачи получили явные конструкции, работающие как в компонентах, так и в обычных JavaScript-файлах:

```javascript
// В Svelte 3/4 — только внутри .svelte-файлов
let count = 0;
$: doubled = count * 2;
$: console.log(count);

// В Svelte 5 — везде
let count = $state(0);
let doubled = $derived(count * 2);
$effect(() => console.log(count));
```

При этом старая синтаксическая модель не была мгновенно уничтожена: Svelte 5 сохраняет **legacy mode** для существующего кода. Для нового кода официальная документация рекомендует использовать **Runes mode**. Стоит иметь в виду направление дальнейшего развития: команда Svelte уже анонсировала, что в **Svelte 6** поведением по умолчанию для всего проекта станет `runes: true` — то есть компиляторный флаг, который сегодня нужно включать явно в конфигурации (`compilerOptions: { runes: true }`), станет стандартной настройкой. Legacy mode при этом не исчезнет мгновенно, но новые проекты будут по умолчанию рассчитывать на Runes-код. Для книги, ориентированной на 2026 год, это значит, что legacy mode стоит воспринимать как временный переходный механизм для существующих кодовых баз, а не как равноправную с Runes долгосрочную модель.
### Runes не являются ECMAScript Signals

Это принципиально важно для архитектуры **Modern JavaScript 2026**.

Svelte Runes **не являются частью ECMAScript** и не используют стандартизированный механизм Signals браузера или JavaScript. Они представляют собой собственную модель реактивности Svelte.

Это также означает, что нельзя говорить о «синхронизации Svelte 5 с нативными Signals». TC39 Signals — отдельное предложение стандартизации, а Runes — уже существующий механизм Svelte.

Таким образом, в 2026 году нужно различать три уровня:

1. **JavaScript** — язык ECMAScript, его синтаксис и встроенные объекты.
2. **Svelte Runes** — механизм реактивности Svelte (`$state`, `$derived`, `$effect`).
3. **TC39 Signals** — отдельное направление стандартизации, которое не является частью Runes.

Такое разделение важно и с практической точки зрения: код на `$state`, `$derived` и `$effect` не становится автоматически совместимым с гипотетическим будущим API Signals ECMAScript.

## 27.2. Гранулярная реактивность: обновлять только необходимое

Одно из главных преимуществ модели Svelte 5 — возможность выполнять очень точечные обновления DOM.

**Пример компонента:**

```svelte
<script>
  let count = $state(0);
  let name = $state('Anatoly');
</script>

<button onclick={() => count++}>
  {count}
</button>

<p>{name}</p>
```

Изменение `count` не требует повторного построения всего компонента как абстрактного дерева. Компилятор и runtime Svelte создают механизм, который связывает реактивное состояние с конкретными участками DOM.

**Как это работает:**

1. Компилятор анализирует шаблон и определяет, какие части DOM зависят от каких переменных.
2. Для каждого реактивного значения генерируется код обновления только тех DOM-узлов, которые его используют.
3. При изменении `count` обновляется только текстовое содержимое кнопки, а `name` и его DOM-узел не затрагиваются.

Это принципиально отличается от архитектур, в которых Virtual DOM используется как промежуточное представление интерфейса:

```
изменение состояния
        ↓
реактивная система (Svelte)
        ↓
определение затронутых DOM-узлов (компилятор знает зависимости)
        ↓
точечное обновление DOM (только изменившиеся узлы)
```

В Svelte компилятор заранее знает структуру шаблона и может генерировать специализированный код обновления:

```
.svelte-компонент (HTML + CSS + JS)
        ↓
      compiler (анализ зависимостей)
        ↓
специализированный JavaScript (для каждого компонента)
        ↓
   точечные DOM-операции (только необходимые узлы)
```

Это не означает, что Svelte «магически гарантирует максимальную производительность». Стоимость вычислений, размер JavaScript, количество DOM-узлов, сетевые задержки и возможности устройства по-прежнему определяют реальную производительность приложения.

Правильнее говорить о том, что **архитектура Svelte уменьшает один из классов runtime-издержек — необходимость поддерживать и сравнивать отдельное Virtual DOM-представление.**

## 27.3. Компилятор вместо Virtual DOM

Svelte принципиально отличается от Virtual DOM-фреймворков способом представления интерфейса.

**Virtual DOM-подход (React, Vue):**

```
Template (декларативное описание)
    ↓
Virtual DOM (в памяти JavaScript)
    ↓
Diff (сравнение с предыдущим состоянием)
    ↓
Патчинг (применение изменений к реальному DOM)
```

Приложение поддерживает структуру, которая описывает интерфейс в памяти JavaScript. После изменения состояния система определяет, какие части этой структуры изменились, и затем применяет необходимые изменения к реальному DOM.

**Svelte-подход:**

```
Template (декларативное описание)
    ↓
Svelte Compiler (анализ структуры и зависимостей)
    ↓
Специализированный JavaScript (прямые DOM-операции)
    ↓
DOM API (обновление только необходимых узлов)
```

**Пример сгенерированного кода:**

Официальный Svelte Playground показывает, что компилятор превращает шаблон в JavaScript, использующий специализированные внутренние операции:

```javascript
// Сгенерированный код (упрощённо)
import * as $ from 'svelte/internal/client';

// Реактивное состояние
let count = $.state(0);

// Шаблон с зависимостями
$.template_effect(() => {
  // Обновление текста кнопки при изменении count
  $.set_text(buttonElement, count);
});
```

Svelte использует операции вроде `template_effect`, `set_text`, `event` и других runtime-примитивов для точечных обновлений. Поэтому Svelte не нуждается в полноценном Virtual DOM runtime для выполнения обычного компонентного обновления.

Это особенно важно для понимания термина **compiler-first architecture**: компилятор не просто преобразует синтаксис `.svelte` в JavaScript. Он знает структуру шаблона и может генерировать код, специализированный именно под этот шаблон.

## 27.4. Что означает «исчезающий runtime»

Выражение «исчезающий runtime» удобно как архитектурная метафора, но его нельзя понимать буквально.

После компиляции Svelte-приложение действительно не содержит большого универсального runtime, который должен интерпретировать Virtual DOM всего приложения. Однако сгенерированный код использует runtime-операции Svelte.

**Что остаётся в runtime:**

```javascript
// Сгенерированный код импортирует runtime-операции
import * as $ from 'svelte/internal/client';

// Использует операции для реактивности
let count = $.state(0);

// Использует операции для DOM-обновлений
$.template_effect(() => {
  $.set_text(element, count);
});

// Использует операции для событий
$.event(button, 'click', handler);
```

**Что не входит в runtime:**

- Virtual DOM — полностью отсутствует.
- Diff-алгоритм — не нужен, так как зависимости известны на этапе компиляции.
- Интерпретатор шаблонов — шаблоны уже скомпилированы в код.

Следовательно, точнее говорить:

> **Svelte не устраняет runtime, а переносит как можно больше работы в компилятор и оставляет в браузере только необходимые для конкретного приложения runtime-механизмы.**

Именно это является одним из главных архитектурных преимуществ Svelte.

## 27.5. Почему Svelte не следует считать «чистым JavaScript после компиляции»

Ещё одна распространённая ошибка — считать, что после компиляции Svelte-компонент превращается в полностью независимый JavaScript, не связанный с фреймворком.

**Сгенерированный код остаётся специализированным под Svelte runtime.**

Это видно непосредственно по результату компиляции:

```javascript
// Сгенерированный код импортирует Svelte runtime
import * as $ from 'svelte/internal/client';

// Использует Svelte-специфичные операции
let count = $.state(0);
$.template_effect(() => {
  $.set_text(element, count);
});
$.event(button, 'click', handler);
```

Вместо чистого `document.getElementById()` или `element.textContent = ...`, сгенерированный код использует обёртки Svelte, которые обеспечивают реактивность, управление жизненным циклом и оптимизации.

Таким образом, результат компиляции — это **обычный JavaScript-код, использующий специализированные runtime-примитивы Svelte**.

Это важное отличие от идеи «компилятор полностью уничтожает фреймворк». Svelte уменьшает runtime-слой, но не превращает весь проект в набор полностью независимых от Svelte DOM-вызовов.

## 27.6. Tree Shaking и размер клиентского кода

Svelte хорошо сочетается с современными системами сборки, которые выполняют:

- **Tree shaking** — удаление неиспользуемого кода из бандла.
- **Code splitting** — разделение кода на чанки, загружаемые по требованию.
- **Динамический `import()`** — ленивая загрузка модулей.
- **Минификацию** — сжатие кода для уменьшения размера.
- **Оптимизацию production-бандлов** — удаление отладочной информации.

Однако эти возможности нельзя приписывать исключительно Svelte.

**Пример tree shaking в Svelte:**

```javascript
// Если компонент не использует определённую runtime-операцию
// она не попадёт в бандл
import * as $ from 'svelte/internal/client';
// Используется только $.state и $.set_text
// $.effect, $.event, $.bind и другие операции не попадают в бандл
```

Например, tree shaking в значительной степени является функцией модульной системы (ES Modules) и сборщика (Vite, Rollup, Webpack). Размер итогового JavaScript зависит от архитектуры приложения, используемых пакетов, конфигурации сборки и особенностей конкретного deployment pipeline.

Поэтому утверждение «Svelte гарантирует, что в бандл попадут только необходимые микрофункции» слишком сильно.

Корректнее сформулировать принцип следующим образом:

> **Svelte генерирует специализированный код для конкретного компонента, а современный bundler затем может удалить неиспользуемые части этого кода и его зависимостей.**

Эти два механизма работают совместно, но это не одно и то же.

## 27.7. Svelte и Web Platform

Svelte хорошо вписывается в архитектурную тенденцию, описанную в предыдущих главах: фреймворк не обязан заменять возможности браузера собственными аналогами.

**Компонент Svelte по-прежнему работает с обычными Web API:**

```javascript
// Сетевые запросы
fetch('/api/data');

// Хранение данных
localStorage.setItem('theme', 'dark');

// Наблюдение за элементами
const observer = new IntersectionObserver(...);

// События
element.addEventListener('click', handler);

// Web Workers
const worker = new Worker('worker.js');

// Canvas
const ctx = canvas.getContext('2d');
```

Svelte предоставляет декларативный слой над этими механизмами, но сам браузер продолжает выполнять основные системные задачи:

- DOM — управление структурой документа.
- CSS — стилизация и анимации.
- События — обработка пользовательского ввода.
- Fetch — сетевые запросы.
- Web Streams — потоковая обработка данных.
- Web Storage — хранение данных.
- Web Workers — фоновые вычисления.
- Canvas и WebGPU — графика.
- Web Components — кастомные элементы.

Поэтому Svelte не следует описывать как «замену Web Platform». Его задача — **скомпилировать декларативное описание интерфейса в эффективный JavaScript, который затем работает поверх Web Platform.**

## 27.8. SvelteKit: где заканчивается Svelte

Для современной архитектуры важно не смешивать **Svelte** и **SvelteKit**.

**Svelte** — это UI-фреймворк и компилятор компонентов. Он отвечает за:
- Компиляцию `.svelte`-файлов в JavaScript.
- Реактивность через Runes (`$state`, `$derived`, `$effect`).
- Обновление DOM.
- Жизненный цикл компонентов.

**SvelteKit** — это фреймворк более высокого уровня, который добавляет архитектуру веб-приложения:
- Маршрутизацию (file-based routing).
- Server-side rendering (SSR).
- Prerendering (генерация статических страниц).
- Загрузку данных (load functions).
- Серверные функции (server endpoints).
- Code splitting.
- Клиентскую навигацию (SPA-переходы без перезагрузки).
- Deployment adapters (адаптеры для разных платформ: Vercel, Netlify, Cloudflare, Node.js).

**Архитектурные уровни:**

```
Web Platform (браузер, DOM, CSS, Fetch, Web APIs)
      ↓
JavaScript / DOM / Fetch / Streams (язык и платформа)
      ↓
Svelte compiler + runtime (компиляция компонентов, реактивность)
      ↓
SvelteKit (маршрутизация, SSR, загрузка данных, адаптеры)
      ↓
приложение (бизнес-логика, пользовательский интерфейс)
```

Поэтому такие возможности, как SSR, предварительная загрузка маршрутов или управление серверной и клиентской частью приложения, нельзя автоматически приписывать Svelte compiler. Они относятся к SvelteKit.

Это особенно важно для темы **Modern JavaScript 2026**: современная веб-архитектура состоит из нескольких уровней, каждый из которых решает собственную задачу.

## Заключение

Svelte 5 показывает один из наиболее последовательных вариантов **compiler-first architecture** в современной веб-разработке.

Его основная идея состоит не в том, чтобы «исчезнуть полностью», а в том, чтобы **перенести как можно больше работы из браузерного runtime в компилятор**.

Runes (`$state`, `$derived`, `$effect`, `$props`, `$bindable`) делают реактивность явной и позволяют использовать её как в компонентах, так и в обычном JavaScript-коде. `$state` создаёт реактивное состояние, `$derived` — производные значения, `$effect` — побочные эффекты, `$props` — свойства компонента, `$bindable` — двустороннюю привязку.

Компилятор знает структуру шаблона и генерирует специализированный JavaScript, который использует runtime-примитивы Svelte (`template_effect`, `set_text`, `event`). Поэтому Svelte может выполнять точечные DOM-операции без обязательного Virtual DOM и без поддержки виртуального дерева в рантайме.

При этом Svelte 5 не является «нативной реактивностью JavaScript»: Runes принадлежат самому Svelte и не являются частью ECMAScript. Они также не являются реализацией TC39 Signals. Это собственная модель реактивности Svelte, развивающаяся независимо от предложений стандартизации.

Не следует и говорить, что Svelte полностью устраняет runtime. Сгенерированный код импортирует и использует runtime-операции Svelte. Корректная формулировка — **Svelte минимизирует и специализирует runtime, перенося значительную часть работы на этап компиляции**.

SvelteKit дополняет Svelte на уровне приложения, добавляя маршрутизацию, SSR, загрузку данных и адаптеры для разных платформ. Эти возможности не входят в сам Svelte compiler.

Именно это делает Svelte особенно интересным для архитектуры **Modern JavaScript 2026**:

> **JavaScript остаётся языком выполнения, Web Platform — фундаментом, а Svelte использует компилятор для того, чтобы отправить в браузер только ту логику интерфейса, которая действительно нужна приложению.**

Это не означает отказ от фреймворка в пользу платформы. Это означает изменение места, где выполняется работа: **меньше универсальной логики в runtime — больше специализации на этапе компиляции.**
