# Часть VI. Современная архитектура

## Глава 22. JavaScript и HTML Living Standard: единая платформа Web

Современный JavaScript нельзя рассматривать только как язык программирования. Код JavaScript выполняется внутри host environment — браузера, Node.js, Deno или другой среды, которая предоставляет ему дополнительные возможности.

Для браузера основой такого окружения служат стандарты Web Platform. ECMAScript определяет сам язык JavaScript и его встроенные объекты, а HTML Living Standard и связанные с ним спецификации определяют значительную часть браузерной среды: документы, DOM, события, навигацию, загрузку ресурсов, Web Workers и взаимодействие скриптов с жизненным циклом страницы.

Поэтому современное веб-приложение строится не вокруг одного JavaScript. Он объединяет несколько специализированных подсистем:

- **HTML** определяет структуру документа и декларативное поведение интерфейса;
- **DOM** предоставляет JavaScript программное представление документа;
- **CSS** отвечает за стили, компоновку, анимации и значительную часть визуального поведения;
- **Web APIs** предоставляют сетевые, файловые, графические, мультимедийные и другие возможности;
- **JavaScript** связывает эти подсистемы и реализует прикладную логику.

Главный архитектурный принцип 2026 года можно сформулировать просто:

> **Не заставляйте JavaScript выполнять работу, которую браузер уже умеет выполнять декларативно и эффективнее.**

Это не означает отказ от JavaScript. Наоборот, JavaScript становится более ценным именно там, где требуется координация нескольких возможностей платформы.

## 22.1. ECMAScript и Web Platform: два стандарта, одна среда выполнения

ECMAScript и HTML Living Standard нельзя считать двумя частями одной спецификации. Они развиваются независимо и решают разные задачи.

**ECMAScript**, разрабатываемый сообществом TC39, определяет:

- синтаксис JavaScript;
- типы данных (`string`, `number`, `object`, `symbol`, `bigint`, `undefined`, `null`);
- функции и классы;
- объекты и прототипы;
- модули (`import`/`export`);
- `Promise`, `async`/`await`;
- итераторы и генераторы;
- встроенные коллекции (`Map`, `Set`, `WeakMap`, `WeakSet`);
- управление памятью на уровне языка;
- правила выполнения ECMAScript-кода.

**Web Platform** предоставляет браузерные возможности, которых в самом ECMAScript нет:

- `window` и `document`;
- DOM (`Element`, `Node`, `Document`);
- `EventTarget` и события;
- `fetch()`;
- `URL` и `URLSearchParams`;
- Web Workers;
- Service Workers;
- Web Components (Custom Elements, Shadow DOM);
- Canvas;
- Web Audio;
- WebGPU;
- Web Storage (`localStorage`, `sessionStorage`);
- History и Navigation API;
- множество других API.

**Пример различия:**

```javascript
const response = await fetch('/api/users');
const users = await response.json();
```

Здесь:

1. `await` и `Promise` относятся к возможностям ECMAScript (язык).
2. `fetch()` предоставляется host environment (браузером или серверным рантаймом).
3. HTTP-запрос выполняется браузерной сетевой подсистемой.
4. Результат возвращается в JavaScript в виде объекта `Response`.

Это фундаментальное различие необходимо понимать при изучении современного JavaScript: **язык определяет вычислительную модель, а Web Platform предоставляет среду, в которой эта модель получает доступ к браузерным возможностям.**

## 22.2. HTML как декларативный слой приложения

HTML не является альтернативным синтаксисом JavaScript. Он решает другую задачу: описывает структуру документа и интерфейса в декларативной форме.

**Пример:**

```html
<button type="button">Save</button>
```

браузеру не требуется JavaScript для того, чтобы:

- создать элемент;
- включить его в DOM;
- сделать его доступным для взаимодействия;
- обработать базовое поведение кнопки (фокус, нажатие, отображение);
- включить элемент в accessibility tree (дерево доступности).

JavaScript нужен тогда, когда приложение должно добавить собственную логику:

```javascript
button.addEventListener('click', saveDocument);
```

Такое разделение обязанностей уменьшает количество кода и позволяет браузеру использовать собственные оптимизированные механизмы.

### HTML предоставляет поведение без JavaScript

Современный HTML содержит множество возможностей, которые раньше часто реализовывались библиотеками:

- **Семантические элементы** — `<header>`, `<main>`, `<section>`, `<article>`, `<nav>`, `<footer>`, обеспечивающие доступность и SEO.
- **Формы и встроенная валидация** — атрибуты `required`, `pattern`, `min`, `max`, `type="email"`, `type="url"` для проверки ввода без JavaScript.
- **`<dialog>`** — встроенные модальные окна с методами `show()`, `showModal()`, `close()`.
- **`<details>` и `<summary>`** — раскрывающиеся блоки без JavaScript.
- **`<template>`** — шаблоны для будущего содержимого.
- **`<input>` с различными типами** — `date`, `color`, `range`, `number`.
- **Нативные механизмы загрузки ресурсов** — `loading="lazy"`, `preload`, `prefetch`.
- **Ссылки и навигация** — обычные ссылки с нативной навигацией.
- **Встроенные элементы мультимедиа** — `<video>`, `<audio>` с нативными контролами.

**Пример раскрывающегося блока:**

```html
<details>
  <summary>More information</summary>
  <p>Additional information.</p>
</details>
```

Браузер обеспечивает анимацию, управление доступностью и состояние раскрытия без JavaScript.

Такой подход имеет важное архитектурное преимущество: браузер знает семантику элемента и может обеспечить его базовое поведение, доступность и взаимодействие без дополнительного runtime-кода.

### JavaScript дополняет HTML

JavaScript не должен без необходимости заменять декларативную возможность императивным кодом.

- Если задача решается HTML, лучше использовать HTML.
- Если задача относится к визуальному представлению, лучше использовать CSS.
- Если задача требует вычислений, координации данных, работы с API или сложного поведения, тогда используется JavaScript.

Это разделение ответственности является одним из ключевых принципов современной Web Platform.

## 22.3. DOM: граница между документом и JavaScript

DOM представляет документ в виде объектов, доступных программному коду. Это интерфейс, через который JavaScript взаимодействует с HTML-документом.

**JavaScript может:**

- находить элементы (`querySelector`, `getElementById`);
- создавать узлы (`createElement`, `createTextNode`);
- изменять атрибуты (`setAttribute`, `getAttribute`);
- изменять текст (`textContent`, `innerHTML`);
- добавлять и удалять элементы (`appendChild`, `removeChild`, `remove`);
- подписываться на события (`addEventListener`);
- изменять классы (`classList.add`, `classList.remove`);
- изменять CSS Custom Properties (`style.setProperty`);
- взаимодействовать с формами и другими браузерными API.

**Пример:**

```javascript
const button = document.querySelector('#save');

button.addEventListener('click', () => {
  button.disabled = true;
});
```

В этом коде JavaScript не рисует кнопку самостоятельно. Он изменяет состояние объекта DOM, после чего браузер самостоятельно определяет, какие изменения необходимо выполнить в стилях, layout, paint и compositing.

Это принципиально важное различие.

### JavaScript не является графическим движком

Когда JavaScript выполняет:

```javascript
element.classList.add('active');
```

он не выполняет самостоятельно:

1. пересчёт CSS;
2. вычисление геометрии (Layout);
3. растеризацию (Paint);
4. композицию слоёв (Composite).

Эти задачи относятся к браузерному rendering pipeline (глава 16).

Поэтому архитектура производительного приложения заключается не в попытке вручную управлять каждым этапом отрисовки, а в том, чтобы **передавать браузеру минимально необходимое количество изменений**.

Именно поэтому вопросы DOM-мутаций, layout thrashing, `transform`, `opacity`, CSS animations и compositor layers рассматриваются в контексте производительности в главе 16.

## 22.4. CSS как специализированный язык представления

Современный CSS — это не просто набор свойств цвета, размера и отступов. Он предоставляет собственную вычислительную модель для:

- layout (flexbox, grid);
- адаптивного дизайна (media queries, container queries);
- анимаций (CSS animations, transitions);
- переходов (transitions);
- медиа-запросов (media queries);
- container queries;
- custom properties (переменные CSS);
- scroll-driven animations;
- визуальных эффектов (фильтры, маски, клипы).

Поэтому JavaScript не должен вычислять то, что CSS может выразить непосредственно.

**Пример:**

Вместо постоянного изменения координаты элемента через JavaScript:

```javascript
// ❌ Плохо — JavaScript управляет позицией
element.style.transform = `translateX(${x}px)`;
```

JavaScript может установить состояние:

```javascript
// ✅ Хорошо — JavaScript устанавливает состояние
element.classList.add('open');
```

а CSS отвечает за визуальное представление:

```css
.panel {
  opacity: 0;
  transform: translateY(-10px);
  transition: opacity 0.3s, transform 0.3s;
}

.panel.open {
  opacity: 1;
  transform: translateY(0);
}
```

Такое разделение позволяет браузеру самостоятельно оптимизировать визуальное обновление, используя механизмы transitions и compositing.

### CSS Custom Properties как граница между JavaScript и CSS

JavaScript может передавать данные в CSS через Custom Properties:

```javascript
element.style.setProperty('--progress', '72%');
```

CSS использует это значение:

```css
.progress {
  width: var(--progress);
}
```

JavaScript при этом не знает, каким способом браузер должен отрисовать результат. Он передаёт состояние, а CSS определяет его визуальное представление.

Это особенно полезно для компонентов (передача параметров), темизации (переменные темы), анимаций (динамические значения) и визуализации данных (индикаторы, графики).

## 22.5. Web APIs: JavaScript как координатор специализированных подсистем

Современный JavaScript особенно эффективен тогда, когда он связывает несколько специализированных API.

**Пример приложения, использующего множество подсистем:**

```
HTML
  ↓
DOM
  ↓
JavaScript
  ├── Fetch API ─────── сеть
  ├── Streams ───────── потоковые данные
  ├── Web Workers ───── фоновые вычисления
  ├── WebGPU ────────── GPU
  ├── Web Audio ─────── аудио
  └── Web Components ── компоненты
```

Каждая подсистема выполняет свою специализированную работу. JavaScript связывает их в единое поведение приложения.

**Пример приложения обработки изображения:**

1. Получить файл через HTML `<input type="file">`.
2. Прочитать его средствами File API.
3. Передать тяжёлые вычисления Web Worker (не блокируя UI).
4. Выполнить GPU-вычисления через WebGPU.
5. Показать результат через Canvas.
6. Обновить интерфейс через DOM.

JavaScript в такой архитектуре не должен самостоятельно реализовывать файловую систему, сетевой стек, GPU-драйвер или растеризатор. Его задача — **координировать специализированные возможности платформы**.

## 22.6. Декларативность не означает отказ от JavaScript

Переход к декларативным возможностям Web Platform иногда ошибочно интерпретируют как движение к «JavaScript без JavaScript». Это неверно.

Современная архитектура не устраняет JavaScript. Она изменяет границу его ответственности.

**JavaScript особенно нужен для:**

- бизнес-логики;
- управления состоянием;
- асинхронных операций;
- сетевого взаимодействия;
- обработки пользовательских событий;
- координации Web APIs;
- сложных вычислений;
- интеграции независимых компонентов;
- фоновой обработки через Workers;
- управления данными приложения.

**При этом JavaScript не должен без необходимости брать на себя:**

- базовую семантику HTML;
- стандартное поведение элементов;
- CSS layout;
- большую часть визуальных эффектов;
- ручную реализацию браузерной навигации;
- собственную систему событий вместо `EventTarget`;
- собственный механизм загрузки ресурсов вместо возможностей платформы.

Именно такое разделение позволяет уменьшить объём прикладного кода без потери возможностей.

## 22.7. Что означает «нативный» в 2026 году

Термин «нативный» необходимо использовать точно.

**Следующие возможности являются частью зрелой Web Platform и могут использоваться как фундамент архитектуры при наличии соответствующей браузерной поддержки:**

- DOM;
- `EventTarget`;
- `URL` и `URLSearchParams`;
- Fetch API;
- Web Workers;
- Web Components (Custom Elements, Shadow DOM);
- Declarative Shadow DOM;
- CSS Custom Properties;
- CSS animations и transitions;
- многие современные HTML-элементы (`<dialog>`, `<details>`, `<template>`).

**Но наличие стандарта ещё не означает одинаковую поддержку каждой новой возможности во всех браузерах.**

Поэтому перед использованием свежего API необходимо проверить:

1. Статус стандарта (какая стадия TC39 или WHATWG).
2. Статус Baseline (Newly Available или Widely Available).
3. Поддержку целевых браузеров (Chrome, Firefox, Safari, Edge, их версии).
4. Необходимость fallback (альтернативное решение для старых браузеров).
5. Необходимость polyfill (возможность эмуляции через библиотеку).
6. Влияние API на архитектуру приложения.

Это особенно важно для технологий, которые в 2026 году всё ещё находятся на разных стадиях зрелости.

### Signals не являются частью этой нативной основы

TC39 Signals нельзя включать в список уже стандартизированных нативных механизмов JavaScript. Предложение Signals находится на ранней стадии стандартизации (Stage 1). Поэтому в 2026 году приложение, использующее Signals, использует конкретную библиотечную или фреймворковую реализацию реактивности, а не встроенный стандарт ECMAScript.

Гранулярная реактивность при этом является вполне реальной архитектурной техникой. Но её нельзя называть нативной возможностью JavaScript до завершения стандартизации и появления соответствующей реализации в целевых средах.

## 22.8. Почему современный JavaScript требует меньше инфраструктурного кода

В прошлом веб-приложение часто включало собственные реализации или библиотеки для задач, которые постепенно переходили в Web Platform.

Разработчику приходилось добавлять дополнительные решения для:

- маршрутизации (сейчас — Navigation API);
- HTTP-запросов (сейчас — Fetch API);
- событий (сейчас — EventTarget);
- компонентов (сейчас — Web Components);
- анимаций (сейчас — CSS animations, View Transitions);
- управления DOM (сейчас — DOM API, Shadow DOM);
- работы с потоками (сейчас — Streams API);
- фоновых вычислений (сейчас — Web Workers, Service Workers).

Сегодня значительная часть этих задач имеет стандартизированные API.

**Это не означает, что библиотеки больше не нужны.**

Библиотека или фреймворк оправданы, когда они дают приложению дополнительную архитектурную ценность:

- сложное управление состоянием;
- реактивную модель (при отсутствии стандарта);
- маршрутизацию с поддержкой вложенных маршрутов;
- SSR и hydration;
- code splitting;
- единый компонентный runtime;
- инструменты сборки;
- разработческую инфраструктуру (DevTools, hot reload);
- соглашения для большой команды.

Современный принцип заключается не в том, чтобы **отказаться от библиотек**, а в том, чтобы **не добавлять зависимость для возможности, которую Web Platform уже предоставляет достаточно хорошо**.

## 22.9. JavaScript как оркестратор Web Platform

Современное веб-приложение можно представить как систему специализированных подсистем:

```
                 Web Application
                       │
                  JavaScript
                  /    │    \
                 /     │     \
              HTML    CSS    Web APIs
               │       │       │
              DOM   Rendering   ├─ Network (Fetch)
                               ├─ Workers
                               ├─ Storage (IndexedDB)
                               ├─ Graphics (Canvas, WebGPU)
                               └─ Media (Web Audio, WebRTC)
```

JavaScript находится в центре этой системы не потому, что должен выполнять всю работу самостоятельно, а потому, что он связывает разные подсистемы.

**Правильная архитектура выглядит так:**

- HTML описывает структуру и семантику.
- CSS описывает представление и визуальное поведение.
- Браузер управляет DOM, layout, paint и compositing.
- Web APIs предоставляют системные возможности (сеть, файлы, графика).
- JavaScript связывает данные, состояние, события и действия пользователя.
- Специализированные Workers и другие API получают задачи, которые не должны блокировать основной поток.

Такой подход уменьшает количество кода, снижает связанность и позволяет браузеру использовать собственные оптимизации.

## 22.10. Главный принцип Modern JavaScript 2026

Modern JavaScript 2026 — это не движение от JavaScript к HTML и не движение от библиотек к «чистому браузеру».

Это движение **от ручной реализации инфраструктуры к использованию стандартизированных возможностей платформы**.

Разработчик должен сначала определить, какая часть задачи уже решается HTML, CSS или Web API. Только после этого следует писать собственную JavaScript-логику.

**Практическое правило:**

> **Сначала используй семантику HTML, затем возможности CSS, затем Web APIs и только после этого добавляй необходимую JavaScript-логику.**

При этом JavaScript остаётся центральным языком координации приложения. Он управляет состоянием, данными, событиями, асинхронными операциями и взаимодействием между подсистемами.

Именно поэтому современный JavaScript становится не менее важным, а более архитектурным: **меньше кода выполняет больше работы, потому что всё больше работы делегируется специализированным механизмам Web Platform.**

### Итог

В 2026 году профессиональная работа с JavaScript требует понимания не только ECMAScript, но и среды, в которой этот язык выполняется.

Необходимо различать:

- **ECMAScript** — язык и его вычислительную модель (синтаксис, типы, функции, классы, Promise).
- **HTML** — структуру и семантику документа (элементы, атрибуты, доступность).
- **DOM** — программное представление документа (объекты, методы, события).
- **CSS** — представление, layout и визуальное поведение (стили, анимации, адаптивность).
- **Web APIs** — возможности браузерной среды (Fetch, Workers, Storage, Graphics).
- **JavaScript** — прикладную логику и координацию этих подсистем.

Главный навык современного JavaScript-разработчика — не умение заменить платформу собственной абстракцией, а способность правильно определить **границу ответственности JavaScript**.

Хороший код 2026 года не пытается управлять браузером на каждом низком уровне. Он формулирует намерение, передаёт работу подходящей подсистеме и использует JavaScript там, где действительно требуется программная логика.
