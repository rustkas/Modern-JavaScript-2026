# Часть I. JavaScript в 2026 году

# Глава 3. JavaScript как язык современной Web Platform

За последние годы JavaScript изменился не только как язык, но и как способ построения приложений. Если раньше большая часть логики реализовывалась собственным кодом или сторонними библиотеками, то современная Web Platform предоставляет готовые стандартизированные механизмы для работы с сетью, файлами, потоками данных, многопоточностью, безопасностью и пользовательским интерфейсом.

Сегодня задача JavaScript — не заменить возможности платформы, а объединить их в единую архитектуру приложения.

---

## 3.1. Web Platform как стандартная библиотека JavaScript

ECMAScript определяет синтаксис языка, но большинство прикладных возможностей предоставляет сама платформа.

Современная среда выполнения включает десятки стандартизированных API, которые стали частью повседневной разработки:

- **Fetch API** — современный интерфейс для сетевых запросов, заменивший устаревший XMLHttpRequest. Поддерживает промисы, потоки и отмену операций.
- **URL API** — парсинг, конструирование и работа с URL-адресами через объекты `URL` и `URLSearchParams`.
- **URLPattern** — маршрутизация и сопоставление URL с шаблонами, замена для ручного разбора путей с помощью регулярных выражений.
- **Streams API** — потоковая обработка данных, позволяющая читать и записывать данные по частям без загрузки всего объёма в память.
- **Web Crypto API** — криптографические операции: хеширование, шифрование, генерация ключей и цифровые подписи.
- **Encoding API** — преобразование между различными кодировками (UTF-8, UTF-16, Base64).
- **Clipboard API** — безопасное чтение и запись данных в системный буфер обмена.
- **Permissions API** — запрос и проверка разрешений на использование чувствительных функций (геолокация, уведомления, камера).
- **File API** — работа с файлами из операционной системы: чтение, запись, получение метаданных.
- **Web Storage** — хранение данных в браузере через `localStorage` и `sessionStorage`.
- **IndexedDB** — полноценная документо-ориентированная база данных в браузере для хранения больших объёмов структурированных данных.

Вместо написания собственных реализаций разработчик использует встроенные механизмы платформы, получая высокую производительность, безопасность и кросс-платформенность. Например, вместо того чтобы писать собственный клиент для HTTP-запросов с обработкой ошибок, перезапросами и отменой, разработчик использует Fetch API с AbortController. Вместо ручного парсинга и сборки URL применяется встроенный конструктор `URL`. Вместо использования сторонних криптографических библиотек применяется Web Crypto API, который использует аппаратное ускорение и безопасное хранение ключей.

## 3.2. JavaScript и декларативный пользовательский интерфейс

Одним из важнейших изменений последних лет стало смещение логики из JavaScript в HTML и CSS. Современные приложения всё чаще используют декларативные возможности платформы, которые не требуют написания JavaScript-кода для базовой функциональности.

**`<dialog>`** — встроенный элемент для создания модальных окон и диалогов. Поддерживает методы `show()`, `showModal()` и `close()`, а также автоматическое управление фокусом и доступность. Раньше для создания модального окна требовалась библиотека или сотни строк JavaScript.

**Popover API** — декларативный способ создания всплывающих элементов (popovers, tooltips, dropdowns) без JavaScript. Использует атрибуты `popover`, `popovertarget` и `popovertoggle`.

**Form Validation** — встроенная валидация форм через атрибуты `required`, `pattern`, `min`, `max`, `minlength`, `maxlength`. Браузер автоматически проверяет ввод и показывает сообщения об ошибках без написания кода.

**View Transitions** — плавные анимации перехода между состояниями страницы. Позволяют создавать анимированные переходы между разными представлениями одной страницы или даже между разными страницами сайта.

**Scroll-driven Animations** — анимации, привязанные к позиции скролла. Позволяют создавать эффекты параллакса, анимировать элементы при прокрутке без JavaScript.

**CSS Anchor Positioning** — позиционирование элементов относительно других элементов с помощью CSS, без необходимости вычисления координат в JavaScript.

**Container Queries** — адаптивный дизайн на уровне компонента, а не всей страницы. Элементы могут изменять свой стиль в зависимости от размера родительского контейнера.

JavaScript больше не управляет каждым пикселем интерфейса. Его задача — изменять состояние приложения, позволяя браузеру самостоятельно выполнять отображение. Например, вместо того чтобы вручную показывать и скрывать модальное окно через JavaScript (`document.getElementById('modal').style.display = 'block'`), разработчик просто добавляет атрибут `open` к элементу `<dialog>` или использует Popover API. Браузер сам обрабатывает анимации, фокус, доступность и управление Z-индексом.

Такой подход уменьшает объём кода, снижает количество ошибок и повышает производительность, поскольку браузер оптимизирует отображение на уровне движка рендеринга.

## 3.3. Современный JavaScript как оркестратор платформы

Современные приложения состоят из множества специализированных подсистем. JavaScript координирует их взаимодействие:

- инициирует сетевые запросы через Fetch API;
- управляет потоками данных через Streams API;
- связывает пользовательский интерфейс с бизнес-логикой через реактивные модели;
- запускает вычисления в отдельных потоках через Web Workers;
- синхронизирует состояние между компонентами через сигналы или другие реактивные примитивы.

При этом вычисления могут выполняться в различных средах, каждая из которых оптимизирована для своего типа задач:

- **Web Workers** — вычисления в фоновых потоках, не блокирующих основной поток.
- **Worklets** — лёгкие скрипты, выполняющиеся на определённых этапах рендеринга (Paint Worklet, Animation Worklet, Audio Worklet).
- **WebAssembly** — высокопроизводительные вычисления, выполняемые в изолированной среде с почти нативной производительностью.
- **Сервер** — вычисления, требующие доступа к базе данных, файловой системе или другим серверным ресурсам.

JavaScript становится связующим слоем между компонентами системы, а не универсальным исполнителем всех операций. Например, в приложении с AI-обработкой изображений JavaScript запускает модель в Web Worker, передаёт данные через `postMessage`, получает результаты, обновляет UI через реактивную систему и отправляет метрики на сервер. Каждый компонент выполняет свою специализированную задачу, а JavaScript обеспечивает их интеграцию.

## 3.4. Унификация браузера и сервера

Исторически браузер и сервер предоставляли разные API. В последние годы ситуация кардинально изменилась.

Практически одинаково работают:

- **Fetch** — HTTP-запросы как в браузере, так и в серверных средах.
- **Request** — объект запроса, содержащий метод, URL, заголовки и тело.
- **Response** — объект ответа, содержащий статус, заголовки и тело.
- **URL** — парсинг и конструирование URL-адресов.
- **Streams** — потоковая обработка данных.
- **AbortController** — отмена операций.
- **Web Crypto** — криптографические операции.

Большую роль в этом процессе играет инициатива WinterTC (Winter Community Group), целью которой является стандартизация общих интерфейсов для браузеров и серверных сред. WinterTC определяет минимальный набор Web API, которые должны быть доступны в любой среде выполнения JavaScript.

Благодаря этому один и тот же код может использоваться в различных средах без изменений:

- **Browser** — клиентские приложения.
- **Node.js** — серверная разработка и инфраструктура.
- **Deno** — современная безопасная среда выполнения.
- **Bun** — высокопроизводительный JavaScript Runtime.
- **Edge Runtime** — выполнение на границе (Cloudflare Workers, Vercel Edge).
- **Cloudflare Workers** — вычисления в сети доставки контента (CDN).

Например, функция, которая выполняет HTTP-запрос и обрабатывает ответ с помощью Fetch API и Streams, будет работать одинаково в браузере, Node.js, Deno и Bun, без необходимости использования различных библиотек для каждой среды.

## 3.5. Архитектура без лишних зависимостей

Одной из тенденций JavaScript 2026 года стало постепенное сокращение количества внешних библиотек. То, что раньше требовало отдельных пакетов, сегодня часто реализуется средствами платформы:

| Раньше          | Сегодня                    |
| --------------- | -------------------------- |
| Axios           | Fetch API                  |
| Moment.js       | Temporal                   |
| path-to-regexp  | URLPattern                 |
| XHR             | Fetch                      |
| EventEmitter    | EventTarget                |
| Buffer-полифилы | Web Streams + Typed Arrays |
| crypto-js       | Web Crypto                 |

**Как это работает на практике:**

- **Axios → Fetch API** — вместо использования сторонней библиотеки для HTTP-запросов применяется встроенный `fetch()` с полной поддержкой промисов, отмены через AbortController и перехвата ошибок.

- **Moment.js → Temporal** — вместо тяжёлой библиотеки для работы с датами используется встроенный объект Temporal, который поддерживает временные зоны, длительности, интервалы и форматирование.

- **path-to-regexp → URLPattern** — вместо стороннего пакета для маршрутизации по URL используется встроенный URLPattern, который сопоставляет URL с шаблонами.

- **EventEmitter → EventTarget** — вместо сторонней реализации событийной модели используется встроенный EventTarget с методами `addEventListener`, `removeEventListener` и `dispatchEvent`.

- **crypto-js → Web Crypto** — вместо сторонней криптографической библиотеки применяется Web Crypto API с аппаратным ускорением.

Современный проект содержит меньше зависимостей, быстрее собирается и проще сопровождается. Меньшее количество пакетов означает меньшую поверхность для атак, меньше уязвимостей и меньший размер бандла. Кроме того, встроенные API обновляются вместе с браузером или рантаймом и не требуют отдельного управления версиями.

## 3.6. Реактивность и будущее JavaScript

Современные интерфейсы строятся вокруг реактивной модели, где изменения в данных автоматически приводят к обновлению пользовательского интерфейса.

Сегодня большинство популярных фреймворков используют собственные реализации реактивности:

- **Angular Signals** — реактивные примитивы в Angular, обеспечивающие точное отслеживание зависимостей.
- **Vue Signals** — реактивная система Vue, основанная на прокси и отслеживании зависимостей.
- **Solid Signals** — реализация реактивности в Solid.js, обеспечивающая тонкозернистые обновления.
- **Preact Signals** — реактивные примитивы в Preact, обеспечивающие высокую производительность.
- **Qwik Signals** — реактивность в Qwik, работающая на уровне компонентов и обеспечивающая возобновляемость (resumability).

На уровне ECMAScript ведётся работа над предложением Signals. На момент написания книги оно находится на ранней стадии стандартизации (Stage 1). Это означает, что предложение уже имеет формальную спецификацию и рассматривается комитетом TC39, но ещё не готово к реализации в движках.

Статус Stage 1 означает, что:

- Предложение было представлено и принято комитетом.
- Идёт работа над детальной спецификацией.
- Экспериментальные реализации могут появляться, но не гарантированы.
- API и поведение могут существенно измениться до финальной стандартизации.

Говорить о встроенной реактивности языка пока преждевременно. Однако направление развития уже очевидно: язык постепенно получает общие механизмы, которые позволят различным библиотекам использовать единые примитивы реактивного программирования. Это снизит фрагментацию и позволит фреймворкам взаимодействовать между собой через стандартный интерфейс.

## 3.7. JavaScript как язык композиции

Главная особенность JavaScript 2026 года заключается не в появлении большого количества нового синтаксиса. Изменился сам стиль разработки.

Современное приложение строится как композиция независимых возможностей платформы:

- **HTML** отвечает за структуру — семантические элементы, атрибуты, доступность.
- **CSS** — за отображение — внешний вид, адаптивность, анимации.
- **Web API** — за инфраструктуру — сеть, файлы, потоки, криптография, хранение.
- **JavaScript** — за координацию и бизнес-логику — управление состоянием, интеграция API, обработка пользовательских действий.

Чем меньше JavaScript занимается тем, что уже умеет браузер, тем проще, быстрее и надёжнее становится приложение. Например, вместо того чтобы писать код для валидации формы, можно использовать встроенные атрибуты валидации. Вместо управления модальными окнами через JavaScript можно использовать `<dialog>` или Popover API. Вместо реализации сложной анимации в JavaScript можно использовать CSS-анимации или View Transitions.

Этот подход не означает, что JavaScript становится не нужен. Он означает, что JavaScript используется там, где он действительно необходим: для бизнес-логики, сложных вычислений, интеграции с внешними системами и координации компонентов, а не для решения задач, которые платформа уже умеет решать.

## Заключение главы

Современный JavaScript перестал быть языком, который должен самостоятельно решать каждую задачу. Его главная роль — объединять возможности Web Platform в целостную архитектуру приложения. Стандартизированные API, такие как Fetch, Streams, Web Crypto и Temporal, заменяют сторонние библиотеки и предоставляют высокопроизводительные, безопасные и хорошо протестированные решения. Декларативные механизмы HTML и CSS — `<dialog>`, Popover API, View Transitions, Container Queries — снижают необходимость в JavaScript для управления интерфейсом. Унификация браузерных и серверных сред через WinterTC позволяет использовать один и тот же код в разных средах. Реактивные модели и будущее стандартизация Signals создают единую парадигму для управления состоянием. Все эти изменения формируют новую модель разработки, в которой язык выступает координатором взаимодействия между компонентами платформы. Именно эта способность эффективно использовать уже существующие возможности среды, а не дублировать их собственным кодом, определяет стиль разработки на JavaScript в 2026 году.
